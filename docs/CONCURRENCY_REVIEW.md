# 并发平台代码 Review

审查范围：`35f5232` 至本分支的运行平台、数据库、API、前端、部署和测试改动。方式为代码自审、故障注入、多进程集成与浏览器验证；未使用子 Agent。

## 审查中修复的问题

| 问题 | 处理与验证 |
|---|---|
| API 与 Redis 分别写入可能只成功一半 | 消息、路由和 Job 同事务提交；恢复不依赖用户轮询。Outbox 原子性/重投/进程测试覆盖 |
| 多进程重复 DDL 与业务事务可能死锁 | schema version 与迁移锁；已应用版本跳过 DDL；升级在停止旧进程后执行 |
| Case 旧快照覆盖新幂等状态、复活归档事项 | 三方合并拒绝冲突，归档与删除同事务，回滚重置本地基线；真实 PG 测试通过 |
| 全局确认锁让不同用户互相等待 | 对象锁与每用户事务；一个用户行锁被占用时另一用户仍能获得确认 |
| 业务提交后的网络异常被记为确定失败 | 异常归为 unknown；新确认也不能自动重执行；写后超时测试验证执行一次 |
| 异步取消发生在额度获取期间造成泄漏 | 等待线程完成获取再释放；重复取消与同步/异步模型路径测试覆盖 |
| SSE 首部断连/发送阻塞漏掉清理，任务 SSE 高频轮询 | finally 清理、发送期限、跨实例用户额度；事件唤醒替代 250ms 轮询 |
| 本地额度被 LRU 淘汰后重建绕过上限 | 活跃租约保留引用，弱引用注册表清理闲置项；600 个身份切换测试覆盖 |
| 通知合并但事件循环回调仍可能积压 | 每连接同时最多安排一个唤醒回调 |
| 已结束任务在 Redis 保留运行状态和会话占位 | 按 DB 终态清理，Redis 元数据有 TTL；数据库执行占位与未知状态保留 |
| 检索下载完整响应后才检查大小 | 下载期间限制字节、期限和结构；超大流响应提前终止测试覆盖 |
| 长会话首次加载重放全部历史 | 一致快照、最近 50 条消息、游标补拉；历史分页及工单权限测试、浏览器验证通过 |
| 集成场景依赖前一项启动消费者 | 场景可独立启动角色，Worker/Dispatcher 以成功轮询/迭代心跳判断就绪 |

## 结论和边界

已审查范围内未发现仍需阻塞本分支提交的缺陷。验证结果见 `CONCURRENCY_PROGRESS.md`。故障恢复采用可靠受理、可重复投递、数据库执行占位和未知结果人工核实，不能承诺跨第三方系统的 exactly-once。

生产容量尚未定标：合成负载验证回归行为，实际 GPU、模型质量、供应商额度及大规模长连接需要目标环境测试。Redis Cluster 分片、数据删除政策、托管基础设施高可用不在已验证能力内。嵌入式 Chroma 按版本化索引快照分发给独立副本。

部署应遵循运行手册的迁移顺序、连接预算、额度解释和故障处置。现有业务数据库、真实订单系统和原 JSON Case 未被本次测试修改。
