# 多轮任务与结构化提问方案

## 目标与交互

一个会话可以保留多个诉求，机器人一次推进一个任务。前端提供待办列表、继续/暂停/取消按钮和提问卡片；支持选择选项及自由文本。回答只补充所属任务，不能重新解释为无关对话。明确的改口直接执行，存在多个可能对象时先询问用户。

典型验收：

1. 用户申请退款，客服询问订单，用户补充订单号后继续原退款任务。
2. 用户在选择订单时说“不退款了，改查物流”，停止退款流程，旧选择和确认失效，进入物流任务。
3. 用户说“退款先放着，查另一单”，退款保存为暂停，可从待办列表恢复。
4. 用户一次提出查物流、退款、开票三个诉求，分别建任务，先推进第一项，其余保留待办。
5. 用户取消正在生成回复的任务，迟到回复不再发布。下游业务写入若已开始，不宣称撤回成功，转人工核实。
6. 页面刷新后仍可看到待办及未回答的问题；同一问题重复提交只处理一次，过期问题返回冲突。

## 领域与状态

新增 Task 管理会话内执行进度；保留 Case 管理跨会话业务事实、订单证据和幂等结果。Task 不擅自修改 Case 的订单状态，也不清空业务写操作的幂等记录。

任务保存 ID、所属会话、意图、原始请求、已补充字段、状态、版本、提问及创建/更新信息。状态包含 queued、ready、running、waiting_input、waiting_confirmation、paused、completed、cancelled、needs_human。同一会话最多一个 ready/running/waiting_input/waiting_confirmation 任务。

提问包含 question_id、任务版本、字段、提示语、选项；订单候选来自现有权威订单查询结果。字段补充与敏感业务确认分开：选择订单不能视为同意退款。确认令牌继续由 MutationGuard 管理。

## 数据与并发

任务存储复用人工客服数据库及会话行锁，新增任务快照、会话级选择问题、任务轮次路由表。每次状态变化写入同一会话事件流，供客户端断线补拉和历史工单回看。新表使用独立 CREATE TABLE/INDEX，不改动现有业务表。

聊天入站事务同时完成消息去重、任务路由、版本更新及执行占位；Worker 从已保存的路由恢复原任务。等待用户期间不保留 Worker、LLM 配额或数据库事务。

取消、改口、切换及恢复任务递增会话 control_version，复用现有 LLM/工具/发布拦截和确认令牌绑定。任务版本用于按钮与问题提交的乐观检查。新建请求 ID，重复提交同一 ID，均保持现有幂等约束。

下游写操作在途或结果未知时，暂停后续执行、记录待核实并转人工；取消的是后续任务推进，不等价于撤回退款。人工接管冻结待办；人工结束后需要用户明确继续，不自动重放业务操作。客服查看任务列表遵守工单历史结束序号。

## 路由与执行

处理顺序：验证身份与请求幂等 → 明确任务控制/提问回答 → 新增或切换诉求 → 恢复原请求和补充字段 → 现有意图/查询改写/执行器。

首版用保守规则识别明确的任务控制及常见电商意图组合；不确定指代通过选择卡片询问，不猜测要取消哪个任务。复杂表达可通过待办按钮明确操作。每轮新增任务数和会话未完成任务数设上限。

Workflow 显式返回结构化缺失字段/订单候选，不能通过匹配最终回复中的问号判断任务是否完成。未开放的开票等业务沿用真实人工接管，不伪造执行能力。对话问候不创建待办。

## 接口与前端

扩展 chat 请求的 task_action、task_id、task_version、question_id。所有实际任务字段与路由由服务端验证、生成；客户端不能直接设置任务状态。新增会话任务查询接口。chat 响应可携带任务和提问快照，SSE 以事件序号刷新任务列表。

客户端使用稳定请求 ID 重试，问题被回答/取消后禁用旧卡片。处理期间允许用户提出改口或取消；旧响应不能清除新请求的输入或确认。客服工作台显示交接时的待办与缺失信息。

## 实现与运行

实现分支为 `codex/multiturn-tasks`，基于人工接管基线 `a3c2936`。

- `app/tasks/routing.py`：明确控制词、常见诉求拆分、选项解析、原任务与补充字段重建。
- `app/tasks/service.py`：数据库状态转换、提问版本、待办选择、轮次路由和历史快照。未命中入站规则的单个业务诉求，在现有意图识别后也会登记任务。
- Workflow 返回缺失字段；ReAct 可调用 `ask_user` 返回提问和最多 5 个选项。订单选项必须来自本轮成功的订单查询。回答后重新进入执行器，不保存长期运行的模型调用。
- 用户端 `TaskPanel` 展示待办及提问；客服端只读展示交接任务。任务状态与提问经同一 SSE 事件流恢复。

新增 `conversation_tasks`、`conversation_task_choices`、`conversation_task_turns` 三张表，无新增运行依赖。数据库与启动配置沿用 [人工接管运行说明](HUMAN_SUPPORT.md)，运行 `python -m scripts.init_support_db` 初始化新表；API 和 Worker 使用相同的 `SUPPORT_DATABASE_URL`。本次新表尚未正式发布；后续修改已发布表结构必须提供版本化迁移。

升级时暂停入站并排空旧任务，同步更新 API、Worker 与前端，避免旧 Worker 忽略任务路由。原有消息仍保留，但不会根据历史聊天自动重建待办；旧 Case 中的待选订单继续使用兼容路径，新流程使用任务表保存问题。

### 接口示例

`GET /api/v1/sessions/{session_id}/tasks` 返回 `tasks`、会话级待办选择 `question`、`mode` 与 `control_version`。身份校验沿用原会话所有权。

回答任务问题仍使用 `POST /api/v1/chat`：

```json
{
  "session_id": "会话 UUID",
  "request_id": "本次请求 UUID，重试时复用",
  "message": "ORD-A",
  "task_action": "answer",
  "task_id": "任务 UUID",
  "task_version": 3,
  "question_id": "当前问题 UUID"
}
```

暂停、继续、取消分别使用 `pause`、`resume`、`cancel`，提交当前任务 ID 和版本。会话级“处理哪个待办”卡片只需 `task_action=answer`、`question_id` 和选项值；服务端保存对应动作及原诉求。普通文本消息仍可识别明确控制和补充信息。过期版本或问题返回 409，不能覆盖较新的任务。

### 当前边界

- 一次最多创建 5 个任务、会话最多保留 20 个未完成任务。一次只推进一个任务，完成后由用户选择继续其他待办，不自动批量提交业务。
- 普通选择答案不代表同意退款。退款等写操作仍须单独确认；改口或切换后旧确认失效。刷新后点击“重新核对”获取新的确认。
- 自然语言任务控制采用保守规则，复杂否定、指代和长段混合诉求仍需进一步扩充评测。按钮提供明确的控制路径，不声称已支持任意自然语言任务规划。
- 队列、订单和模型分别使用既有设施。此次浏览器/API 验证使用隔离的模拟订单和模型，不包含真实退款或模型质量评估。
- 会话任务和事件尚未提供归档清理、容量指标或压测报告；现有数据库轮询 SSE 的容量边界保持不变。
