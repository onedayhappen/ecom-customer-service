# 事项执行与调度设计

## 执行单位

执行器处理一个明确事项，使用该事项的目标、有效原话、当前版本和业务证据。原话中的其他诉求只提供上下文，不自动加入当前执行；独立事项由调度器分别安排。

`task_id` 标识事项，`job_id` 标识一次执行。执行记录保存所属用户、事项版本、来源、会话控制版本、租约、截止时间、工具结果和已消耗预算。

## 调度与并发

`TaskSchedule` 先持久化执行请求，再发出唤醒；`TaskWorker` 在短事务中检查事项、来源、依赖与资源额度后领取任务。模型和工具调用在事务外运行。

同一事项跨会话只有一个有效执行者。相同事项及版本的重复唤醒复用任务；新版本替代尚未开始的旧任务。独立事项可在用户、租户和全局额度内并行。

等待用户、等待外部结果、暂停和终止事项不持续占用模型槽位。涉及同一订单、库存或权益的业务操作还要检查共同资源，事项编号不同不意味着资源独立。

`TASK_GLOBAL_CONCURRENCY`、`TASK_USER_CONCURRENCY` 和租户额度约束各进程的资源使用。数据库唯一性、条件更新和租约防止跨进程重复领取，进程内线程池只控制本进程并发。

## ReAct 执行

1. 验证执行资格，构建当前事项上下文及工具定义。
2. 调用模型，解析工具名称及参数。
3. 每个工具调用前重新检查身份、事项范围、来源、控制状态与预算。
4. 工具返回后保存带对象和来源的事实，再决定下一步。
5. 通过 `ask_user` 等待补充，通过准备工具生成确认内容，通过人工交接工具建立工单。
6. 生成执行结果供回复协调器检查；ReAct 自由草稿不直接成为业务结论。

模型不能指定他人身份或绕过确认提交业务。完整工具目录计入上下文，分发时检查实际调用权限。

## 运行中接收事项变化

在模型调用前、工具调用前后和发布前检查新输入。新消息尚未关联时，等待发生在事务外，仍受总截止时间约束。

关联完成后，只有能逐版本对应到有效关联决定的变更可以由原执行消费：

| 更新                             | 执行处理                                   |
| -------------------------------- | ------------------------------------------ |
| 无实质变化                       | 继续                                       |
| 补充信息或改变条件               | 读取新上下文，放弃未执行的旧计划，重新规划 |
| 新增独立目标                     | 新事项单独调度                             |
| 变更处理对象                     | 重新确定范围，旧对象证据不能移用           |
| 暂停、取消、接管、纠错或来源失效 | 原执行退出，走对应控制与恢复路径           |

一次模型响应含多个工具调用时，每次调用前都检查更新。已返回的模型计划不能跨越事项更正继续执行。

## 预算与恢复

模型、工具、循环和重试预算随执行持久化在 `runtime_jobs.payload.usage`。重新规划和进程恢复继承消耗与总截止时间，不能清零后无限重试。

过期租约使旧 Worker 失去提交权。恢复从数据库中的最新事项、有效来源和已有回执重建请求，不要求恢复某个协程或模型调用现场。

迟到工具结果保留在事件中并标记迟到，不直接作为当前回复依据。只读证据复用仍检查对象、参数、来源和时效；业务写入结果未知时查询原操作编号，不自动重放。
