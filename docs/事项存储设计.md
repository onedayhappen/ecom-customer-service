# 事项存储设计

## 职责与数据模型

事项保存用户希望完成的目标及处理进度，不以订单号或会话号作为唯一标识。例如，同一订单的物流咨询和退货申请可以是两个事项；用户切换会话后仍可续接原事项。

| 字段                        | 语义                                       |
| --------------------------- | ------------------------------------------ |
| `task_id` / `user_id`       | 事项编号与所属用户；用户身份来自认证上下文 |
| `goal`                      | 当前完整目标，包含仍有效的条件与限制       |
| `details`                   | 有来源的结构化细节                         |
| `waiting_for`               | 待用户补充或待外部结果的信息               |
| `status`                    | 事项沟通状态                               |
| `version`                   | 并发更新与证据有效性检查使用的版本         |
| `created_at` / `updated_at` | 创建与变更时间                             |

`TaskStatus` 包含 `in_progress`、`waiting_user`、`waiting_external`、`paused`、`completed`、`cancelled`。这些状态不表示订单、退款或物流的真实状态。

## 数据关系

`conversation_tasks` 保存事项；会话与原始消息通过关联记录连接到事项。一条消息可以关联多个事项，同一事项也可以关联多个会话。事项变更通过 `task_changes` 和事件记录保留来源与前后值。

来源契约包括：

- `MessageSource`：指定会话与原始消息序号。
- `ToolSource`：指定同一用户事项中的工具结果事件。
- `SupportSource`：指定同一事项中的人工更新事件。

来源用于解释“为什么保存这个值”，不自动赋予业务操作权限。工具结果、原话和业务操作回执保留各自身份。

## 读写接口

`TaskRepository(store, authenticated_user_id)` 在用户范围内提供：

| 方法           | 行为                         |
| -------------- | ---------------------------- |
| `create`       | 创建事项及来源关联           |
| `get` / `list` | 按用户、事项或会话读取与分页 |
| `update`       | 检查预期版本后更新允许字段   |
| `ask`          | 保存问题、选项和绑定版本     |
| `history`      | 查询事项版本及变更来源       |

`update` 中省略的字段保持原值，提供 `details` 时替换整个对象，`waiting_for=None` 明确清除等待。读取后合并细节的调用方必须携带读取时的版本提交。

## 原子性、版本与幂等

一次变更同时保存事项、版本、来源、事件和幂等回执。事务失败时一起回滚。两个请求竞争同一预期版本时，只接受符合当前版本的一次变更。

稳定的 `change_id` 标识一次固定变更。相同编号与相同内容重试返回原回执；同编号不同内容被拒绝。原回执描述当时的变更结果，读取最新状态仍需调用 `get`。

待答问题具有 `question_id` 并绑定事项版本。只有问题已公开发布、版本有效且事项仍等待回答时，后续简短回答才能按该问题关联。

## 跨会话与恢复

按事项恢复时读取最新目标、有效来源、历史操作和接管状态。恢复历史事项只恢复沟通进度，不恢复旧确认凭证，不重复提交业务操作。另一用户即使知道 `task_id` 也不能读取或更新它。
