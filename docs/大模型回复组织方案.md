# 大模型回复组织

## 目标与流程

用户得到针对问题的自然语言回答，而不是工具字段列表。事项关联和 ReAct 不变；
回复模型只选择已核实的结论和顺序，不调用业务工具、不改变事项状态。

流程：收集可发布结果 → 生成允许结论 → 冻结证据 → 模型选择结论编号 → 后端校验并渲染 → 重新校验时效 → 原子发布。

## 输入

- 用户最近一次连续发送的原话，包括补充和改口；即使已有一个事项先回复，也保留这组请求。
- 业务时区、当前日期和消息时间，用于准确表达“今天”等相对时间。
- 最多 20 条近期公开对话，排除已失效消息；历史政策回答沿用现有重新检索提示。
- 本次可发布的各事项：目标、订单、状态、执行状态、允许结论编号与选择摘要、来源完整性和数据时间。
- 必须附上的澄清问题、固定编号选项、确认卡片提示。
- 当前会话仍在执行或等待外部结果的其他事项，只用来说明进度。

工具证据仍经过原来的用户归属、对象、版本、控制权、有效期和政策检查，再由 `app/tasks/reply_claims.py` 投影。
完整快照保留每条结论的对象引用、查询参数、证据编号、数据时间、完整性及限制。
发给模型的选择视图合并重复来源信息，仅保留摘要；完整正文和证据留在发布端校验，不重复发送。
不把完整数据库行、工具元数据、确认凭证、内部推理或 ReAct 草稿交给回复模型。
改写语句不作为业务事实；此次实现直接使用用户原话和已关联的事项目标。
整个模型请求遵守已有 token 预算，超限先删除完整历史消息；当前用户原话不裁切，无法容纳时兜底。
选择摘要有长度上限，完整正文留在发布快照。来源限制不会截断或遗漏；过长而无法安全展示时不生成该结论。

## 表达边界

提示词位于 `app/prompts/reply_composition.py`。模型仅返回 `{"claim_ids":["..."]}`，不能生成业务正文。
`render_plan` 拒绝自由文本、额外字段、未知或重复编号，以及遗漏其他待答事项的计划。
发布时只使用可信快照中的正文；给模型的副本即使被修改也不能改变已允许的结论。

物流和订单状态由后端模板生成：没有发货记录只表示未查到记录；签收时间缺失不能证明现实中未签收；
物流状态不能确定家人拿到的包裹身份。其他工具保留按单条回执组织的白名单记录，不能跨回执拼接状态。
结论与数据限制一起渲染，模型不能单独省略限制；原包裹与换货补发包裹保留各自对象及规格。
退款渠道成功记录明确不等于核实银行卡到账。查询读取时间不能替代上游同步时间。

澄清问题及其选项、操作确认提示、缺少可核实证据的提示由后端原样附在正文后。
只有这些固定提示时直接发送，不调用模型。业务记录本身的正确性仍依赖上游，系统只表达记录支持的范围。

## 并发与发送前校验

- `ConversationWorker` 使用独立线程池，至多两个回复任务并行；单个 Worker 内每会话最多一个任务。
- 模型调用在数据库事务之外，默认 15 秒超时，复用 `LlmClient`、并发限额和上下文预算，场景为 `reply_composition`。
- 先快照输入与可发布结果；生成后重新收集有效结果与政策检查，并比较指纹。
- 指纹包括用户各会话的消息接收位置、当前对话上下文、控制版本、来源修订号、事项版本和完整证据结论。
- 新消息、用户改口、转人工、证据过期、事项变化、新结果到达或已有回复发布，都会使旧草稿失效。
- 失效时不标记结果已发送，下轮重新准备。新消息即使与当前事项无关，也先等待关联完成；有效工具结果可复用。
- 发布事务沿用用户锁、会话锁、回复记录和通知写入。多个 Worker 可能重复生成，但只能发布一次。
- 进程退出不保存纯文本草稿；可发布结果仍在数据库，下次启动可重新组织，不重复执行业务工具。

本期不引入 Redis 草稿副本或新的数据库表。只合并生成开始时已经就绪的结果；
不为等待所有事项完成而无限延迟回复，也不新增人为聚合等待时间。

## 失败与观测

空输出、无效结论计划、被截断的模型输出、超时、调用失败或预算不足时，直接使用后端允许的结论兜底，
优先回答直接物流查询并保留证据限制，不再补调模型。迟到的模型结果无法自行写入用户消息。
通过 `reply.composition` 记录输入与输出，通过 `reply.composition.fallback` 记录降级，
通过 `reply.composition.discarded` 记录草稿未发送原因，继续写入原有逐交互日志。

配置：`REPLY_COMPOSITION_ENABLED=true`；`REPLY_COMPOSITION_TIMEOUT_SECONDS=15`。
关闭开关后 Worker 同样使用安全结论兜底，不会绕过证据含义限制。直接使用 ReplyCoordinator 的调用方需传入 composer；
正常 ConversationWorker 已注入 AgentEngine.compose_reply。

## 验证范围与后续事项

测试覆盖多事项合并、原话输入、ReAct 草稿隔离、模型调用不持有事务、新消息与状态变更、
证据过期、并发发布去重、问题提示保留、模型异常和迟到结果。另验证 Worker 接入与日志记录。

`tests/test_reply_evidence.py` 使用 `tests/fixtures/reply_evidence_cases.json` 中两条真实评测记录的原始工具结果，
经实际 TaskRuns / ReplyCoordinator 重放；覆盖历史错误答复拦截、正确计划、附加文本注入、关闭模型时的安全性、
跨订单和原件/补件边界、证据时间变化、退款范围及模型修改快照副本。使用隔离 SQLite，不访问业务数据库。

性能复核命令：`python scripts/verify_reply_evidence.py --baseline 7b65437 --output data/evaluation/reply-evidence-verification.json`。
脚本记录实际发布结果、调用次数、估算输入 token 和 500 次本地投影/校验耗时。不会调用真实模型；
测量不代表供应商端到端延迟或生产并发压测。发布路径没有新增业务查询、模型调用或数据库结构。

旧澄清未关闭造成的回复阻塞仍是独立问题；本次沿用现有澄清规则，未将其静默绕过。

  两次均生成自然语言正式回复，日志中没有模型降级或错误。
- 实测使用隔离 SQLite 和预置模拟工具证据，不代表真实业务数据库联调。没有提交业务操作。
