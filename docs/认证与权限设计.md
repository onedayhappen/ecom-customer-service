# 认证与权限设计

## 身份入口

MySQL 认证模式下账号身份保存在 MySQL，`users.user_id` 是稳定内部标识。用户名用于登录，不能代替业务外键。密码保存哈希，登录会话保存哈希编号、到期和撤销状态。`API_AUTH_BACKEND=auto` 按业务 DSN 选择 MySQL 或旧本地凭证模式；注册和服务端登录撤销能力不能不加区分地推广到旧模式。

注册、登录和退出由 `app/api/auth.py` 提供。正常注册不接受客服或管理员角色，新账号也不会自动取得已有演示用户的订单。

## HTTP 认证与 CSRF

认证中间件校验 Bearer JWT 或登录 Cookie，要求有效用户与过期时间。MySQL 认证模式还检查服务端登录会话，退出或撤销后旧会话不再有效。

通过 Cookie 认证的写请求要求 CSRF Cookie 与 `X-CSRF-Token` 匹配。前端统一客户端负责凭证、CSRF 和接口错误。CORS 限制允许来源，但不替代身份或资源归属校验。

健康、就绪、指标、登录注册及 CORS 预检使用明确公开路径；具体路径以中间件配置为准。

## 资源与角色权限

```mermaid
flowchart LR
    Request[请求凭证] --> Auth[身份与登录会话]
    Auth --> Scope[会话、事项与业务归属]
    Scope --> Role[客服角色与负责范围]
    Role --> Version[控制版本与操作条件]
    Version --> Action[读取或受控提交]
```

- 会话、事项、订单、持券、售后和票据逐层检查所属用户。
- 平台和租户范围由服务端构造，不能接受模型或请求正文自报。
- 已知订单、运单或工单编号不足以取得访问权限。
- 客服角色以 `support_staff` 为当前授权来源，工单读取与修改还检查负责关系和历史边界。
- SSE 每次补拉重新检查访问资格；权限撤回后关闭旧订阅。

模型输入中的政策、工具结果、历史文本和用户偏好都是资料，不改变服务端权限。用户说“以后不用确认”不能取消业务确认入口。

## MCP 请求上下文

独立 MCP 校验服务 Bearer 令牌及 `X-MCP-User-Context`，后者使用独立签名与有效期证明所代表的用户。

默认 Worker 还将可信的 `platform_code/store_id` 和本次允许的业务只读工具名写入该签名。服务端发现与实际调用均检查签名工具范围和服务端全局白名单，业务查询继续核验用户及渠道归属。每次获准读取独立签发令牌并关闭连接，认证状态不从其他用户的旧连接继承，见 [MCP工具服务设计](MCP工具服务设计.md)。

身份通过请求级 ContextVar 进入工具，调用结束或异常时在 `finally` 中恢复，避免跨用户残留。目录的 `readOnlyHint` 等元数据不构成授权；MCP 服务仍检查对象归属并拒绝需要事项上下文的工具。

## 敏感字段与确认凭证

地址、确认私密参数和处理方参数使用 AES-256-GCM，密文携带密钥版本与场景绑定信息。轮换保留旧版本以读取历史记录，各应用进程使用一致密钥。

确认凭证绑定固定操作、用户、事项版本、参数摘要和有效期，不交给模型。公开事件和日志保存必要脱敏信息，内部备注不进入客户或模型上下文。

开票进度查询按登录用户核验申请归属；票据下载每次再核验登录用户、申请归属、票据状态、私有文件路径范围及摘要，不接受任意文件 URL。演示票据沿用同样的权限检查，不因 `is_demo` 而公开。

图片原图和预览也通过鉴权接口读取，客户按所有者检查，客服按 `ticket_id` 及工单历史上限检查。知道附件 UUID 或文件摘要不能绕过归属，详见 [图片处理与多模态上下文设计](图片处理与多模态上下文设计.md)。
