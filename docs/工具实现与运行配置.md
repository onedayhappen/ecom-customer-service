# 工具实现与运行配置

本文对应 [工具设计](工具设计.md) 的 33 个基础工具和 15 个扩展工具，共 48 个。扩展能力包含数据库读写、用户确认、后台处理和处理方协议；真实渠道需部署时配置，未配置返回 unavailable。

## 2. 配置与迁移

2026-10-24 新增迁移 `008_after_sale_fulfillment`。数据库升级后，商品明细查询支持独立履约与售后进度；售后查询读取多个寄回/补发包裹。处理方协议新增逆向事件的 `return_shipment_id`，以及补发包裹的 `delivered_at`、`receipt_confirmed_at`。多退件事件须指明包裹；缺少换货收货确认时，本地任务保持处理中继续查询。补发回执按售后、承运商、单号复用已有包裹，实际 SKU 和规格单独存档。字段及模拟数据见 [售后履约说明](数据库表设计.md#after-sale-fulfillment)。

安装 `requirements.txt`，在 `.env` 配置 `ORDER_DB_DSN`、`API_JWT_SECRET` 和现有事项运行连接，然后执行：

```powershell
python -m scripts.migrate_mysql_business_schema
python -m scripts.migrate_mysql_business_schema --check
```

脚本按 `schema_migrations` 顺序执行 001–004。003 增加 7 张核心配套表，004 增加 19 张扩展表；已有数据库仅执行未登记版本。迁移不自动生成真实业务数据、用户领券记录或默认资格政策。

准备操作使用 AES-256-GCM 保存敏感参数，需配置：

```dotenv
BUSINESS_DATA_KEYS={"1":"<32字节随机密钥的URL-safe Base64编码>"}
BUSINESS_DATA_KEY_VERSION=1
```

密钥通过系统安全随机数产生，保存在本地环境配置或密钥管理服务，不提交到 Git。API 和 task worker 必须使用相同密钥，轮换后保留旧版本以读取历史记录。未配置密钥时读取工具可用，准备操作会明确返回配置不可用。

地址密文格式为 `12 字节 nonce + AESGCM 密文及 tag`，AAD 为 `address:{user_id}:{field}`，field 分别为 `recipient_name`、`phone`、`detail`。地址写入方必须遵守相同约定；改址准备会核实目标地址可以解密。发票抬头和税号分别使用 `invoice-title:{user_id}`、`invoice-tax:{user_id}`。完整目标地址及发票信息只在登录用户的确认卡片中显示，工具结果和事项回执保存脱敏摘要。

## 3. 可执行业务规则

`business_policy_versions.rules` 使用严格的 JSON 契约。`schema_version=1`；未知字段、未知版本、缺失规则、多个同时有效版本均不能自动放行。

| 字段 | 类型／含义 |
| --- | --- |
| `schema_version` | 固定整数 1 |
| `time_basis` | `request`、`order_created` 或 `delivered`；决定有效版本选择时间，默认 request |
| `allowed_statuses` | 该操作允许的订单状态数组，默认空数组 |
| `window_days` | 售后签收后期限；为空不应用该期限。要求完整签收依据 |
| `requires_reason_review` | 为 true 时需人工审核原因，自动资格返回 unknown |
| `refund_shipping` | 为 true 时当前实现返回 unknown；运费分摊依据尚未接入 |
| `local_authority` | 本地具有取消／改址／撤回控制权；默认 false |
| `inventory_managed`、`coupons_managed` | 取消订单时库存预留和券占用须纳入同一事务；默认 false |
| `threshold_basis` | 当前只支持 `goods_after_promotions` |
| `coupon_stacking`、`promotions_with_coupons` | 多券叠加、活动与券叠加许可；默认 false |
| `rag_policy_id`、`rag_policy_version` | 对应政策检索结果的 source_id 和 version；不一致会显示冲突，回复发布时拒绝引用 |

可执行 action：`refund_only`、`return_refund`、`invoice`、`cancel_order`、`change_address`、`after_sale_cancel`、`pricing`。这些字段由业务管理方维护，模型不能修改。带 channel 的规则要求可信渠道上下文；目前不能自动采用该规则。

优惠 kind 目前支持 `amount_off` 和 `percent_off`。`discount_bps` 表示减免比例的基点，例如 1000 表示减免 10%，不是支付 10%。适用范围类型为 `all`（scope_id 为 `*`）、`merchant`、`product`、`sku`。活动按 priority 降序执行，同组互斥；券按指定组合顺序执行并逐行分摊至分，不擅自替换组合。SKU 列价、优惠、订单必须使用相同币种。

领取成功时将券模板和范围保存到 `coupon_claim_rules`，后续按此快照解释持券承诺。领取事务锁定券模板并重查总量／个人限领；同一事项来源请求使用同一服务端生成的请求标识。

## 4. 当前执行边界

- 仅从 MySQL 读取业务事实，不使用旧工具或假数据回退。候选分页 10 条、明细 20 条、订单包裹每页 5 个且每包展示最近 3 条轨迹；签名游标绑定用户、筛选和数据快照，有效期 15 分钟。结果变动要求从第一页重新查；单次查询超过 10000 条返回范围过大。
- 订单、售后、发票必须属于当前用户；订单引用包含平台与订单号。公共商品未明确平台时，价格／领券判断需要先澄清，事项中的平台须能通过本人订单或有效账号绑定核实。
- `prepare_after_sale` 提交待审核申请与商品行；不调用支付退款接口。`prepare_invoice` 提交加密的待处理申请；不生成正式发票。
- 改址仅适用于本地控制且尚未进入发货流程的订单。取消仅适用于未支付、无进行中支付、无发货、库存预留完整且可释放券占用的订单。售后撤回仅适用于有本地提交依据、尚未受理且无有效退款的申请。
- 确认有效期 10 分钟；确认绑定事项、用户、操作参数、订单平台及业务快照，提交时再次核验规则和数据。MySQL 的业务变更、事件与回执在同一事务提交；超时通过原 operation_id 查询，不盲目重复写入。
- `ask_user` 保存具体问题并停止本轮；`handoff_to_human` 创建或复用真实工单；`read_task_context` 只读取当前授权事项及其工单记录。
- 政策文本来自现有经审核的 RAG 索引；未配置索引或检索失败时返回依据不足。外部办理通过下述后台处理协议接入。

## 6. 扩展能力与数据准备

| 能力 | 所需业务数据与行为 |
| --- | --- |
| 配送与补货 | `sku_fulfillment` 提供仓库和重量；`delivery_rules` 提供地区、首续重费用及天数；`restock_plans` 保存有来源的补货计划。多个匹配规则或缺数据不生成完整报价 |
| 会员积分 | `membership_levels`、`memberships`、`points_ledger`；余额按完整账务流水汇总，过期扣减由积分系统显式入账 |
| 下单 | `pricing` 和 `purchase` 规则、保存地址、SKU 库存、冻结券规则。报价不占用；用户确认时重新校验并事务创建订单、库存预留、券占用及超时记录 |
| 价格保护 | `price_protection` 规则、`order_item_benefits` 的成交时权益、`price_protection_prices` 的当前同口径价格；扣除历史申请和退款占用；确认登记，真实退款回执单独入账 |
| 换货与维修 | `exchange` / `repair` 规则和已配置处理渠道；换货占用指定 SKU 库存。真实处理回执驱动审核、退货授权、逆向物流和补发；拒绝／未受理撤回释放库存 |
| 退货寄回 | 必须已有有效 `return_authorizations`，读取真实地址和支持承运商。确认后仅登记实际运单，后续由处理方提供物流及验收事实 |
| 正式票与重开 | 由开票系统提供 `issued_invoices` 和真实私有文件；`invoice_reissue` 规则与处理渠道。重开完成必须同时提供原票作废凭据及新票，不覆盖旧票 |
| 催单 | 明确用户请求、本人可催订单及 `dispatch` 渠道；用户确认后登记队列，后台处理真实受理回执 |

新增可执行 action：`purchase`、`exchange`、`repair`、`price_protection`、`invoice_reissue`。新增规则字段：`quote_ttl_seconds`（30–3600，默认 600）、`payment_timeout_minutes`（1–1440，默认 30）、`allow_exchange_price_difference`（默认 false；启用时价差交由处理渠道办理，不由客服工具支付）。维修保修期使用原有 `window_days` 与签收依据。默认不生成政策、会员、运费或售后地址数据。

源码职责与相关表详见 [数据库设计](数据库表设计.md#12-扩展工具配套表)。业务数据的导入／同步由实际业务系统负责，工具不把知识库自然语言自动转换为可执行资格规则。

## 7. 外部处理协议与后台进程

配置示例（凭证仅存环境／密钥管理服务）：

```dotenv
COMMERCE_PROVIDER_CONFIG={"dispatch":{"url":"https://your-provider.example/commerce","token":"<secret>"}}
COMMERCE_INVOICE_ROOT=/private/invoices
CONTEXT_REQUEST_INPUT_TOKENS=24000
```

配置键可用 `dispatch`、`exchange`、`repair`、`price_protection`、`invoice_reissue`，每个独立配置 `url` 和 `token`。固定 HTTPS 地址，不接受工具参数指定 URL，不跟随重定向。通过 `Authorization: Bearer ...` 调用：

- `POST {url}/submit`：JSON `{request_id, kind, payload}`，请求头 `Idempotency-Key` 同 request_id。
- `POST {url}/query`：同一结构和请求编号。处理方必须保证 submit 幂等、query 可按编号核实；返回 not_found 后才按原编号重投。payload 会附最新已登记的 return_shipment，处理方按运单去重接收。
- 响应 `{status, reference, message?}`；status 为 accepted / processing / completed / rejected / not_found。除 not_found 外必须返回真实 reference。受理与完成分开。
- 换货／维修可附 `return_authorization: {address, carriers:[{code,name}], requirements, deadline}`，以及 `return_events:[{status,event_time,description}]`；先有授权和登记包裹才能保存逆向轨迹。
- 换货补发使用 `replacement_shipment: {tracking_number,carrier,shipped_at,sku_id,quantity,delivered_at?,receipt_confirmed_at?}`；可分次回执不同包裹。`completed` 需要全部换货数量已有可信收货确认记录，只有补发凭据时本地保持 `processing`。重复运单不重复创建和扣库存。
- 价保 completed 必须附 `refund: {payment_id,provider_refund_id,amount,currency,completed_at}`，原支付须属于订单且成功，金额与申请一致。
- 发票重开 completed 必须附 `original_voided: true` 和 `invoice: {invoice_number,document_key,mime_type,sha256,issued_at}`。document_key 为私有目录内文件路径。

时间使用 ISO 8601，金额使用十进制字符串。`commerce_provider_requests` 加密保存提交参数，用租约协调多 worker；业务状态与回执在一个事务更新。无凭据、超时或异常不能标记成功。轮询处理方完成状态也会更新真实售后子流程。

```powershell
python scripts/commerce_worker.py        # 常驻，每 10 秒检查一批
python scripts/commerce_worker.py --once # 单批维护／排障
```

Compose 已配置 `commerce-worker` 服务。该进程与 API 使用相同数据库、加密密钥和处理方配置，可单独作为服务部署。还负责关闭本地创建的超时未支付订单，释放库存及券；有支付处理中、成功支付或发货记录时不自动关单。没有自动扣款工具。正式票下载入口为 `/api/commerce/invoices/{issued_invoice_id}/document`，必须登录，每次检查归属、票状态、路径范围及文件摘要。

完整工具定义和上下文均计入请求预算，默认输入预算从 12000 调整到 24000；已有 `.env` 需同步修改，并按实际模型设置窗口与输出预留。不会根据关键词或 intent 裁掉工具。

事项维护进程通过已确认操作回执绑定新售后／开票申请，查询新表中的实际进度。维修完成、换货补发签收及正式开票各自核实；渠道退款成功不会被解释为银行卡已入账。被拒绝的业务进入人工核实。


## 2026-10-25 工具校验修复

- 无明确平台上下文时，从本人订单、已验证平台绑定和有效会员记录解析唯一平台；没有本人平台记录时，使用业务规则中唯一生效的平台。多平台有歧义时拒绝猜测，不沿用历史路由默认值 `pdd`。平台和用户身份不由模型参数提供。
- `claim_coupon`、`request_dispatch` 统一生成确认卡片；确认令牌绑定用户、事项、参数及版本。领取和催单分别复用券模板／订单锁及幂等回执。催单确认仅登记队列，由 commerce worker 联系处理方。
- 售后规则版本及期限按申请商品的原始包裹判断，换货和其他商品的物流不延长期限。商品分包时采用最早签收时间；缺少完整商品签收证据或跨规则版本时返回未知，需进一步核实。
- 改址准备和确认均核验新地址的配送规则；运费必须与原单一致。配送规则、地址或报价变化后不得使用旧确认，暂不支持自动补退运费。
- 商品搜索在 MySQL 过滤关键词、商家名、预算和属性，批量读取每个商品最多 5 个 SKU 摘要。商品和物流轨迹使用签名键集游标，每页独立读取并绑定用户和查询条件；它们不是跨请求的不可变快照。
- 售后详情限制内嵌包裹与轨迹，返回完整数量、截断标记和 `logistics_ref`。`get_logistics` 接受售后及退货包裹引用，可继续分页查看。
- 零金额商品或优惠分摊为零时直接保留原金额；负数或超额分摊被拒绝。
