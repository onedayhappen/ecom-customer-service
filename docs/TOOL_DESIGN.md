# 客服工具设计

更新日期：2026-10-22。状态：38 个核心工具已实现；18 个扩展工具待实现。部署配置见第 10 节。

本文定义工具的能力、参数、返回结果、业务数据依赖和调用流程。核心工具共 **38 个**：29 个业务读取／判断／计算工具、5 个业务准备工具、1 个直接业务写入工具、3 个事项流程工具。另规划 **18 个后续扩展工具**，在配套数据模型和接口完成后实现。一个工具可以服务多个意图，复杂意图通过多个工具组合处理。

## 1. 设计依据与业务边界

### 1.1 依据

- [业务数据库设计](DATABASE_DESIGN.md)。
- [业务表 DDL](../migrations/mysql/001_business_schema.sql)、[数据库结构脚本](../scripts/migrate_mysql_business_schema.py)。
- 基础表定义：[账号](../app/data/auth_store.py)、[商品与商家](../app/data/product_dao.py)、[订单](../app/data/order_dao.py)。
- 运行框架：[事项模型](../app/tasks/models.py)、[操作确认](../app/tasks/operations.py)、[人工处理](../app/support/store.py)、[政策适用范围](../app/rag/policy.py)。

MySQL 包含 **38 张账号与业务表**（基础 31 张、核心工具配套 7 张），另有 `schema_migrations`。字段以 DDL 为依据；角色授权必须使用服务端已接通的可信权限来源。

这些事实决定工具边界：

1. 商品、SKU、订单商品行是三个对象；商品现价不能覆盖购买时快照。
2. 订单键为 `(platform_code, order_id)`；一个订单可以有多笔支付、多个包裹、多次售后和多笔退款。
3. 优惠券模板、用户持有的一张券、核销记录是三个对象。
4. 售后申请、退款处理、支付渠道退款成功是不同事实，不能互相代替。
5. `invoice_requests` 保存申请，不包含完整正式发票号码、文件和重开关系。
6. MySQL 保存业务事实；PostgreSQL 保存消息、事项、确认、人工交接等运行记录；政策文本仍使用现有 RAG 服务。
7. 有表不代表已有可信数据、完整业务规则或第三方接口。数据缺失时返回未知；每项结论都须有对应的数据和规则依据。

### 1.2 适用对象

本方案面向登录用户的电商客服，覆盖售前咨询、交易查询、售后办理与人工协作。商家后台上架、批量发券、人工审批退款、直接改价、库存盘点、角色授权不向顾客侧 Agent 开放。

### 1.3 实现依赖分类

| 标记 | 含义 | 注册条件 |
| --- | --- | --- |
| A | 已有主要数据字段，可以基于新表开发读取能力 | 数据接入、归属校验、状态映射和服务实现完成后注册；核心工具现已实现 |
| B | 已有部分模型，还需要明确规则、补充约束／审计或接入写入流程 | 核心入口已实现，运行时缺少规则或数据则返回未知／拒绝准备 |
| F | 复用现有事项框架，需要重新编写模型调用适配层 | 有可信事项与会话上下文时注册 |
| E | 缺少关键表或外部业务接口 | 配套数据模型和业务接口完成后实现并注册 |

### 1.4 按实际行为分类

业务域用于查找工具，以下分类用于确定调用后会发生什么；不能把所有 W 类都理解成已经办理成功。

| 行为类别 | 数量 | 工具 | 完成一次调用意味着什么 |
| --- | --- | --- | --- |
| 事实／政策查询 | 24 | U01–U03、G01–G06、O01–O06、C01、C03、C04、S01–S03、I01–I02、K01 | 返回已有记录或政策依据；没有业务变更 |
| 资格判断 | 4 | O07、C02、C05、S04 | 返回规则判断；S04 可附可退金额估算，不创建申请 |
| 购买试算 | 1 | C06 | 返回指定方案的估算，不创建订单、锁库存或锁券 |
| 业务准备 | 5 | W02–W06 | 创建待确认方案，尚未提交业务申请或变更订单 |
| 直接业务写入 | 1 | W01 | 在用户明确领取请求下实际生成持券实例 |
| 事项协作 | 3 | F01–F03 | F01 读取上下文，F02 发布待答问题，F03 创建／复用人工交接 |

核心工具中 23 个为 A 类、12 个为 B 类、3 个为 F 类；实现依赖与行为分类分别标记。

## 2. 工具与参数的共同约定

### 2.1 参数只包含用户需要表达的业务信息

多数工具只有 0–2 个必填参数。确实需要区分办理类型、商品数量、发票抬头的工具保留必要字段，不把信息塞进无类型 JSON 或一句自然语言来制造“只有一个参数”的假象。

以下信息由服务端注入，不作为模型参数：`user_id`、角色、当前事项／会话编号、事项版本、访问范围、可信渠道、当前时间、幂等编号、确认凭证、数据库连接、SQL、计算出的退款金额和优惠金额。

工具目录不按表拆成 CRUD，也不按每个意图各造一个工具。例如，库存咨询、规格咨询和价格咨询可以复用 SKU 查询；漏发判断需要组合订单行与包裹明细。

### 2.2 对象引用

| 参数类型 | 定义与使用规则 |
| --- | --- |
| `order_ref` | 服务端生成、完整对应平台和订单号的字符串引用。用户只有订单号时，先在本人订单中定位；多平台同号必须返回候选。引用不是权限凭证，每次访问仍校验归属。 |
| `product_id` / `sku_id` | 分别指商品与确定规格；服务端校验 SKU 的商品、商家与访问范围；历史订单关联 SKU 可按授权读取并标明下架，不能因不可售就阻断历史查询。购买试算另检查可售状态。商品目录尚无平台挂牌关系，不能从 SKU 擅自推导销售平台。 |
| `order_item_id` | 一笔订单中的购买明细行，用于部分数量售后。不能用当前 SKU 替代历史订单行。 |
| `shipment_id` | 系统内部包裹编号；运单号不一定全局唯一。仅凭运单号不得查询他人包裹。 |
| `coupon_ref` | 服务端返回的带类型引用，只对应券模板或本人券实例之一；工具解析后检查类型。不能把模板编号当作已领券。 |
| `subject_ref` | 服务端返回的商品、SKU、商家或订单引用，用于限定活动或政策范围；各工具说明接受的对象种类。 |
| `after_sale_id` / `invoice_id` | 分别为售后申请编号与发票申请编号，均从属于已验证订单。正式发票未来另用 `issued_invoice_id`。 |
| `address_id` | 本人的未删除地址编号，以十进制字符串传输，避免 BIGINT 精度丢失。 |

对象已在当前事项中被明确核实，可直接复用引用；不能隐式使用整个会话中“最后查过的订单”。多候选时先澄清，不默认选最新一笔。

### 2.3 通用参数与类型

- `cursor?: string`：上一页原样返回的 `next_cursor`，省略查第一页。游标绑定用户／公共范围、工具、筛选条件、排序和有效期；续页不能改筛选条件。默认每页 20 条，由服务端控制，不暴露 `page_size`、SQL 排序或返回字段选择。
- `status?: string`：受限枚举，省略为 `all`。订单、券、售后各自定义状态集合，不共用万能状态。数据库自由文本须先映射，无法映射则返回 `unknown` 和来源状态。
- `days?: integer`：最近多少天，默认 30，范围 1–365；服务端决定结束时间。
- `query: string`：检索用自然语言，1–200 字；只用于受限文本检索。预算、时间、规格等无法准确落实时说明未应用的条件，不能声称已满足全部约束。
- `reason: string`：用户表达的办理原因，1–255 字；可精简原话，但不能编造事实。
- 所有对象严格校验字段，拒绝未声明参数。数组有大小上限，禁止传入任意对象、可执行表达式或外部 URL。

订单查询状态建议为 `all/pending_payment/paid/fulfilling/shipped/completed/cancelled/closed/unknown`；售后查询状态建议为 `all/pending_review/approved/rejected/processing/completed/cancelled/closed/unknown`。这些是待实施的对外查询枚举，不代表库中现有值；接入时须建立明确映射，不能仅凭相似文字认定状态。订单与包裹、支付状态分别保存和解释。

复合参数定义如下，**嵌套字段也计入调用复杂度**：

| 类型 | 字段 | 约束 |
| --- | --- | --- |
| `Money` | `amount: string` 必填，非负十进制金额；`currency: string` 必填，三位币种 | 不跨币种自动换算；当前金额字段按两位小数处理 |
| `DateRange` | `from: string`、`to: string` 必填，均为带时区的 ISO 8601 时间 | 左闭右开，`from < to`；最大跨度 366 天；相对日期按用户／渠道配置时区解析并回显，不能凭模型猜时区 |
| `PurchaseItem` | `sku_id: string` 必填，待购买的确定规格；`quantity: integer` 必填，购买数量 | 1–20 行；每行数量 1–999；首版同商家、同币种、同可信销售范围；重复 SKU 合并后再校验总量 |
| `AfterSaleItem` | `order_item_id: string` 必填，购买明细行；`quantity: integer` 必填，申请数量 | 1–20 行；同一订单；拒绝重复订单行；不超过购买数量扣除有效售后占用后的余量 |
| `sku_ids` | 2–5 个确定 SKU 编号 | 去重；比较价格时区分币种、规格和报价口径 |
| `coupon_refs` | 0–5 个本人券实例引用 | 省略或空数组都表示不使用券；一次调用表示一组确切的用券组合，不能将数组有时解释为全部使用、有时解释为择优候选；比较不同组合时分别调用；不允许模板冒充持券，不隐式领取 |
| `choices` | 2–5 个简短字符串选项 | 与实际候选绑定；仍允许用户自由回答；选项不承载隐藏指令 |

## 3. 核心工具：38 个

以下是待实现接口。每个参数均列出类型、是否必填和用途；`?` 表示可选。

### 3.1 用户与地址：3 个

| 编号／工具 | 工具描述 | 参数 | 返回内容与对应库表 | 标记 |
| --- | --- | --- | --- | --- |
| U01 `get_my_profile` | 查询本人展示资料和联系方式验证状态 | 无 | 用户名、展示名、头像；联系方式仅返回脱敏摘要与已验证标记。`users`、`user_profiles`、`user_contacts`。不返回密码哈希、登录令牌、完整联系方式或内部角色。 | A |
| U02 `list_addresses` | 列出本人可用于收货的地址 | `cursor?: string`，同条件下一页 | 地址编号、地区、脱敏收件人／手机号／详细地址、默认标记。`user_addresses`；过滤 `deleted_at`。完整地址由可信页面按需展示，模型默认只看摘要。 | A |

| --- | --- | --- | --- | --- |

### 3.3 订单、支付与物流：7 个

| 编号／工具 | 工具描述 | 参数 | 返回内容与对应库表 | 标记 |

#### 变更工具的共同流程

```text
用户明确诉求 → 查询业务对象 → 校验必需信息和规则
    → prepare_* 固定对象、数量、金额口径、规则版本和影响
    → 前端展示确认卡片，用户显式确认
    → 服务端复核身份、状态、版本和确认绑定
    → 事务／外部接口提交 → 记录真实回执 → 查询与通知结果
```

1. `prepare_*` 只能生成准备结果，不能执行真实交易。模型不调用“确认工具”，不能通过 `confirmed=true` 或聊天中的“好的”绕过前端确认。
2. W01 是实际写入，不标为只读。用户明确要求领指定券后可执行；只是咨询“有什么券”不能触发领取。服务端生成请求身份，重复传输不多发券，另一次明确领取意图可以按限领规则领取另一张。
3. 写入金额以订单快照、有效优惠分摊和已占用／已完成退款为依据。不让模型提供可退款上限、运费补偿或赠送金额。
4. 确认时对象版本、数量、价格／金额、政策版本或履约状态变化，旧准备结果失效，返回重新准备；不能悄悄扩大为整单处理。
5. MySQL 业务写入和幂等回执需同事务；PostgreSQL 的确认记录与 MySQL 不假定跨库原子提交。超时先按同一操作编号核实，禁止换编号重试扣款／退款。
6. 确认结果须绑定操作类型、业务对象和事项版本，提交时重新核验事项与业务状态。

## 4. 意图目录与工具组合

| E12 `get_membership` | 无 | 会员等级、积分余额、权益 | 用户会员账户、等级规则、权益授予与有效期；`user_roles` 是权限表，不能用来代表会员等级 |
| E13 `list_points` | `cursor?: string`，本人积分流水下一页 | 积分明细、积分变动／过期原因 | 积分流水、过期批次、来源业务与撤销关联；没有记录时不能只从余额反推流水 |
| E14 `quote_checkout` | `items: array<PurchaseItem>` 必填；`address_id: string` 必填；`coupon_refs?: array<string>`，指定本人券 | 含运费完整到手价、结算报价 | E01、可执行优惠规则、报价快照／有效期、库存与券竞争处理；与 C06 的商品估算区分 |
| E15 `prepare_purchase` | `quote_ref: string` 必填，E14 返回的有效报价引用 | 创建订单、按确认报价购买 | 完整订单创建、库存预留、优惠占用、支付发起与回调、过期释放；创建订单与实际付款分别确认／办理 |
| E16 `get_return_status` | `after_sale_id: string` 必填；`cursor?: string`，逆向包裹／事件下一页 | 退货寄回、仓库签收、验货进度 | 逆向包裹、承运轨迹、收货与验货记录；按包裹区分物流签收与验货通过，不能从物流签收推断退款获批 |
| E17 `get_repair_status` | `after_sale_id: string` 必填；`cursor?: string`，维修事件下一页 | 维修受理、检测、报价、维修与寄回进度 | 售后申请与维修工单关联、检测事件、费用授权及寄回包裹；没有记录时不推断已修好 |
| E18 `get_exchange_status` | `after_sale_id: string` 必填；`cursor?: string`，换货明细／事件下一页 | 换货受理、退件、替换商品与重新发货进度 | 换货商品行、库存占用、逆向退件及替换发货关联；新包裹须绑定本人原售后，不能按任意运单跨订单访问 |

扩展行为也须明确：E01/E02/E03/E06/E11/E12/E13/E16/E17/E18 是 10 个读取／评估工具；E04/E05/E07/E08/E10/E15 是 6 个准备工具，复用受控确认流程。E09 是实际催发货写入，须有明确催单请求和去重回执，查询发货状态不能触发它。E14 会保存报价快照并返回 `quote_ref`，属于报价准备，不能声明为纯只读；该步骤不预留库存或券，报价有效期内也须在确认下单时重新校验。

扩展上线时，S01/S02 应能定位对应售后类型和子流程引用；E08 不能只返回无法再次查找的维修工单编号。E03 默认评估所选订单行全部剩余可价保金额，E04 准备同一范围，部分数量价保另行扩展；E05 的数量不超过剩余可换数量。E14/E15 属于新增导购与下单范围，排在客服核心能力之后。

快递拦截、改约配送时间、现金赔偿、会员权益补发等目前统一转交真实人工渠道。待对应接口和数据模型明确，再决定是否增设专用工具；不将它们塞进一个任意 `action` 的通用写接口。

| 缺项 | 建议补充内容 | 影响能力 |

## 8. 返回契约、权限与注册

### 8.1 统一返回

```json
{
  "ok": true,
  "data": {},
  "observed_at": "2026-10-22T04:00:00Z",
  "data_as_of": null,
  "sources": [],
  "completeness": "partial",
  "limitations": [],
  "next_cursor": null
}
```

- `observed_at` 是本次查询时间；`data_as_of` 是可验证的数据源更新时间，没有依据时为 `null`。不同记录时间不同则在记录级分别返回，不能用一个最新时间掩盖旧数据。
- 金额用十进制字符串并带币种；未知为 `null`，不能填 0。数量与金额来源明确，派生值说明依据与口径。
- `completeness` 为 `complete/partial/unknown`；部分数据不等于全部结论成立。
- `sources` 包含允许展示的记录／规则引用和版本，不包含密钥、SQL、未脱敏身份或内部凭证。
- 只返回本次需要的摘要，明细分页；汇总金额和数量基于整个授权查询集合计算，标明范围，不能用当前页求和冒充全量。历史最低价也不能仅取当前页后称为区间最低。
- 嵌套集合采用固定条数上限并返回总数与截断标记；包裹的商品关联随 O05 游标继续展开，游标绑定包裹与明细位置，发出数量核对始终按全订单计算，待履约余量另须具备取消／售后依据。U01/U03 只返回限定摘要，超过上限须说明并引导页面；不静默遗漏。工具文本中的指令不增加任何权限。

失败返回 `ok=false` 和 `error.code/message`，按需提供缺项或脱敏候选：`invalid_arguments`、`not_found`、`ambiguous_target`、`invalid_cursor`、`insufficient_data`、`not_eligible`、`state_changed`、`temporarily_unavailable`、`unsupported_capability`、`result_unknown`。他人的私人对象统一按 `not_found` 处理。

### 8.2 模型工具与内部执行接口分开

模型只调用表中已注册的读取、判断、试算、准备、领券和流程工具。确认、业务提交、支付／退款回调、库存预留、券核销、轮询恢复等为服务端接口，不因为存在对应表就开放给模型直接写。

对于 MCP，读取工具和纯试算声明只读；`claim_coupon`、`prepare_*`、`ask_user`、`handoff_to_human` 会产生业务或事项记录，不能声明只读。幂等声明按实际调用语义设置：一次请求的重试防重，不等于同一参数在未来永远不能再办理。元数据不能代替服务端授权和事务校验。

### 8.3 按事项提供工具子集

38 个工具是服务能力目录，不能每次全部塞给模型。示例：

| 事项 | 常用工具子集 |
| --- | --- |
| 售前推荐 | G01–G05、C01–C04、C06、K01、F02；按需 G06、F03 |
| 查订单／物流 | O01–O06、K01、F01–F03 |
| 优惠券问题 | C02–C05、O01/O02、W01、K01、F02、F03 |
| 退款／退货 | O01–O03、S01–S04、W02、W06、K01、F01–F03 |
| 发票申请 | O01、O02、O07、I01、I02、W03、K01、F02、F03 |
| 改地址／取消订单 | O01、O02、O04、O05、O07、U02、W04、W05、F02、F03 |

子集由可信任务范围和实际能力开关交集确定。意图分类只能帮助选择，不能绕过用户身份、对象归属、参数校验和确认机制。身份从会话和 MCP 可信上下文取得，不让模型自行指定平台账号；当公共商品缺少销售平台时先澄清，由服务端验证后绑定范围。

## 9. 实施顺序与验收场景

### 9.1 分批实施

1. **先定义数据契约**：统一状态、金额、对象引用、来源时间、加解密、未知值、分页与权限；按新结构准备测试数据。
2. **第一批：A 类读取 + F 类流程**。先覆盖用户资料、商品、订单、支付、包裹、持券、售后、退款和发票申请查询。F03 必须产生真实交接记录。
3. **第二批：规则与试算**。完成 K01、O07、S04、C02、C05、C06 的规则契约；保留 `unknown` 路径。活动缺作用域时仅展示规则。
4. **第三批：逐个接通业务变更**。先 W01，再 W02/W03；W04/W05/W06 按历史、占用和外部流程证据补齐情况启用，不能因为都是 B 类就一次性开放。
5. **扩展批次**：根据真实客服量优先补 E01、E06/E07/E16、E05/E18，再考虑价保、正式开票、会员或下单。扩展工具实施前须完成对应库表和事务设计。

### 9.2 代表性调用链

| 用户需求 | 计划调用链与结果边界 |
| --- | --- |
| “两款耳机哪个好？我只要黑色。” | G01 → G02 → G03/G04；用实际规格筛选和解释，不编造口碑评分 |
| “这个颜色没货，什么时候有？” | G03；没有 E02 的补货数据时明确未知，不能由库存猜日期 |
| “买两件用哪张券合算？” | 明确 SKU/数量 → C03/C04 → C06；展示指定候选范围内估算，运费未知则不报完整实付 |
| “这张券为什么没退回来？” | C04 核销／释放记录 → O02 → S02/S03；缺释放规则或处理记录则转人工，不擅自补发 |
| “我买了三件怎么只收到一个包裹？” | O02/O03 → O05 → 相关包裹 O06；区分拆包、未发货与缺件反馈 |
| “我付了钱订单还没变化。” | O02 → O04；区分支付尝试与成功回执，存在冲突就核实，不再触发支付 |
| “只退其中一件，不要把整单退了。” | O03 明确行与数量 → S04/K01 → W02 → 确认 → S02/S03；不扩大范围 |
| “帮我改尺码。” | 澄清未发货订单规格修改还是售后换货；后者走 E05 前提；当前不可执行时交人工，不用改地址或退款替代 |
| “还没发货，取消吧。” | O02/O04/O05 → O07 → W05；缺库存占用归属或支付关闭证据则不提交 |
| “寄到我家里，不是公司。” | U02 → F02 确定地址 → O07/W04 → 确认；保留原地址历史，地址变化不影响其他订单 |
| “给公司开发票，后来能下载吗？” | O07 → W03 → I02；核心工具方案只规划申请／查询，正式下载依赖 E11 |
| “上一单的投诉谁在处理？” | F01 查询本事项已有交接；未找到则明确未查到并澄清；只在用户请求转交或符合既定升级规则时调用 F03，不能因单纯查询就新增投诉或虚构客服姓名 |

### 9.3 必须验收的边界

- 不同用户、同平台账号绑定、跨平台同号、多个同时进行的订单不会串对象。
- 空库、缺 SKU／库存／价格、未知状态、过期规则均返回缺项，不返回假数据。
- 多包裹拆分、部分发货、部分售后、多笔支付与退款累计分别正确。
- 券模板与实例不混用；并发领券不超发；同一请求重试不重复发券；已释放与未释放可区分。
- 价格试算只算证据充分的部分；规则冲突、渠道未知、运费缺失不输出确定实付。
- 准备后状态变化使原确认失效；暂停事项／转人工后不能继续提交。
- 外部提交超时保留未知状态，核实原操作，避免重复支付／退款／开票。
- 密码、验证码、完整联系方式、地址和税号不会不必要地进入模型、日志与事件。
- 自然语言“确认”“取消”“谢谢”不会误触发付款、整单取消、撤销售后或判定业务完成。
- “只问能退多少”不生成申请或待确认卡片；依赖原因、质检的资格不会被默认为通过。
- 查询区间内的历史价包含区间前生效的有效记录；商品预算命中具体 SKU，订单日期筛选回显时间边界。
- 券已用后到期不会被标为过期未用；指定不兼容券组合不被悄悄替换；模板变更不覆盖历史领券承诺。
- 仅建运单不计为已发货；取消商品或部分售后不被误报为等待发货；重发／换货出库数量需对应独立履约关系。
- 申请退货、维修、换货后能凭本人售后引用查询后续进度；核实进度不会重复创建申请。

### 10.2 配置与迁移

安装 `requirements.txt`，在 `.env` 配置 `ORDER_DB_DSN`、`API_JWT_SECRET` 和现有事项运行连接，然后执行：

```powershell
python -m scripts.migrate_mysql_business_schema
python -m scripts.migrate_mysql_business_schema --check
```

脚本按 `schema_migrations` 顺序执行 001、002、003。已有前两个版本的数据库只增加 003 中的 7 张配套表；新建空库依次执行三版。迁移不自动生成真实业务数据、用户领券记录或默认资格政策。

准备操作使用 AES-256-GCM 保存敏感参数，需配置：

```dotenv
BUSINESS_DATA_KEYS={"1":"<32字节随机密钥的URL-safe Base64编码>"}
BUSINESS_DATA_KEY_VERSION=1
```

密钥通过系统安全随机数产生，保存在本地环境配置或密钥管理服务，不提交到 Git。API 和 task worker 必须使用相同密钥，轮换后保留旧版本以读取历史记录。未配置密钥时读取工具可用，准备操作会明确返回配置不可用。

地址密文格式为 `12 字节 nonce + AESGCM 密文及 tag`，AAD 为 `address:{user_id}:{field}`，field 分别为 `recipient_name`、`phone`、`detail`。地址写入方必须遵守相同约定；改址准备会核实目标地址可以解密。发票抬头和税号分别使用 `invoice-title:{user_id}`、`invoice-tax:{user_id}`。完整目标地址及发票信息只在登录用户的确认卡片中显示，工具结果和事项回执保存脱敏摘要。

### 10.3 可执行业务规则

`business_policy_versions.rules` 使用严格的 JSON 契约。`schema_version=1`；未知字段、未知版本、缺失规则、多个同时有效版本均不能自动放行。

| 字段 | 类型／含义 |
| --- | --- |
| `schema_version` | 固定整数 1 |
| `time_basis` | `request`、`order_created` 或 `delivered`；决定有效版本选择时间，默认 request |
| `allowed_statuses` | 该操作允许的订单状态数组，默认空数组 |
| `window_days` | 售后签收后期限；为空不应用该期限。要求完整签收依据 |
| `requires_reason_review` | 为 true 时需人工审核原因，自动资格返回 unknown |
| `refund_shipping` | 为 true 时当前实现返回 unknown；运费分摊依据尚未接入 |
| `local_authority` | 本地具有取消／改址／撤回控制权；默认 false |
| `inventory_managed`、`coupons_managed` | 取消订单时库存预留和券占用须纳入同一事务；默认 false |
| `threshold_basis` | 当前只支持 `goods_after_promotions` |
| `coupon_stacking`、`promotions_with_coupons` | 多券叠加、活动与券叠加许可；默认 false |
| `rag_policy_id`、`rag_policy_version` | 对应政策检索结果的 source_id 和 version；不一致会显示冲突，回复发布时拒绝引用 |

可执行 action：`refund_only`、`return_refund`、`invoice`、`cancel_order`、`change_address`、`after_sale_cancel`、`pricing`。这些字段由业务管理方维护，模型不能修改。带 channel 的规则要求可信渠道上下文；目前不能自动采用该规则。

优惠 kind 目前支持 `amount_off` 和 `percent_off`。`discount_bps` 表示减免比例的基点，例如 1000 表示减免 10%，不是支付 10%。适用范围类型为 `all`（scope_id 为 `*`）、`merchant`、`product`、`sku`。活动按 priority 降序执行，同组互斥；券按指定组合顺序执行并逐行分摊至分，不擅自替换组合。SKU 列价、优惠、订单必须使用相同币种。

领取成功时将券模板和范围保存到 `coupon_claim_rules`，后续按此快照解释持券承诺。领取事务锁定券模板并重查总量／个人限领；同一事项来源请求使用同一服务端生成的请求标识。

### 10.4 当前执行边界

- 仅从 MySQL 读取业务事实，不使用旧工具或假数据回退。分页固定 20 条；签名游标绑定用户、筛选和数据快照，有效期 15 分钟。结果变动要求从第一页重新查；单次查询超过 10000 条返回范围过大。
- 订单、售后、发票必须属于当前用户；订单引用包含平台与订单号。公共商品未明确平台时，价格／领券判断需要先澄清，事项中的平台须能通过本人订单或有效账号绑定核实。
- `prepare_after_sale` 提交待审核申请与商品行；不调用支付退款接口。`prepare_invoice` 提交加密的待处理申请；不生成正式发票。
- 改址仅适用于本地控制且尚未进入发货流程的订单。取消仅适用于未支付、无进行中支付、无发货、库存预留完整且可释放券占用的订单。售后撤回仅适用于有本地提交依据、尚未受理且无有效退款的申请。
- 确认有效期 10 分钟；确认绑定事项、用户、操作参数、订单平台及业务快照，提交时再次核验规则和数据。MySQL 的业务变更、事件与回执在同一事务提交；超时通过原 operation_id 查询，不盲目重复写入。
- `ask_user` 保存具体问题并停止本轮；`handoff_to_human` 创建或复用真实工单；`read_task_context` 只读取当前授权事项及其工单记录。
- 政策文本来自现有经审核的 RAG 索引；未配置索引或检索失败时返回依据不足。18 个扩展工具、外部退款／正式开票、逆向物流、自动外部进度跟进不在此次实现范围。
