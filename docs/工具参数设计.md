# 工具参数设计

## 设计目标

参数应能表达用户的自然线索，并明确区分查询条件、对象引用和办理意图。参数模型位于 `app/tools/contracts.py`，工具登记位于 `app/tools/catalog.py`；本地执行与 MCP 使用同一份定义。

本次逐项检查当前注册的 55 个工具，重点修正搜索线索混杂、引用类型说明不清、无效参数组合进入业务层后才报错的问题。已经明确的接口保留，不要求每个工具都增加参数。

## 统一约定

- `*_id` 通常是查询返回的原始编号，`*_ref` 是服务端返回的对象引用。原样复制，不能互换，也不要求用户记忆内部编号。身份、权限、计算金额和确认凭证由服务端提供。
- `cursor` 只能使用同一工具、同一条件的 `next_cursor`。更换条件重新查第一页，不同工具不能混用游标。
- `specs` 使用已知的结构化规格名和值，同一名称不重复。当前业务库的鞋码字段名为“尺寸”，不能写成“尺码”；常用字段还包括颜色、容量、版本和规格。历史订单规格缺失时不能算严格命中；商品目录查询保留原有 `unapplied_conditions`，未知属性不等于满足条件。
- 金额使用十进制字符串和明确币种，不自动换汇。时间必须带时区，包含开始、不包含结束，跨度不超过 366 天。
- 待购商品中同一 SKU 只出现一次，售后明细中同一购买行只出现一次。数量来自用户意图，不由模型扩大。
- Schema 校验类型、范围和参数组合；对象存在、归属、资格、库存和最终金额仍由业务服务核验。

## 订单搜索

`find_orders` 顶层条件用于严格筛选，全部成立才返回。`hints` 接收用户明确不确定、可能记错的线索，仅用于排序，不排除未匹配订单。

| 参数 | 含义 |
| --- | --- |
| `order_id` | 已知的确切原始订单号 |
| `query` | 空格分隔的商品名称、品牌或型号关键词，逐词匹配；保留旧调用的编号片段匹配 |
| `specs` | 同一购买行的确切规格，尺码 `38` 不匹配 `38.5` |
| `item_quantity` | 同一购买行的原购买数量，不是整单总件数、发货数量或售后数量 |
| `paid_amount_range` | 整笔订单已支付金额的上下界及币种，不是单价或商品行金额；至少指定一个边界 |
| `created_range` | 下单时间，不是付款、发货或收货时间 |
| `status` | 订单状态；用户说“没收到”不能直接转成排除已签收订单的条件 |
| `hints` | 可包含 `query/specs/item_quantity/paid_amount_range/created_range`，仅影响排序 |

例如用户说：“查一下我的红色鞋，好像是上周买的。”已知规格名为“颜色”、本次评测时间为 2026-11-02 时，可调用：

```json
{
  "query": "鞋",
  "specs": [{"name": "颜色", "value": "红色"}],
  "hints": {
    "created_range": {
      "from": "2026-10-26T00:00:00+08:00",
      "to": "2026-11-02T00:00:00+08:00"
    }
  }
}
```

更早购买的红鞋仍会返回。日期根据本次业务或评测时间解释，不能照抄示例。同一线索不要同时放在顶层和 `hints`；金额或数量口径不明时省略，不擅自换算。

`app/services/commerce/order_search.py` 构造参数化 SQL，集合服务执行查询。商品线索必须落在同一购买行；商品提示也必须与严格商品线索落在同一行，不能用红衬衫的颜色匹配另一双鞋。SQL 在分页前对全部候选排序，再按分数、下单时间和稳定编号分页。

`hint_matches` 分为 `item`（关键词、规格、数量整体）、`created_range`、`paid_amount_range` 三组。`unmatched_hints` 列出未匹配组，`hint_score` 是命中组数，不是置信度。缺失数据按未匹配处理，不代表用户一定记错。购买摘要的 `query_match` 标记严格商品条件命中，`hint_match` 标记商品提示命中，相关购买行优先展示。

排序第一、甚至唯一命中，都不代表取得业务授权。候选与用户陈述冲突或仍有歧义时，执行模型交接 `needs_input`，由回复组织模型提出简短澄清。

## 全部工具检查结果

### 用户资料与流程

| 工具 | 参数检查与处理 |
| --- | --- |
| `recall_user_memory` | 保留历史偏好/用途问题，不查询实时状态或授权 |
| `inspect_image` | 明确附件来源、具体观察问题及 `brief/full` 粒度 |
| `get_my_account` | 新增游标必须同时指定 `collection` 的校验 |
| `list_addresses` | 明确单个标签或省市区片段，不查询电话、详细街道 |
| `get_membership` | 保留无参数，身份及平台范围来自可信上下文 |
| `list_points` | 保留分页，身份和余额由服务端处理 |
| `read_task_context` | 保留无参数，只读取当前事项 |
| `handoff_to_human` | 原因改为待处理问题和阻碍，不再误限定为用户提出的办理原因 |

### 商品与购买

| 工具 | 参数检查与处理 |

| `prepare_purchase` | 明确只使用完整结算工具返回的有效报价引用 |

## 验证与边界

`tests/test_tool_arguments.py` 验证参数组合、重复行、严格类型及公共 Schema。`tests/test_order_search_parameters.py` 验证实际 MySQL 的规格、同一购买行约束、数量/金额、身份范围、不确定提示排序、跨页完整性、时间边界与售后查询。后者需显式配置 `CORE_TOOLS_TEST_MYSQL_ADMIN`，创建唯一命名的独立测试库，结束后删除，不写入应用业务库。

没有增加模型调用或事实复核环节。品牌中英文别名、语义检索及搜索索引仍未实现；提示排序是确定性的匹配组计数。超时、模型调用次数和多轮模拟效果仍需通过完整模拟验证，不能由参数测试推断性能结论。
