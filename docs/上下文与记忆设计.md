# 上下文与记忆设计

## 上下文分层

| 信息         | 用途                             | 有效性边界                               |
| ------------ | -------------------------------- | ---------------------------------------- |
| 原始公开消息 | 确定用户本次请求与原话证据       | 校验所有者、事项关联和来源是否失效       |
| 事项记录     | 保存目标、细节、等待与进度       | 使用最新事项及控制版本                   |
| 历史摘要     | 定位更早原话                     | 回查原文，不独立提供授权                 |
| 长期偏好     | 跨会话保留用户明确表达的稳定信息 | 区分范围、时间、否定、更正和遗忘         |
| 业务回执     | 说明已发生操作或查询事实         | 检查对象、来源和时效，当前状态必要时重查 |

恢复事项不等于恢复订单事实。物流、金额、资格与退款状态仍由业务查询提供，长期偏好不能用来猜订单或省略确认。

**当前接入方式：** 模型可以按需调用 `recall_user_memory(query)`，经当前事项的 `TaskMemory.recall` 读取本人 v3 长期偏好。返回值进入工具上下文，并投影为有来源的回复结论；没有每轮自动预注入。已完成的接入记录见 [待改进](待改进.md) 的 `INT-01`。保存成功、实际召回与业务效果仍分别判断。

短期原话选择、引用式摘要及其当前接入方式见 [短期上下文与摘要设计](短期上下文与摘要设计.md)。

## 完整请求预算

`request_budget.py` 对提示词、工具定义、原话、候选、记忆和工具结果统一计算输入预算，并为输出预留空间。

当前事项执行场景超限时直接停止，不自动裁剪事项目标或工具证据。其他适用场景先移除完整可选历史，必要时投影工具结果；保留当前请求、否定、条件和更正，不能截断关键句改变语义。必要内容仍无法容纳时明确暂停或走兜底，不以局部片段继续办理。

来源被纠错、删除或权限变化后立即从读取层排除，后台再更新摘要和缓存。缓存失效不能恢复旧来源。

## v3 长期记忆模型

默认 `MEMORY_ENGINE=v3`，记忆和事项共用 SupportStore。模型输出变更计划，程序负责证据和事务校验。

变更动作包括 `ADD`、`UPDATE`、`MERGE`、`FORGET`、`NOOP`、`NEEDS_CLARIFICATION`。每个变更具有组编号、偏好属性、作用范围、正负倾向、值和逐字原话证据。用户与时间由服务端给出，模型不能自填身份或时间戳。

范围区分商品品类、使用场景和尺码体系。例如跑鞋尺码与日常鞋尺码分开，未知尺码体系保留 `unknown`，不能猜成欧码。更新顺序依据原始消息接收时间，明确偏好不固定按 90 天过期。

## 提取与提交

1. 记忆 Worker 按会话读取公开用户原话和待处理截止点。
2. 在事务外调用模型生成批量计划。
3. 核验逐字证据、消息所有者、属性、范围和目标记录。
4. 用户级版本锁检查提取快照是否仍有效。
5. 在同一事务中写入记录版本、遗忘命令、处理回执和消息检查点。
6. 在进入提交事务前尝试准备可选本地向量；失败不阻断持久化与词法检索，不存在独立的 v3 向量建库 Worker。

同一组变更共同接受或拒绝，独立组可以分别处理。模型或存储失败不推进消息检查点，受限重试后保存失败状态。

## 检索、更正与遗忘

按需调用链为：`recall_user_memory → 当前事项上下文 → TaskMemory.recall → v3 管理器`。查询结果进入 ReAct 工具消息；后端将其转换为带“历史陈述、本次要求优先”限定的允许结论，再由回复模型选择。当前偏好与历史时点查询使用不同标识，历史值不会被渲染为当前偏好。

[task_recall.py](../app/memory/task_recall.py) 保存并验证用户记忆版本、具体记录、时效和原话来源。有效性依赖持久化到执行与后续工具证据，并在追问和准备操作中保留；更正、遗忘或有效来源变化后，旧执行、确认和未发布回复停止。没有使用记忆的普通查询不受该读取依赖影响；新执行不复用旧记忆及依赖它的工具快照。

检索先读取当前用户有效记录和版本，再匹配当前问题。来源检查覆盖原话所有者、公开范围和纠错状态。向量相似度不能绕过这些限制。

`FORGET` 同时阻止当前及历史记忆召回，并阻止旧消息重放重新恢复该值。只有用户明确要求重新记住时才能恢复。遗忘是记忆访问规则，原始会话及审计数据遵循各自保留策略。

v3 通过当前记录、属性族和时间索引读取，避免为一次请求重扫所有历史。写入只重建受影响属性族，不让无关记忆被覆盖。

## 归档与历史迁移

`POST /api/v1/sessions/{session_id}/memory-archive` 固定当前消息截止点，返回归档编号；`GET /api/v1/memory-archives/{archive_id}` 查询处理位置与逐组结果。

`completed` 表示截止点已处理；`completed_with_issues` 表示存在歧义或拒绝；`pending`、`running`、`retrying` 仍在处理中，`failed` 需要核查。归档不关闭客服事项。

首次迁移只导入有可验证来源的结构化旧记录。已迁移用户继续使用 v3，防止回退到遗忘前的旧快照；迁移标记不能作为清空后重放的开关。
