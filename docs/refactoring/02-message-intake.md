# 02 持续接收消息并记录处理位置

Agent 工作时仍能接收后续消息，并能在重启后找到未处理的信息。本次不判断消息属于哪件事。

前置：完成 [01 保存事项与修改来源](01-task-storage.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/api/task_messages.py`、`app/tasks/intake.py`、`app/support/store.py`、`app/runtime/outbox.py`。

## 实施步骤

1. 复用现有消息记录和请求编号。接收事务先保存原话，再返回已接收；同一请求编号和相同内容返回原结果，内容不同则拒绝。
2. 为会话保存已接收与已完成归属判断的消息位置。复用现有事件序号时允许中间夹有其他事件，不能把序号不连续误判成丢消息。
3. 将接收、关联判断、事项执行、回复发布分开记录。暂不能关联的消息进入待澄清状态，也要能追溯；读取消息不代表理解完成。
4. 把唤醒关联处理的记录与消息一起写入现有 Outbox。重复唤醒可以合并，判断期间到来的消息在后续继续读取，不能因合并通知丢掉原文。
5. 为新链路建立独立接收入口或受控开关，避免旧 `conversation_route` 收到每条消息就使整次执行失效。默认流量仍使用旧路径。
6. 转人工和明确的结构化取消优先受理。自然语言中的模糊取消先留给归属判断；数据库不可用时不返回虚假的已接收。

## 验收

- 连续三条消息在处理前、处理中、完成后到达，均能按服务端顺序找到。
- 接收成功后进程退出，Outbox 能重新唤醒；重复投递不产生重复原话。
- 判断进程只推进自己完成的消息范围，不能跳过期间到来的新消息。
- 数据库故障不丢失已成功接收的记录；拒绝的新请求不会显示为已接收。

## 本次交付边界

交付读取待处理消息、保存处理位置和恢复唤醒的接口。此时使用固定处理器验证，不调用真实业务写工具。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现接口

- `MessageIntake.receive` 在同一事务保存用户原话、请求回执、接收位置和 Outbox 唤醒。相同请求重试返回原接收回执；不同请求即使文字相同也分别保存。
- `progress` 返回接收位置、归属判断完成位置，以及消息的 `pending`、`associated`、`clarification` 或 `control` 状态。这些状态不表示事项已执行或已经回复。
- `claim_next` 从现有 `runtime_jobs` 中领取 `association` 类型工作；`claim` 领取指定会话。领取时保存本次消息范围和有期限的占用凭证，模型调用在事务外完成。
- `complete` 只接受当前凭证对应的完整消息范围。支持与事项创建、修改共用数据库事务；过期凭证、错误范围或保存失败时整体回滚。后续消息会生成下一份待处理工作。
- 处理器崩溃后，新处理器可以领取到期工作并重新读取尚未理解的消息。旧处理器不能回写；现有业务执行 Worker 不读取、不恢复此类工作。
- `POST /api/v1/task-messages` 和 `GET /api/v1/task-messages/{session_id}` 是受控测试接口，要求认证。`TASK_INTAKE_ENABLED` 默认关闭；开启后也只负责接收和查询，不会自动启动 Agent。当前用固定处理器调用上述接口测试，第 04、06 部分再接入判断和执行。
- 新接收会话不能再走原 `/api/v1/chat` 链路。明确转人工立即交接；结构化取消要求事项编号、版本和用户权限，只修改所选事项。对象不明确的自然语言取消继续保留为待判断消息。
- 版本 11 迁移增加消息处理位置和请求索引，并为原 Outbox 增加工作类型。原始消息仍只有 `support_events` 中的一份。

验证入口为 `tests/test_message_intake.py` 和 `tests/test_message_intake_api.py`；前者同时支持 SQLite 和隔离 PostgreSQL。测试包括提交后进程直接退出、过期处理器回写、持续输入、跨会话请求冲突、迁移中断和数据库写入失败。
