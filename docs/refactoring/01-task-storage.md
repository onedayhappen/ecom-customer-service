# 01 保存事项与修改来源

让一件事有独立、可恢复的记录，换一个会话也能读取它。本次只完成保存与读取，不接入模型判断。

前置：从已提交的清理基线开始，遵守 [实施入口](README.md) 的共用规则。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/tasks/service.py`、`app/support/store.py`、`app/memory/case_manager.py`；必要时在 `app/tasks` 新增数据模型和存储模块。

## 实施步骤

1. 定义事项字段：`task_id`、`user_id`、`goal`、`details`、`waiting_for`、`status`，另存版本和时间。用户身份从认证上下文取得。业务状态以工具回执为准，事项状态表示沟通进度。
2. 使用版本化迁移改造事项表，按所属会话补齐旧记录的用户归属；无法确认归属的数据保留为历史，不开放给其他用户。取消会话内只能有一个活跃事项的数据库限制。改造依赖旧列数的 INSERT，使用明确列名，保持旧入口可运行。
3. 增加事项与会话、原始消息的关联；同一消息可关联多个事项。订单号不是事项唯一键，同一订单的开票与退款可以分别保存。
4. 提供创建、按用户查询、按编号读取、带预期版本更新的接口。稳定查询字段使用普通列，业务细节在 PostgreSQL 用 JSONB；本地 SQLite 测试通过存储适配保持相同语义。
5. 事项变更和事件在同一事务保存，记录修改前后值、来源消息或工具结果、变更编号和版本。失败时一起回滚，重复提交同一变更不重复修改。
6. 新链路以事项记录为进度的唯一写入位置。此时保留旧 Case 的证据、审计和操作记录，不迁移运行中的业务申请，也不启动旧草稿与新事项的双向同步。

## 验收

- 同一用户在两个会话中读取同一个事项；另一用户按编号读取也被拒绝。
- 同一会话保存多个事项，同一订单可以有不同目标；重复创建请求不多建一份。
- 两次更新竞争同一版本时只接受一次；事项与事件不会部分提交。
- 迁移可重复执行，旧数据可读取，旧默认入口的相关测试仍通过。至少用隔离 PostgreSQL 检查迁移和版本竞争。

## 本次交付边界

交付可独立调用的事项存储接口及迁移。02 只通过该接口关联消息，不另建一套事项数据。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。
