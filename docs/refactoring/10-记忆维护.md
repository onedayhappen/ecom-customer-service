# 10 维护跨会话记忆和上下文

在 03 已能定位历史事项的基础上，稳定提供有来源的历史信息，并使错误和过时记忆及时失效。

前置：完成 [09 确认具体内容后提交业务操作](09-确认与业务操作.md)。 共用约束见[实施入口](重构实施入口.md#共用实现规则)。

## 改动位置

`app/session/short_term.py`、`app/session/request_budget.py`、`app/memory`、`app/tools/memory_tool.py`、`app/runtime/maintenance.py`。

## 实施步骤

1. 明确最近原话、事项进度、历史摘要、长期偏好和业务证据的用途。恢复进度直接读事项，订单状态重新查询，长期偏好不用于猜具体订单或代替授权。
2. 将 03 的候选与原话接入完整模型请求预算。提示词、工具定义和工具结果都计入；资料太多时缩小范围或明确暂停，不静默截掉条件与否定。
3. 复用长期记忆提取与更新机制，仅从可追溯原话提取跨会话适用的信息。保存来源和版本；用户陈述与业务系统核实结果分开，不从待确认事项草稿推断长期事实。
4. 让摘要、记忆与缓存消费 05 的纠错和删除事件。读取立即排除失效来源，后台重新生成或更新索引；更新失败时继续使用可靠原话和事项记录。
5. 跨 session 恢复时核对原事项、已提交操作和最新业务状态。重新唤醒表示继续沟通，不复用过期确认或重放已提交请求。
6. 密码、令牌、长期免确认要求和无权查看的备注不进入模型记忆。保留必要审计时仍遵守删除与访问范围，不能从缓存恢复已被清理的内容。

## 验收

- 新会话继续原退款事项，能够看到真实进度且不重复提交。
- 摘要生成失败、缓存丢失后仍可恢复；当前明确更正覆盖过去陈述。
- 错误归属写入派生信息后，纠错立即阻止旧结论召回，异步重建完成后内容一致。
- 其他用户记忆、交易授权和私密信息不会通过检索或摘要进入当前请求。

## 本次交付边界

交付来源一致的上下文与记忆维护，不另建一套事项流程。语义检索不能替代用户归属与对象检查。

完成后在 [实施入口](重构实施入口.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 实现顺序与数据边界

1. 03、04 继续通过当前消息、历史原话和事项记录判断归属，不把长期偏好加入订单选择。候选请求仍计算提示词、原话和工具定义的总预算；含敏感信息的整段文本替换为明确提示，不保留可能改变含义的局部片段。
2. 归属确定后，执行器读取该用户、该事项的最近八条有效原话、事项当前版本，以及最近二十条操作状态。已有摘要只用于定位更早的原话，还须重新核对这些原话是否属于本事项；摘要损坏时使用近期原话和事项记录。历史操作仅返回编号、类型、状态和少量业务回执字段，不返回确认凭证、待提交参数或内部备注。要回答最新物流或退款状态，仍须调用业务查询工具。
3. 需要历史偏好时，单一 Agent 调用 `recall_user_memory`。它沿用原有检索和版本账本，不增加 Agent。每次检索先重新读取账本，再到会话数据库检查来源所有者、公开范围、原文及纠错记录。原有聊天 API 也接入同一来源检查，避免从旧入口召回失效内容。记忆存储失败时返回不可用提示，原话和事项记录照常提供；检索超时受统一执行预算限制，不长期占用执行资源。
4. 后台提取只接受有效的用户公开原话。提取结果保留原消息编号、来源内容摘要值、关联决定编号、记忆版本和证据；这些来源字段由服务端生成，模型不能自填。落盘前在记忆账本的用户锁内再次检查来源，避免先清理、后写回的竞争。
5. 模型调用前后检查已经提供的原话和记忆。期间发生删除、来源失效或版本替换，本次执行停止，不继续调用业务工具。新的执行重新读取最新内容。历史偏好不能改变当前事项的订单范围，也不能恢复操作授权。
6. 摘要保存的是原话索引。读取时重新检查原消息并返回完整原文，避免一句“如果不能换货才退款”只剩“退款”。完整原话放不下时，省略整条可选资料并给出范围不足提示；任务执行请求整体过大时明确暂停。新消息入口的长期提取不再把一条超长原话切成局部窗口；旧入口的兼容提取在 14 切换时清理。

## 纠错、删除与后台维护

`SourcePolicy` 是模型读取记忆的来源检查。05 写入纠错记录后立即生效，无需等待 Redis、摘要或记忆文件更新。错误关联涉及的原话仍可供用户核对，但其旧派生记忆不再召回；以后新的明确原话可以生成新记忆。

`forget_source(store, user, session_id, sequence)` 是服务端删除模型记忆来源的入口。它验证用户身份范围，在同一事务中记录来源失效、移除该会话摘要、安排重建并写入只含来源编号的私有审计事件。它表示禁止再把该来源用于模型记忆，不承诺删除交易或审计记录，不对模型开放调用。

已有的 `task_invalidation` 后台任务由 `process_memory_invalidations` 消费：读取版本账本，将失效来源对应的记忆标为撤回并清理缓存。任务有领取租约、失败重试和重复处理保护；进程退出后可以重新领取。删除期间仍在执行的提取不能把旧来源恢复为有效记忆。后台失败只影响清理速度，不影响读取时的排除。

运行原有维护入口即可处理纠错、记忆清理、摘要和长期提取：

```sh
python -m scripts.platform_maintenance --once
```

没有新增事项状态机或数据库表。复用原话、事项、操作回执、来源失效表、后台任务和记忆版本账本。

## 测试入口

`tests/test_task_memory.py` 覆盖跨会话退款续接、历史偏好与订单隔离、模型调用中删除、提取中纠错、清理后迟到写入、重复清理与租约恢复、完整原话预算、私密来源、敏感信息、缓存失效和记忆存储故障。设置 `ECOM_INTEGRATION=1` 后验证隔离 PostgreSQL；其中专门用真实 PostgreSQL 记忆账本和 Redis 验证清理后迟到的缓存写入不会恢复旧内容。

共享能力同时回归 `test_long_term_runtime.py`、`test_memory_atomic.py`、`test_short_term_memory.py`、`test_long_term_memory_api.py`，以及事项候选、纠错、执行、业务操作和回复协调测试。模型和业务工具使用受控替身；测试结果不代表线上模型准确率或真实退款已办理。
