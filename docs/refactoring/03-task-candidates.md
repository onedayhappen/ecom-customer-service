# 03 找出可能相关的事项

为归属判断准备少量可靠候选，包含最近对话、待答问题和其他会话的历史事项。本次只找候选，不替用户选定事项。

前置：完成 [02 持续接收消息并记录处理位置](02-message-intake.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/tasks`、`app/session/short_term.py`、`app/memory/case_manager.py`、`app/tools/user_orders.py`、`app/session/request_budget.py`。

## 实施步骤

1. 先读取当前消息、最近原话、尚未回答的问题及对应事项、当前会话未完成事项。问题保存稳定编号、所属事项、对应版本和是否仍有效。
2. 存在历史指代或当前候选不足时，在该用户可访问的历史事项中检索。先按明确订单、商品、时间和状态筛选，再使用已有检索能力补充；不以 session 变化为由新建事项。
3. 候选包含事项编号、目标、当前细节、待答问题、更新时间和原文引用。保留多个合理候选，不因某事项最近出现就直接选中。
4. 必要时调用只读订单工具核实商品和订单。历史已结束事项也可以成为线索，但被召回不等于恢复执行，更不等于恢复旧授权。
5. 控制候选数量和完整请求的 token 预算。优先去掉无关历史，保留当前请求、否定、条件和区分候选所需的信息；不能静默截掉关键内容。
6. 查询和缓存均以认证用户及业务访问范围隔离。记忆与检索结果只提供资料，不改变工具权限。

## 验收

- “昨天那单”能找到其他 session 的候选及来源；同一商品的两笔订单都保留。
- 同时存在两道待答问题时，返回各自的事项和版本，不合并成一个问题。
- 他人的相似订单、私有人工备注不进入候选；摘要不足时可回查原话。
- 候选过多时仍保留明确订单、否定与条件；检索失败会返回缺失状态，不编造事项。
