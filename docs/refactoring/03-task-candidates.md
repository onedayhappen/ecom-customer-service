# 03 找出可能相关的事项

为归属判断准备少量可靠候选，包含最近对话、待答问题和其他会话的历史事项。本次只找候选，不替用户选定事项。

前置：完成 [02 持续接收消息并记录处理位置](02-message-intake.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/tasks`、`app/session/short_term.py`、`app/memory/case_manager.py`、`app/tools/user_orders.py`、`app/session/request_budget.py`。

## 实施步骤

1. 先读取当前消息、最近原话、尚未回答的问题及对应事项、当前会话未完成事项。问题保存稳定编号、所属事项、对应版本和是否仍有效。
2. 存在历史指代或当前候选不足时，在该用户可访问的历史事项中检索。先按明确订单、商品、时间和状态筛选，再使用已有检索能力补充；不以 session 变化为由新建事项。
3. 候选包含事项编号、目标、当前细节、待答问题、更新时间和原文引用。保留多个合理候选，不因某事项最近出现就直接选中。
4. 必要时调用只读订单工具核实商品和订单。历史已结束事项也可以成为线索，但被召回不等于恢复执行，更不等于恢复旧授权。
5. 控制候选数量和完整请求的 token 预算。优先去掉无关历史，保留当前请求、否定、条件和区分候选所需的信息；不能静默截掉关键内容。
6. 查询和缓存均以认证用户及业务访问范围隔离。记忆与检索结果只提供资料，不改变工具权限。

## 验收

- “昨天那单”能找到其他 session 的候选及来源；同一商品的两笔订单都保留。
- 同时存在两道待答问题时，返回各自的事项和版本，不合并成一个问题。
- 他人的相似订单、私有人工备注不进入候选；摘要不足时可回查原话。
- 候选过多时仍保留明确订单、否定与条件；检索失败会返回缺失状态，不编造事项。

## 本次交付边界

交付结构化候选上下文，供 04 使用。跨会话定位能力在本步具备，长期偏好维护留到 10。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现接口

- `CandidateService(store, authenticated_user_id, scope=BusinessScope(...)).build(session_id, sequences)` 从已保存的原话建立候选上下文，不接受模型提供的用户身份，也不写事项进度。
- 先读取当前消息、最近公开对话和本会话未结束事项，再按明确订单或商品编号查历史，使用现有中文词语检索补充候选。“昨天”匹配事项更新时间，返回的依据会明确说明时间含义，不冒充订单下单日期。
- `candidates` 保留事项编号、版本、目标、细节、待答内容、状态、原话引用和召回依据。多个合理候选分别返回，没有“选中事项”字段；已结束事项只作为线索。
- `TaskRepository.ask` 为待答问题生成稳定编号，绑定保存后的事项版本。发送问题时，公开消息需带 `task_id`、`question_id` 和 `task_version`。候选上下文中的 `question.valid` 仅在消息已公开发送、版本一致且事项仍等待用户时成立。
- `source_message` 可按引用回查完整原话。候选、原话回查和只读订单核实均校验用户；业务范围由认证后的渠道传入。范围受限而原话没有可靠事项关联时返回缺失，不猜测归属。
- `build(..., check_orders=True)` 按需调用现有只读订单列表工具。调用期间设置认证身份，结束或失败后恢复原身份；商品相同的多个订单一起保留，工具失败写入 `gaps`。
- `CandidateContext.request(template, input_limit=...)` 对提示词、输出结构和候选一起计算预算。先移除完整的非必要历史，保留本次所有原话、明确对象和有效问题；必要内容仍放不下时明确报错。候选过多、历史检索失败及工具结果缺失均在返回结构中说明。
- 当前复用词语检索，不新增向量库或第二份事项缓存；长期偏好整理留给第 10 部分。第 04 部分须检查候选缺失标记，不能把被省略的对象当作不存在，也不能复用历史授权。

验证入口为 `tests/test_task_candidates.py`，同一组用例在 SQLite 和隔离 PostgreSQL 中运行，覆盖跨会话、相同商品多订单、过期问题、身份与渠道隔离、原话回查、检索失败和完整请求预算。
