# 08 协调回复并支持持续输入

综合已经收到的信息回复，能够合并就合并，慢结果稍后补充，不按消息条数机械回复。

前置：完成 [07 让独立事项并行处理](07-parallel-scheduling.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/api/conversation.py`、`app/support/store.py`、`app/runtime/notifications.py`、`app/runtime/streaming.py`、`frontend/src/App.jsx`、`frontend/src/supportClient.jsx`。

## 实施步骤

1. 会话层收集事项结果与待答问题，记录每个结果或问题是否已经发布。多个就绪结果可以组成一条回复，不等待所有事项完成，也不承诺一批消息永远只回复一次。
2. 发布前检查新增消息及相关事项版本。对可能影响当前回复的信息先完成理解；限制重新组织回复的次数与时间，持续输入时先发送已核实且不受影响的部分。
3. 对照结构化证据核对订单、商品、金额和状态，避免不同事项的证据混用。优先问一个具体且有推进作用的问题，不重复询问用户已提供的信息。
4. 在保存回复时再次核验读取的消息位置和有效版本，并保存本次覆盖的结果。检查之后到来的消息作为后续输入处理，不把无法预知的未来信息计为发布错误。
5. 用稳定事件编号保存公开回复，复用 Outbox 和 SSE 游标补拉。通知可以重复，前端展示不能重复；传输中断后能从数据库恢复。
6. 前端允许执行期间继续输入，区分已接收、处理中和回复结果；准备按具体操作展示确认卡片的接口，不增加复杂事项管理面板。

## 验收

- 用户分开发送订单、原因和补充，在处理前或处理中到达都不会重复追问。
- 两个独立事项一快一慢，快结果先回复，慢结果到达后补充且不重复已有内容。
- “不是 A，是 B”在发布前到达时不发送过时结论；发布后到达则正常续接纠正。
- 持续输入不会无限等待；SSE 断开重连、重复通知和页面刷新不会重复显示回复。

## 本次交付边界

交付后端发布协调和前端持续输入。此时可以演示只读的多事项对话，不开放新链路的真实业务提交。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现的处理顺序

1. `POST /api/v1/task-messages` 保存消息后立即返回接收结果。前端在这次请求结束前也能继续发送，每条消息有自己的请求编号；发送失败时单独重试该消息。
2. `ConversationWorker` 在有空位时领取待理解消息，调用同一个 `AgentEngine.associate`。每次模型调用最多等待 15 秒，沿用 04 的两次判断和澄清兜底。模型调用在事务外执行，接收消息不等待模型。
3. 事项修改与执行唤醒记录一起保存。Worker 根据尚未安排的事项版本调用 07 的 `TaskSchedule`；即使进程在归属保存后退出，重启也能补上执行。执行器自己保存等待进度产生的新版本，仍复用原执行，不重复调用模型。
4. `ReplyCoordinator.publish(session_id)` 每次最多检查 50 个完成结果、发布 8 个就绪片段。没有完成的事项继续执行，不挡住其他事项。暂时不能发布的候选轮换检查，避免大量待答问题挡住后面的结果。
5. 发布时锁定当前用户的消息接收边界、会话控制记录和事项来源版本，再检查新消息、人工接管、纠错和待澄清的归属。无效的旧结果记为过期；归属澄清优先于普通追问，同一会话最多保留一个当前有效的已发布问题。
6. 对每个事项分别读取其成功查询回执。回执必须属于该用户和事项、对象一致、来源有效、控制版本一致，且查询时间不超过 60 秒。订单状态和金额、物流状态、商品价格与库存通过固定字段生成文字；不直接发布模型的自由回复。失败、过期、对象不符或格式错误的回执只能得到未能核实的提示。
7. 回复事件、覆盖的结果编号和通知一起提交。公开事件带有稳定 `event_id`、`result_ids`、`task_versions`、`decision_ids` 和 `evidence_ids`；带问题时还保留 `question_id`、`task_id`、`task_version`，供下一次判断归属使用。合并回复关联到其中的每个事项，05 的纠错能够使这条合并回复退出后续上下文。
8. 前端复用已有 SSE 和会话历史。事件按会话序号合并，游标只向前走；刷新从数据库恢复，迟到的 HTTP 响应不会清空新输入。接收进度单独显示，正文只展示已经发布的回复。

## 新消息与持续输入的边界

收到但尚未理解的消息，可能是“不是这笔”或对之前内容的补充。这时先展示“已接收、处理中”，等待归属判断；不能把旧结果直接认定为不受影响。同一段持续积压只保存一次处理提示，该提示不作为客服回复进入对话上下文，也不占用任何结果。

归属明确后，版本未改变且没有被澄清问题影响的结果可以立即发布。发布阶段不再调用模型重新写稿，因此没有反复重写回复的循环。检查与保存处于同一个事务；事务之后接收的消息进入下一次处理。

持续输入且归属一直不明确时，可以保证接收进度及时可见，不能保证立即给出业务结论。不能为了满足回复时限而猜订单。另一个由人工处理的会话不会仅因存在未理解消息就挡住无关事项；已经关联到人工会话的事项仍受人工控制检查保护。

## 保存的数据

数据库升级到版本 16，新增三张小表：

| 表 | 保存什么 | 用途 |
| --- | --- | --- |
| `task_execution_wakes` | 事项编号、已安排的版本、执行编号、下次重试时间 | 进程退出后补上尚未安排的执行 |
| `task_reply_items` | 用户、结果或澄清编号、会话、发布序号、处理情况、检查时间 | 同一结果只发布一次；区分暂缓、过期和已发布 |
| `task_reply_sessions` | 会话、上次检查时间、是否已提示当前积压 | 轮流检查会话，避免重复发送处理提示 |

公开回复继续保存在 `support_events`，通知继续使用现有 Outbox。原始消息和执行回执不复制到新表。升级失败整笔回滚；重复初始化不重建已有记录。

## 受控运行

API 和 Worker 使用同一套配置、同一个会话数据库，优先取 `SUPPORT_DATABASE_URL`，未设置时取 `API_SESSION_POSTGRES_DSN`。只在隔离环境启用：

```dotenv
TASK_INTAKE_ENABLED=true
TASK_WORKER_ENABLED=true
```

启动既有 API，然后另开终端运行：

```sh
python -m scripts.task_worker
```

在前端环境中设置 `VITE_TASK_PIPELINE_ENABLED=true` 和 API 地址，再运行 `npm run dev` 或重新构建。Docker 构建也提供同名参数，默认仍为 `false`。前端使用按用户隔离的新会话标识，避免把旧链路会话送入新入口。

`GET /api/v1/task-messages/{session_id}` 保留消息处理位置，增加 `processing` 和 `active_tasks`，供界面显示处理中或等待补充。待重试消息暂存在当前浏览器标签页，重试保持原请求编号；收到服务端确认或历史记录后移除。

`OperationConfirmation` 仅提供按 `operation_id` 展示确认内容的组件接口，默认不能提交。新链路仍只允许查询、澄清和保存进度；真实业务操作由 09 接入。政策回答和长期记忆继续按 10、11 的计划完善；本部分不会把无结构化依据的模型文字当作已核实结论。

## 验证入口

- `tests/test_coordinated_replies.py`：SQLite 与隔离 PostgreSQL，覆盖快慢结果、合并回复、跨会话新输入、纠错前后、单个追问、已知信息、证据失效、多进程发布竞争、原子回滚、迁移重试、恢复执行、归档和队列到期。
- `tests/test_coordinated_replies_http.py`：真实 HTTP、多个 API 进程、隔离 PostgreSQL/Redis，覆盖消息重投、合并回复、携带 `Last-Event-ID` 重连、历史补拉和刷新。
- 前端 `npm test` 检查消息合并、游标和重试记录；`npm run test:browser` 使用 Playwright 操作实际页面，覆盖连续输入、迟到响应、失败重试、重复通知、乱序通知和刷新。Windows 默认使用已安装的 Edge；其他环境可安装 Playwright Chromium，或通过 `PLAYWRIGHT_CHANNEL` 指定已安装的浏览器。
- 前端开关关闭、开启两种构建均须通过；模型与业务查询使用受控替身，不将这些测试记录为线上模型准确率或真实业务办理验收。
