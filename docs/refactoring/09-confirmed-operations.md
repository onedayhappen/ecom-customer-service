# 09 确认具体内容后提交业务操作

让退款、改地址等已具备接口的操作只作用于正确对象，并防止重复或过期提交。

前置：完成 [08 协调回复并支持持续输入](08-coordinated-replies.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/reliability/mutations.py`、`app/execution/proposals.py`、`app/support/store.py`、`app/tools`、`app/data`、`frontend/src/App.jsx`。

## 实施步骤

1. 复用当前预检、MutationGuard 和回执能力。明确每个已开放工具支持的对象与参数；不具备商品行、数量或撤销能力时拒绝扩大操作范围并转人工，不在本步新建换货、赔付接口。
2. 预检核验归属、资格和已有申请，金额用业务系统及确定性计算得到。展示具体订单、商品、数量、动作、原因、金额和权益影响，区分估算与可提交结果。
3. 确认凭证绑定用户、事项、对象、固定参数、有关版本和有效期。对象或相关参数变化、纠错、取消或接管使确认失效；无关事项的新消息不使它失效。
4. 确认前先处理此前已收到且尚未判断归属的消息。用同一短事务检查消息处理位置、事项版本、取消和接管状态，建立操作记录并登记开始；事务之外请求业务系统。
5. 稳定操作编号贯穿确认、执行和回执。业务侧在提交时再次核验最新状态和共同资源；支持幂等则传同一编号，已成功则返回原回执，未知结果先查询且不自动重提。
6. 确认卡片与后端状态一致，失效卡片不可提交。用户取消先于开始登记时阻止执行，晚于开始则查询真实结果；需要补救时使用既有撤销能力或交人工。

## 验收

- 退款对象 A 改成 B、数量变化或旧确认重放，均不能提交旧参数。
- 无关事项补充不会使合法确认失效；尚未理解的“先别退”会阻止提交。
- 确认、改口、取消、人工接管并发发生时，开始登记与控制版本的先后决定结果，不出现检查后绕过。
- 重复投递、跨 session 重复确认、业务超时和提交后进程退出，不重复写入。验证既有业务工具的确定性校验，未知结果不误报成功。

## 本次交付边界

交付已开放业务工具的完整保护，使用受控业务接口验收。接管与恢复的整条交接在 12 验证，新链路生产写入仍等待 14。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 实际接口范围

- `apply_refund` 只登记整单退款申请。订单金额是参考，不承诺审核金额、优惠券退回或资金到账。
- `issue_invoice`、`reissue_invoice` 只建立本地演示发票记录；重开要明确原发票编号，不连接税务系统。
- 当前改地址接口只能查询可行性，没有提交接口。部分商品、部分数量、换货、赔付和撤销也没有可用写接口，不能用整单退款替代，转人工核实。

## 实现顺序和责任

1. 继续使用同一个 `AgentEngine` 和执行预算。只新增 `prepare_operation`，模型只能给出动作和当前事项版本，不能传入任意订单参数、确认凭证或直接调用写接口。缺少字段继续追问，无法核实范围则实际创建人工工单。
2. `BusinessOperations.preview` 从当前事项固定订单、原因和发票字段，再查询已登录用户的 MySQL 订单、规则和已有申请。核验整单商品及数量；带有无法核验的条件时转人工。金额精确转换成整数分，不做浮点估算。
3. `TaskOperations.prepare` 在查询之后再次检查事项版本、消息处理位置、执行租约和人工控制。保存固定参数、业务数据版本、来源及控制版本；生成 10 分钟有效的确认凭证，只存摘要。凭证绑定整个确认内容，模型和事件日志不接收原凭证。
4. 前端按具体操作展示订单、商品、数量、原因、金额性质、权益影响和演示标识。确认请求只能提交操作编号、会话编号和凭证，服务端从已保存记录读取业务参数。刷新页面仍能恢复同一张卡片。
5. 确认事务先锁定用户的消息接收边界，再检查未理解消息、当前事项、来源有效性和人工控制，并占用该订单、登记开始。新消息先到则阻止确认；确认先登记则视为操作已开始。事务提交后才请求业务系统。
6. 业务库提交时锁定订单，再比较预检版本和办理条件。同一个操作编号同时用于确认、业务幂等和回执；数据库操作与成功回执一起提交。不同事项操作同一订单时也检查共同资源，不能只靠单进程内存锁。
7. 保存回执时核验操作编号、订单和结果状态。把真实结果写入既有操作记录、Case 工具证据和公开消息；相关事项没有更新时，保存等待后续结果的进度。用户已经修改的事项不会被旧回执覆盖，实际已发生的操作仍保留。
8. 超时、连接中断或进程退出后，先查原编号的业务回执。查不到不代表没有提交，标为待核实、保留订单占用并交人工，禁止自动重提。Worker 独立查询过期的执行记录，不阻塞消息理解和其他事项查询。
9. 开始前取消，原卡片不能再执行。开始后取消或修改，保存用户要求并交人工核实补救；卡片取消同时查询原回执，不宣称已撤回。退款申请已登记不等于退款完成，最终结果继续由 13 跟进。

人工核实沿用现有管理员权限和审计接口，确认结果后释放该订单占用。内部调查备注不放进客户卡片；人工核实后又收到业务回执，保留迟到证据并重新交人工复核。

## 数据与接口

会话数据库升级到版本 17。操作状态和回执仍保存在 `support_operations`，不另建一套操作流水。

| 新表 | 保存内容 |
| --- | --- |
| `task_operation_proposals` | 操作编号、用户、事项及版本、固定预检内容、凭证摘要、确认有效期、执行核实期限 |
| `task_operation_resources` | 当前被执行中或结果待核实操作占用的业务订单 |

`support_operation_tasks` 继续保存操作与事项的关联；业务侧复用 `commerce_mutations` 保存原编号的成功回执。升级失败整笔回滚，保留已有事项、操作和消息。

| API | 用途 |
| --- | --- |
| `GET /api/v1/task-operations/{session_id}` | 读取当前会话关联事项的确认卡片和回执 |
| `POST /api/v1/task-operations/{operation_id}/confirm` | 验证凭证并提交固定操作 |
| `POST /api/v1/task-operations/{operation_id}/cancel` | 取消未开始的操作；已开始则核实并转人工 |
| `POST /api/v1/task-operations/{operation_id}/refresh` | 查询原操作结果，不重新办理 |

所有接口验证登录用户和会话归属。重复确认返回当前状态或原回执。过期、取消或相关事项变化后，继续对话重新核实需求，再准备当前事项版本的卡片，不恢复旧授权。

## 隔离运行和验证

仅在隔离环境同时启用 `TASK_INTAKE_ENABLED=true`、`TASK_WORKER_ENABLED=true`、`TASK_OPERATIONS_ENABLED=true`，前端仍使用 `VITE_TASK_PIPELINE_ENABLED=true`。四个开关默认关闭。API 与 Worker 使用同一会话库、相同且至少 32 字符的 `API_JWT_SECRET`；生产业务写入等待 14。

`deploy/compose.integration.yml` 增加独立 MySQL 测试实例（本机端口 23306，数据库 `ecom_operations_test`），与已有隔离 PostgreSQL/Redis 一起运行。专项测试固定使用该数据库，不读取实际 `ORDER_DB_DSN`，每次只清理自身生成的订单和回执。

用 `docker compose -p ecom-refactor-tests -f deploy/compose.integration.yml up -d --wait` 启动隔离设施；在测试进程中设置 `ECOM_INTEGRATION=1` 启用数据库验收，并将 `ORDER_DB_DSN`、`ORDER_CACHE_REDIS_URL`、`API_CONCURRENCY_REDIS_URL` 留空，避免其他测试连接实际业务环境。

- `tests/test_task_operations.py`：SQLite/PostgreSQL 上的凭证、版本、归属、取消竞争、共同订单占用、超时恢复、原子保存和迁移。
- `tests/test_task_operations_api.py`：登录、会话隔离、固定参数、待处理取消消息、接口开关和重复确认。
- `tests/test_task_operations_mysql.py`：真实业务数据库的退款、开票、重开、业务版本变化、订单锁、多个应用进程竞争和进程退出恢复。
- `frontend/tests/browser/confirmed-operations.spec.js`：真实浏览器上的确认内容、持续输入、失效卡片、取消、网络中断及刷新恢复；API 使用受控替身。

本次结果：完整后端回归 1117 通过、258 跳过，另有 15 个子测试通过；最终 09 专项在 SQLite/PostgreSQL、实际 MySQL 业务事务和 API 上共 102 通过。回复协调与真实 HTTP/SSE 集成复测 57 通过，接收取消路径补测 4 通过。前端状态测试 3 通过，实际 Edge 浏览器测试 6 通过，新链路开关关闭、开启两种构建均通过。

完整回归按配置跳过独立基础设施测试，上述专项另行使用隔离数据库验证。MySQL 测试仍有既有连接层 `ping(reconnect=True)` 的弃用提示。模型决策与浏览器 API 使用受控替身；真实资金退款、税务开票及线上模型准确率不在本次验收范围。
