# 13 跟进外部结果并判断事项何时结束

业务受理后继续跟进真实进度，区分提交成功、处理完成和用户暂时不回复。

前置：完成 [12 交给人工并正确恢复机器人](12-human-handoff.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/tasks/service.py`、`app/runtime/maintenance.py`、`app/support/store.py`、`app/tools/commerce_service.py`、`app/tools/logistics.py`。

## 实施步骤

1. 等待外部结果时保存申请号、订单商品或运单、实际阶段、来源、下次可查询时间和必要期限。释放 Worker 和模型额度。
2. 已有回调入口验证来源并按稳定外部编号关联事项；没有回调时复用维护进程，按可配置间隔和次数上限查询现有业务接口。
3. 重复事件去重，晚到事件不覆盖较新状态；来源冲突或先后无法判断时重新查询业务系统。其他渠道新建的申请也应被核实，不能继续重复办理。
4. 按用户目标决定结束条件。目标是提交申请时以成功回执完成提交工作；目标是解决退款时，已受理只能进入等待，不能宣称资金已到账。
5. 用户道谢、不回复或模型成功生成回复不作为业务完成证据。需要暂停时保存待办信息；签收争议同时保留系统状态与用户陈述。
6. 期限和材料要求展示真实来源。首版只更新站内记录与已有通知渠道，不承诺离线提醒；查询次数耗尽或状态无法核实时交人工。

## 验收

- 退款受理、退货寄回和仓库收货分别显示真实阶段，不越级宣布到账。
- 重复、乱序回调和轮询超时不重复申请、不倒退进度；无效来源被拒绝。
- 多包裹只更新对应运单，部分售后只更新对应商品；接口能力不足时说明范围。
- 进程重启继续等待，用户道谢或长时间沉默不误关事项，查询次数有上限。

## 本次交付边界

交付等待外部结果、有限查询和结束判断。任何新的退款、换货、赔付或离线推送接口仍需另行定义能力与验收。
