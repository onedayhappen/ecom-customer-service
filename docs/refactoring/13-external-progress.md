# 13 跟进外部结果并判断事项何时结束

业务受理后继续跟进真实进度，区分提交成功、处理完成和用户暂时不回复。

前置：完成 [12 交给人工并正确恢复机器人](12-human-handoff.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/tasks/service.py`、`app/runtime/maintenance.py`、`app/support/store.py`、`app/tools/commerce_service.py`、`app/tools/logistics.py`。

## 实施步骤

1. 等待外部结果时保存申请号、订单商品或运单、实际阶段、来源、下次可查询时间和必要期限。释放 Worker 和模型额度。
2. 已有回调入口验证来源并按稳定外部编号关联事项；没有回调时复用维护进程，按可配置间隔和次数上限查询现有业务接口。
3. 重复事件去重，晚到事件不覆盖较新状态；来源冲突或先后无法判断时重新查询业务系统。其他渠道新建的申请也应被核实，不能继续重复办理。
4. 按用户目标决定结束条件。目标是提交申请时以成功回执完成提交工作；目标是解决退款时，已受理只能进入等待，不能宣称资金已到账。
5. 用户道谢、不回复或模型成功生成回复不作为业务完成证据。需要暂停时保存待办信息；签收争议同时保留系统状态与用户陈述。
6. 期限和材料要求展示真实来源。首版只更新站内记录与已有通知渠道，不承诺离线提醒；查询次数耗尽或状态无法核实时交人工。

## 验收

- 退款受理、退货寄回和仓库收货分别显示真实阶段，不越级宣布到账。
- 重复、乱序回调和轮询超时不重复申请、不倒退进度；无效来源被拒绝。
- 多包裹只更新对应运单，部分售后只更新对应商品；接口能力不足时说明范围。
- 进程重启继续等待，用户道谢或长时间沉默不误关事项，查询次数有上限。

## 本次交付边界

交付等待外部结果、有限查询和结束判断。任何新的退款、换货、赔付或离线推送接口仍需另行定义能力与验收。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现的处理顺序

1. 事项通过业务确认得到受理回执，或 Agent 查询到具体售后、物流后保存 `waiting_external`。等待记录保留操作号或查询证据，不占用模型和执行 Worker。用户明确只要求提交申请时，以成功提交的回执结束这项提交工作；普通退款诉求继续等待最终结果。判断同时检查事项目标和用户原话，后来的“还要跟进到账”不能被早先的“只提交”覆盖。
2. 维护进程从等待记录建立查询安排。它只接受同一用户、同一事项的真实操作或查询来源，记录订单、申请号、商品范围或运单和结束条件。没有明确对象、原来源已失效或当前接口无法覆盖时，创建真实人工工单。
3. 每次领取一个到期查询，先检查新消息、归属澄清、人工接管、事项版本与状态。领取编号和到期时间保存在数据库；另一进程不能重复领取。查询在事务外执行，不调用模型，不准备或重试业务提交。
4. 退款、退货使用现有 `query_after_sale`，物流直接读取已鉴权的物流数据源，绕过对话缓存。本地演示发票使用 `query_invoice`，始终标明不是税务发票。当前项目没有业务回调接收入口，因此本版采用有限轮询；客户端不能提交一个“已完成”状态改变事项。
5. 结果必须匹配订单和具体申请或运单。跟进本系统提交的申请时，还要匹配原操作编号；不能把同一订单上的旧申请当成本次结果。指定商品、数量或店铺而数据源不能证明对应范围时，不扩大到整单。其他渠道已有申请继续查询，原业务预检会阻止再次申请。
6. 受理、审核、退货寄回、仓库收货、退款处理和资金到账分别记录。单独的 `refunded` 或 `completed` 文本不能证明到账；到账需要业务记录中的资金时间、交易编号和匹配的申请。只有明确目标对应的阶段有证据时才结束。指定运单签收只表示这一票；签收争议同时保留系统状态与用户陈述并转人工。
7. 保存结果时再次检查控制权、版本和领取编号。重复结果不重复通知；较旧结果、倒退阶段、申请编号变化或相同来源时间却内容不同的结果，保留原进度并重新查询。超过查询次数则交人工。超时后迟到的返回不能回写；进程退出后可重新领取到期查询，原先已用的查询次数仍然保留。
8. 事项进度、查询回执、公开消息和通知在同一事务提交。通过原有站内会话和 SSE 展示，刷新和跨实例补拉继续按消息序号去重。进度更新不会另起一个空 Agent 执行、重复追问或生成“没有查询结果”的回复。用户暂停、尚未理解的新输入和人工接管都会停止自动推进。

## 保存的数据

数据库版本升级到 19，新增两张表。事项的业务进度仍保存在原来的事项记录中，不另建一套办理流程。

| 表 | 保存内容 | 用途 |
| --- | --- | --- |
| `task_external_waits` | 事项与用户、发布会话、事项版本、查询对象、次数、下次查询时间、领取编号和到期时间、最近结果与错误类型 | 有限查询、进程恢复和多实例去重 |
| `task_external_receipts` | 事项编号、稳定结果编号、已核实的阶段与来源 | 结果去重与审计 |

公开结果复用 `support_events` 和通知 Outbox，证据复用 Case 回执。既有等待记录在维护时按原来源识别，不凭历史自由文本自动创建业务操作。迁移失败回滚，重复初始化不重复建表。

售后数据契约补充可选的原请求编号、商品范围、运单、材料要求、期限和资金凭据。只有数据源实际提供的字段才可使用，不能由模型或客服聊天补出。材料要求含密码等敏感内容时拒绝展示并交由核实；期限只显示来源中的具体时间，过期未完成则转人工。

查询次数耗尽后保持原待办与证据。用户明确恢复机器人时可开始新一轮有限查询；普通道谢、补充信息或客服标记解决不会自动清零次数或结束事项。

## 受控运行

只在隔离环境启用，API、事项 Worker 和维护进程采用一致配置：

```dotenv
TASK_EXTERNAL_PROGRESS_ENABLED=true
TASK_EXTERNAL_INTERVAL_SECONDS=300
TASK_EXTERNAL_MAX_ATTEMPTS=12
TASK_EXTERNAL_TIMEOUT_SECONDS=10
```

需要已配置的 `ORDER_DB_DSN`。跟进使用已鉴权的业务读取，不在数据源失效时换成模拟结果。维护入口为：

```sh
python -m scripts.platform_maintenance --once
python -m scripts.platform_maintenance --interval 300
```

每轮最多处理 4 个到期查询，单次查询有超时，不占用 Agent 模型额度。维护进程的运行间隔会影响实际查询延迟；用户看到的是站内进度，不承诺离线推送。来源无法确定先后或接口缺少商品、资金等证据时，保留未完成状态并在有限重查后交人工。
