# 06 通过统一执行入口推进一个事项

单次只推进一个事项，明确上下文、工具权限、预算、结果保存和停止条件。并行能力留到 07。

前置：完成 [05 修正错误关联并阻止错误继续传播](05-关联纠正.md)。 共用约束见[实施入口](重构实施入口.md#共用实现规则)。

## 改动位置

`app/agents/engine.py`、`app/tasks/execution.py`、`app/execution/react.py`、`app/reliability`、`app/runtime/budgets.py`、`app/tools/task_context.py`。

## 实施步骤

1. 执行输入明确用户、事项编号、预期版本、消息来源和预算。读取当前事项及相关证据后装配上下文，不把其他订单的细节混入本次操作。
2. 复用现有工具循环和 Agent harness，统一检查工具白名单、参数、身份、调用次数、时长、重复调用和资源额度。先仅开放只读工具、澄清和受控进度保存。
3. 使用 `read_task_context` 和 `save_task_progress` 读取与保存当前事项，只保留一份进度；工具依据从事项事件中读取。
4. 每次模型或工具调用前检查停止状态和有效版本。查询允许有限重试，业务拒绝不反复尝试；工具返回是资料，不能授权任意 SQL、命令或外部地址。
5. 每次取得有效信息就保存结构化结果，包含对象、参数、查询时间、来源和适用版本。调用发生在数据库事务之外，失效执行不得覆盖新进度。
6. 缺资料则输出待答问题，等待外部结果则保存等待原因并释放资源。已取得证据但生成回复失败时使用确定性文字；执行器只交付结果，不直接向用户发送。

## 验收

- 新消息修改对象后，旧执行不能保存结果到新对象；不相关查询结果可按条件复用。
- 没有权限的工具不能调用；重复调用、调用超时和预算耗尽都有有限结束路径。
- 等待用户期间不占 Worker 或模型槽位；重启后能读取已保存进度。
- 模型受到工具文本中的恶意指令影响时，服务端仍阻止越权和写操作。

## 本次交付边界

交付单事项执行接口及结构化结果。07 复用该入口调度多个事项，不再增加新的 Agent 角色。

完成后在 [实施入口](重构实施入口.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现接口

- `AgentEngine.execute_task(store, authenticated_user_id, request, scope=...)` 复用同一 Agent 的模型客户端和 `ReactExecutor`。输入提供 `job_id`、`session_id`、`task_id`、`expected_version`、已经关联的原话 `source`，以及可选的 `budget`；用户身份与渠道访问范围由认证调用方单独传入，执行和回执重放均校验该范围。
- `budget` 限制模型调用数、工具调用数、总时长、单次调用时长和输入输出 token。工具内部通过 `LlmClient` 发起的模型请求也计入预算。继续使用现有模型资源额度和循环检测，不建立第二套 Agent。
- 新入口只开放订单、物流、商品和知识查询，以及 `read_task_context`、`save_task_progress`、`ask_user`。参数采用严格结构，订单和物流必须属于当前事项；受限渠道的查询结果还须核实所属平台或店铺，缺少依据时不能使用。模型返回其他工具名、其他用户参数、任意 SQL 或外部地址时无法执行。
- `runtime_jobs` 保存执行输入、所属事项、有效版本、占位所有者和结果。数据库约束同一事项只能有一个正在执行的作业；相同作业重试返回原结果。过期执行不会用原编号重新跑，后续调度应明确建立新的安全查询作业。
- 每次模型请求、工具请求和结果保存前检查事项版本、执行期限、关联来源与人工接管。查询和模型调用发生在事务外；过期返回值不能保存到新事项。跨会话人工接管与进度保存通过同一用户的持久控制记录协调。
- 每次有效查询把对象、参数、时间、事项版本和结构化结果写入 `support_events`，并在同一事务保存为 事项工具证据。失败查询也记录原因，但不能作为业务事实。近期成功查询仅在对象相同、参数相同、来源有效且未超过 60 秒时复用。
- 新入口的 `read_task_context` 只读当前事项及同订单的历史回执，过滤旧草稿、确认凭据和其他用户记录。`save_task_progress` 改为保存本事项的进度，只接受预期版本、等待状态、问题或等待原因；等待外部结果需要引用有效查询证据。
- `ask_user` 的问题字段与服务端允许字段保持一致，保存为带编号和版本的待答问题。密码、验证码等敏感信息不能成为待答要求。等待用户或外部进度后结束本次执行，之后可以从数据库恢复。
- 同步调用超时后不再使用迟到结果；底层调用真正结束前仍占用调用名额，防止慢调用无限堆积。这一机制只用于模型和只读工具，不能套用到业务写入。进度保存走短事务。
- 已有查询证据而后续模型失败时返回确定性的说明；过期执行返回中断状态。执行器交付结构化结果和来源凭据，不发布公开回复，也不把“需要人工”冒充已创建人工工单。

验证入口为 `tests/test_task_execution.py`。实际模型验证入口为 `python -m scripts.eval_task_execution --live`，使用合成订单、临时数据库和受控查询返回，检查查询、缺信息提问、等待外部进度和恶意工具文本；报告保存在被 Git 忽略的 `data/evaluation/task_execution_smoke.json`。这不代表真实订单系统的业务办理已经接通。

2026-10-20 使用 `deepseek-v4-flash` 复验上述 4 个场景，4 个达到预期结束状态，业务操作 0 次、公开回复 0 条。校验不接受的进度格式会反馈给模型，在同一预算内重新处理；报告保留拒绝原因。该小样本用于检查接入与安全边界，不作为生产准确率估计。
