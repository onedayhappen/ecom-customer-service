# 11 按业务条件检索适用规则

让 RAG 返回当前订单或咨询真正适用的条款，而不是只选语义相似的片段。

前置：完成 [10 维护跨会话记忆和上下文](10-记忆维护.md)。 共用约束见[实施入口](重构实施入口.md#共用实现规则)。

## 改动位置

`app/rag/chunker.py`、`app/rag/retriever.py`、`app/rag/updater.py`、`app/rag/backends`、`app/tools/knowledge.py`。

## 实施步骤

1. 知识按完整条款或小节切分，补齐来源、店铺、渠道、品类、版本、生效时间和访问范围；没有依据的适用条件不能由模型补造。
2. 根据事项的已知条件检索。先过滤访问与业务范围，再结合关键词与向量检索，去重后返回少量片段；额外排序模型暂不作为必需依赖。
3. 处理历史订单时按真实业务规则确定适用版本，不能简单认为购买时或当前最新版本一定适用。缺少适用依据时追问或转人工。
4. 结果携带来源和适用条件，回复可以追溯；订单金额、物流及申请状态仍查询业务工具，不从知识文本推断。
5. 把文档、附件及工具返回作为不可信资料，识别不到可靠条款或出现冲突时明确停止猜测。检索故障不能用过期缓存假装新依据。
6. 沿用 Chroma，以版本化索引发布与回退。更换向量模型时重建配套索引，并把 05 的来源失效检查用于有关缓存。

## 验收

- 相似退货问题在不同店铺、商品或渠道下返回各自适用规则。
- 历史订单、版本交替、缺失条款和冲突条款都不会直接套用最新结果。
- 恶意条款不能改变系统指令、工具权限或确认要求；其他访问范围的片段不泄露。
- 索引发布与回退可验证，模型与索引不匹配时明确失败；用实际条款样例检查检索命中和回答依据。

## 本次交付边界

交付带适用条件和来源的知识检索。附件识别、额外排序模型不在本步扩展。

完成后在 [实施入口](重构实施入口.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 实现后的处理顺序

1. Agent 仍调用 `search_knowledge(query, top_k)`。它不能传访问权限、规则版本或订单时间。Harness 从当前事项构造检索条件；涉及订单时，先取得属于本事项、对象一致且不超过 60 秒的 `query_order` 回执。普通咨询可以使用用户明确提供的店铺、渠道和品类。
2. 订单适用条件取自业务回执，不用用户的陈述填补缺失的业务事实。多商品订单只有在商品编号能选中明确品类、或所有相关商品属于同一品类时才确定品类。时间必须包含时区；没有可靠时间或适用范围时返回缺失项，Agent 追问或转人工。
3. 先读取索引中的条款元数据，排除内部资料、已撤回来源、不匹配的店铺、渠道、品类和有效区间。未通过这些检查的正文不会进入关键词或向量检索。历史版本按运营声明的适用时间依据选择，区间为包含起点、不含终点。按咨询时间适用时使用触发本次执行的原始消息接收时间，排队延迟不能使请求跨到新版本。
4. 对符合条件的正文同时做关键词和 Chroma 向量检索，合并排名、去重，最多返回五段。完全无关的最近向量不能成为答案；相关规则存在版本冲突或仍缺条件时返回明确失败。其他无关主题的冲突不阻止已核实主题的检索。
5. 回执保留完整条款、来源地址、文档及版本、适用范围、时间依据、正文校验值和本次索引版本。Harness 校验回执与实际索引、当前事项条件一致，下一次模型或工具调用前重新检查；索引变化、撤回或订单依据过期时停止使用旧结果。
6. 回复发布前，在数据库事务外限时验证条款；进入发布事务后，再核验事项、消息位置、控制权和原订单回执。按固定结构展示完整条款、来源、适用条件和版本区间。条款不能代替业务查询，也不能授予退款权限或替代第 09 部分的确认。
7. 完整回复和工具证据保留供用户查看及审计。后续模型上下文、原话检索和摘要中，规则正文替换为“须重新检索”的说明；合并回复中的其他事项结果和问题保留。旧规则回执不进入下一次执行的可复用证据。05 的关联纠错、来源失效及 10 的原话校验继续生效。

## 知识资料的准备

每份 Markdown 文件旁放置同名的 `.policy.json`。元数据由了解业务规则的维护者审核填写，不能由模型从正文猜出，也不能直接采用客户上传文件中的声明。每份文件按完整二级小节切分，保留小节内的三级标题、例外和限制；文档导语附在每个小节前。超过 12000 字的完整小节需要人工整理，程序不截断条件。

以下只展示格式，店铺、日期和地址均为测试示例，不代表仓库现有条款的实际适用范围：

```json
{
  "source_id": "refund-policy",
  "source_uri": "https://policies.example.test/refund",
  "version": "v1",
  "rule_key": "refund",
  "platform_code": "pdd",
  "store_id": "shop-a",
  "channel": "web",
  "category": "headphones",
  "audience": "public",
  "selection_basis": "order_created_at",
  "selection_reference": "经业务审核，此版本按订单创建时间适用。",
  "effective_from": "2024-01-01T00:00:00+08:00",
  "effective_until": null,
  "reviewed": true
}
```

- `source_id` 标识资料，`version` 标识版本；同一次发布不能出现重复组合。`rule_key` 把同一规则的版本归为一组，用于发现冲突。
- 店铺、渠道、品类和平台填业务系统使用的值；只有确有不限范围的依据时才填 `*`。`audience` 为 `public` 或 `staff`，客服 Agent 只检索 `public`。
- `selection_basis` 只能是咨询时间 `request_at`、订单创建时间 `order_created_at` 或签收时间 `delivered_at`；`selection_reference` 说明为什么按这个时间选版本。未覆盖的业务选择方式应转人工，不擅自套用现有方式。
- `source_uri` 是可追溯的 HTTP(S) 来源，不含账号密码。它不会由 Agent 自动打开或执行。来源和正文中的指令均不授予工具权限。
- 当前订单 DTO 会保留数据源明确提供的 `store_id`、`channel`、`category`。原有订单表没有这些列，原有无时区时间也不能直接用于历史版本选择；代码不会编造默认值。上线前须由业务数据接入补齐权威字段和时区约定。
- 仓库现有知识文件缺少经过审核的范围与版本声明，未自动为其生成生产元数据。没有可发布资料时返回明确失败，旧检索结果不作为新链路的替代依据。

## 索引发布、回退和撤回

仍使用 Chroma。每次发布创建新的集合，验证条目数、正文校验值和向量维度后，才切换 SQLite 发布目录中的当前版本。切换比较构建开始时的版本号，多个进程不能用旧构建覆盖后来发布。进程中途退出不会删除原集合；已验证但未激活的版本可重新激活。

在项目根目录运行，路径参数放在动作名称之前：

```sh
python -m app.rag.commands.policy_index --kb-dir reviewed-knowledge publish
python -m app.rag.commands.policy_index rollback policy_已有版本编号
python -m app.rag.commands.policy_index revoke refund-policy --version v1
```

发布和回退命令输出当前集合编号、发布版本号及模型标识。撤回不指定 `--version` 时撤回该来源的全部版本；撤回记录独立保存，回退不能恢复已撤回的条款。Chroma 集合和对应的 `.policy-releases.sqlite3` 必须一起保留及备份，不能只复制向量文件。

本地向量模型以实际配置、权重和词表文件的摘要标识。运行中更换文件会拒绝继续编码，须重启模型进程并重建索引。远程模型以提供方、端点和模型名绑定；部署方须使用可识别版本的模型配置，不能在同一个名字下无记录地更换模型。维度、模型或正文不匹配均拒绝使用。

独立检索服务沿用服务令牌、请求体及响应大小限制、超时和并发额度。启用新链路的服务设置 `TASK_INTAKE_ENABLED=true`，启动时检查已发布索引与模型匹配；API/Worker 通过现有 `RETRIEVAL_SERVICE_URL` 访问它。新增 `/v1/policies/search` 和 `/v1/policies/validate`。检索失败或服务不可用时不回退本地旧索引；验证也不会触发模型调用。

## 测试入口

- `tests/test_policy_retrieval.py`：真实 Chroma、完整例外条款、业务范围和访问隔离、历史版本、缺失和冲突、恶意内容、模型与正文校验、多进程发布竞争、构建后进程退出、回退与撤回、操作命令。
- `tests/test_task_policy.py`：SQLite/PostgreSQL 下的单 Agent 工具调用、可信订单条件、公开回复来源、执行中撤回、发布前订单依据过期、伪造工具回执、无授权写操作拦截，以及历史上下文和摘要不复用旧规则。
- `tests/test_policy_http.py`：两个独立检索进程、真实 HTTP、服务鉴权、参数校验、跨实例验证和撤回、远端失败无旧缓存降级。

开启 `ECOM_INTEGRATION=1` 才执行隔离 PostgreSQL 的对应参数组。向量使用可复现的离线测试替身，Chroma、进程、数据库和 HTTP 为实际运行；实际退货条款样例用于检查完整例外与回答来源。上述测试不代表线上向量模型的语义命中率，也不代表生产知识已审核完成。
