## 每次如何开始

1. 阅读本页和当前编号的小方案，只在需要时查阅完整方案的对应章节；无需把全部小方案同时放入上下文。
2. 确认前一部分已完成，从其验证后的提交新建模块分支，分支名说明模块用途，不带 `codex`。阅读本篇涉及的代码和测试，沿用已完成部分的接口。
3. 实现本篇步骤，运行与变更有关的测试。发现前置缺陷时只修复阻塞本篇的部分，并说明影响。
4. 在下表记录状态、实际提交编号和验证结果。状态使用“未开始、进行中、已完成”；没有完成验收就不标完成。每个模块分别提交，单元测试和可靠性验证通过后再进入下一个分支。

可直接使用这样的指令：

> 按 docs/refactoring/01-task-storage.md 实现第 01 部分，只完成该篇范围，运行相关测试并更新实施入口中的状态。

## 共用实现规则

- 采用同一个 Agent 及其执行入口，独立事项可以并行，不引入多 Agent 或独立流程引擎。
- `task_id` 标识一件事，`job_id` 标识一次执行，业务操作编号标识一次固定参数的提交，不能混作同一个编号。
- 01 至 13 在隔离环境或受控测试入口迭代，新链路默认关闭。真实流量维持现有路径；同一真实请求不能同时交给两条链路办理。
- 数据库结构采用版本化迁移，在隔离数据库验证。每份代码可单独检查和提交，生产数据迁移与流量切换统一在 14 执行。
- 用户身份、权限、确认、幂等、人工接管和证据检查从接入对应能力时就必须生效，不留到上线前补做。09 之前新执行入口仅开放只读、澄清和受控进度保存。
- 某能力需要后续部分接入时，本篇完成其接口与契约测试，接入部分再完成整条链路验证；不能把模拟调用记录为真实模型或真实业务集成已通过。
- 一份事项记录保存进度。复用现有消息、Outbox、Case 证据、操作回执和人工工单，不在新路径继续重复维护旧订单草稿。
- 每部分保留来源和必要的结构化日志，隐去敏感信息；不记录隐藏推理。工具与知识内容不授予权限。
- 原有共享能力在替代路径验收前保留，14 再删除无调用的旧链路及配置。前面的每次实现只删除本次已经明确替代的局部代码。
