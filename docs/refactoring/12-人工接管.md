# 12 交给人工并正确恢复机器人

人工能接到真实工单和完整进度，同一事项在其他会话中也不会被机器人抢先办理。

前置：完成 [11 按业务条件检索适用规则](11-规则检索.md)。 共用约束见[实施入口](重构实施入口.md#共用实现规则)。

## 改动位置

`app/support/store.py`、`app/support/runtime.py`、`app/api/support.py`、`app/tasks/service.py`、`frontend/src/SupportConsole.jsx`。

## 实施步骤

1. 沿用现有会话级接管。接管事务保存真实工单、控制版本及受影响事项；将事项的自动执行阻止范围覆盖到该用户其他 session。
2. 交接目标、相关原话、待答问题、已核实信息、处理承诺和操作回执，分别标注用户陈述和已授权结论。
3. 停止未开始的机器人工作，作废受影响确认与未发布回复。已开始操作保留记录，先查实际状态，不因接管就假定已取消。
4. 人工回复直接写入公开会话事件，私有备注按权限保存。客服领取、转派、停用、结案和用户继续发言沿用现有授权规则。
5. 恢复机器人必须有明确恢复事件，并处理相关事项上的所有有效接管约束。读取人工最新更新和业务结果后恢复，不复用接管前的上下文与确认。
6. 无权承诺赔付、改价或额外权益时只记录请求；以前客服的承诺需查询原话和授权。未知操作由有权限人员核实并留证。

## 验收

- 会话 A 已转人工，会话 B 询问同一事项，机器人可说明进度但不能提交业务。
- 机器人工作中被接管，旧结果和旧确认无法发布或执行，已发生操作的回执仍被保存。
- 人工修改信息后恢复，机器人使用新记录；仅标记工单解决不自动夺回服务。
- 越权领取、私有备注泄露、其他客服承诺未核实和未知操作重复提交均被阻止。

## 本次交付边界

交付完整接管与恢复流程；把现有人工支持测试迁移到新事项链路，并保留权限和审计断言。

完成后在 [实施入口](重构实施入口.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现的处理顺序

1. 用户主动转人工，或事项执行器调用 `escalate_to_human`，都通过现有 `SupportStore._handoff` 建立真实工单。工单、控制版本、接管的事项和停止自动执行在同一个事务提交。模型只在文字中说“已经转人工”不会产生工单，也不会直接发布这句话。
2. `task_handoffs` 保存工单与事项的对应关系。事项在其他会话中继续被问到时，可以显示人工处理中，执行和确认入口仍然检查这项约束。接管会停止该事项各会话中尚未完成的执行，取消未提交的确认，使未发布旧结果失效。已经开始的业务操作独立保留状态与回执。
3. 客服工作台显示目标、用户原话、待答问题、查询记录和操作回执。原话带会话、消息编号和时间；客服公开沟通带来源与说话人，并注明可能涉及工单中的多个事项。用户诉求、客服承诺和真实业务结果分别呈现，公开承诺不构成额外权益授权。内部备注继续留在授权客服界面，不进入模型上下文或用户会话。
4. 当前负责客服或管理员可通过 `POST /api/v1/support/tickets/{ticket_id}/tasks/{task_id}` 更新目标和允许的事项字段。请求携带唯一编号和事项版本；断网重试返回同一结果，两人同时修改时只有一个版本能成功。更新事件保存操作者、当时角色、变更内容和来源。数量必须为正整数，权限、赔付结论等字段不能写入。已有执行中、未知或成功业务操作时，不允许把事项对象改成另一笔业务。
5. 标记工单解决仍保留人工服务状态。用户明确恢复机器人时，先检查该事项各会话是否有执行中或未知业务操作，再释放当前工单的接管。存在其他接管时继续停止自动执行；最后一项接管释放后保存明确恢复事件、增加事项版本，清除旧追问并重新安排执行。待外部结果的申请号与进度保留，原确认不恢复。
6. 重新执行时读取人工更新、公开沟通和实际操作状态，重新查询业务事实。新字段与旧回执不会被当作新授权；已提交操作不能重放。未理解的用户消息仍保留，恢复后继续判断归属，不能因转人工而丢弃。

## 数据与权限

数据库版本升级到 18。`task_handoffs` 以工单编号和事项编号共同去重，保存用户、交接时的事项版本、交接快照、接管时间和释放时间。升级为已有人工会话中的未结束事项补建约束；失败整笔回滚，重复初始化不会重复建表或接管。

活动工单读取最新交接，释放时固定历史快照，历史客服不能通过旧工单读取后来新增的事项内容。事项修改复用原有 `task_changes` 和 `matter_change`，增加 `support_event` 来源，只能引用同一事项的真实人工更新或恢复事件，不能借此新建其他事项。

领取、转派、停用、公开回复、内部备注和未知操作核实继续沿用已有授权。新更新接口在读取和写入时都检查工单身份与负责权限，停用客服与非负责客服不能修改。交接的查询和操作回执仅保留必要业务字段，不把确认凭证或私有核实备注传入模型。未知状态必须通过既有有权限核实入口留证后恢复；转人工不代表业务已取消。

## 验证入口

- `tests/test_task_handoffs.py`：SQLite/PostgreSQL 的跨会话接管、多个工单释放、旧结果与旧确认失效、人工更新幂等和版本竞争、私有备注隔离、真实工单创建、接管事务回滚、迁移恢复，以及重新查询和等待申请保留。
- `tests/test_task_handoffs_api.py`：实际认证与 API 权限、客服更新、解决与恢复的区别、公开会话隔离。
- `tests/test_task_handoffs_http.py`：真实双 API 进程与隔离 PostgreSQL/Redis，验证跨实例领取、修改、幂等重试、内部备注、结案与恢复。
- `frontend/tests/browser/human-handoff.spec.js`：实际 Edge 页面验证交接展示、保存响应丢失后的同编号重试，以及工单解决后不自动恢复机器人。

业务提交竞争继续由 `tests/test_task_operations.py` 验证，已开始操作的实际回执不随接管丢失。测试中的模型和业务返回使用受控实现，真实 HTTP、数据库和浏览器测试不等同于线上业务授权或模型准确率验收。
