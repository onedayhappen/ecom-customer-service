# 05 修正错误关联并阻止错误继续传播

发现消息接错事项后，只修正受影响内容，保留正确进度，并阻止旧结果继续使用。

前置：完成 [04 判断消息归属并处理不明确的回答](04-message-association.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/tasks/service.py`、`app/reliability/mutations.py`、`app/session/short_term.py`、`app/memory`、`app/support/store.py`。

## 实施步骤

1. 将用户明确纠正、工具发现对象冲突、服务端校验失败作为纠错入口。记录原消息、原决定、受影响事项和原因；再次纠错也用事件追加保存。
2. 先让受影响执行、待确认操作和未发布回复失效。统一提供版本检查与失效通知接口，供 06、08、09 接入，不能只改展示文字。
3. 按变更来源定位错误字段，检查它们之后是否又被修改。仅恢复或修正错误造成的部分，存在冲突时重新合并或澄清，不恢复整个事项旧快照。
4. 将消息重新关联到明确的正确事项；不明确则进入待澄清。错误新建且没有业务操作的空事项可以结束并保留修正记录，不能删除原话与历史回执。
5. 记录受影响来源已失效，读取摘要、缓存和记忆时立即排除相关结论，再异步重建。10 的记忆维护和 11 的检索缓存必须复用该规则，重建期间不能继续返回旧内容。
6. 对已发布的错误回复补发简短更正。若业务已开始、已成功或结果未知，保留操作记录并查询真实状态；自动办理暂停，按已有业务规则补救或交人工。

## 验收

- 把 A 的原因错记到 B 后纠正，只修改相关字段，其他补充保留。
- 错误之后已有新的正确修改，纠错不会用旧值覆盖它。
- 旧确认和未发布回复被阻止；重建前后的摘要和缓存都不会重新提供错误结论。
- 重复纠错不重复撤回；存在已成功或未知操作时不宣称业务已撤销。

## 本次交付边界

交付可重复执行的纠错服务、失效检查和补救分支。通过模拟回执覆盖已经办理的情况，不实际触发退款。

完成后在 [实施入口](README.md) 更新本项状态、提交编号和验证结果。只完成本篇范围，下一部分单独实施。

## 已实现接口

- `CorrectionService(store, authenticated_user_id, scope=...).correct(session_id, request)` 是内部纠错入口。输入包括稳定的纠错编号、原关联决定编号、原话或已有工具证据、原因、正确事项及受影响事项的预期版本。原因由服务端选择，不能让模型以“校验失败”为由绕过用户选择核验。
- 用户明确纠正时核对正确订单，订单下有多个事项时要求进一步区分。目标不明确可先传空值，恢复错误字段、暂停相关自动处理并返回待澄清问题；明确目标后用新纠错编号继续原决定。已经重关联的事项再次纠错时引用返回的 `new_decision_id`。
- 依据变更前后值和 `written_fields` 恢复错误字段。后续已经修改或重新明确确认的字段保留；正确事项已有冲突值时也保留并请求澄清，不恢复整条旧快照。通过 `TaskRepository.update` 保存同值的明确重申时，调用方需传入对应 `written_fields`。
- 原话、变更记录和业务回执不删除。错误关联标为失效，消息从错误事项移到正确事项；错误新建且没有后续有效修改、没有业务操作的事项结束。纠错和新关联各有独立记录，事务失败全部回滚，相同纠错编号重试返回原回执。
- `ProvenanceGuard.capture` 保存执行输入依赖的事项版本和关联编号。06、08、09 在保存结果、发布回复、登记业务操作前调用 `require_current`；需要锁定时，检查必须与登记动作共用事务。事项无关的纠错不使该事项的执行凭据失效。
- `DerivedData.begin/finish/read` 供 10、11 的派生记忆和检索缓存使用。生成前记录依赖，生成后和每次缓存读取时再次检查；不能给旧输入生成的结果补一个新版本以逃过检查。没有具体事项依赖的用户级摘要按纠错版本整体失效。
- 现有短期摘要已接入失效规则：删除受影响会话的派生快照并安排重建；纠错前启动的摘要任务不能重新写回。错误客服回复在原始历史中保留，但候选、摘要和检索上下文不再引用。已发送的错误回复补发简短更正，后续回复需记录事项版本或关联决定编号。
- 同一事务写入 `task_invalidation` 作业，供后续执行、回复与记忆模块及时刷新；安全检查直接查询持久状态，不依赖通知及时送达。新链路默认关闭期间，该类作业不会被旧对话 Worker 消费。
- 已开始、成功或结果未知的业务操作不修改回执、不重提。暂停受影响事项，建立真实人工工单并附上原事项、正确事项及待核实操作编号，由人工核实和补救。没有事项关联信息的旧操作按会话保守阻断；09 用 `support_operation_tasks` 明确操作所属事项后，可排除已知无关的操作。

验证入口为 `tests/test_association_correction.py`，在 SQLite 和隔离 PostgreSQL 中运行，覆盖后续字段保留、重复纠错、事务失败、多实例竞争、过期结果和缓存、摘要重建，以及已开始或结果未知的操作。业务操作使用模拟回执验证，不实际发起退款。
