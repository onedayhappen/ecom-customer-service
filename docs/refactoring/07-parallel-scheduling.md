# 07 让独立事项并行处理

不同事项可以同时查询，同一事项在多个会话中也只能有一个有效执行。

前置：完成 [06 通过统一执行入口推进一个事项](06-task-execution.md)。 总体约束见 [完整方案](../AGENT_REFACTOR_PLAN.md)。

## 改动位置

`app/runtime/chat_queue.py`、`app/runtime/outbox.py`、`app/runtime/concurrency.py`、`app/support/store.py`、`app/tasks/service.py`。

## 实施步骤

1. 把执行占位从单纯的 session 转为事项，数据库保存当前执行编号和有效版本。会话级控制继续负责重置与转人工等全局操作。
2. 同一事项跨 session 使用同一占位。重复唤醒复用待执行记录，旧 Worker 失去有效资格后不能保存、继续调用工具或发布结果。
3. 不同事项在用户、租户和全局并发额度内运行；等待用户和外部结果的事项不占执行槽位。一个慢查询不占用其他事项的整个处理机会。
4. 新消息只影响实际相关的事项。参数仍适用的查询可以继续；从 A 单改为 B 单后，A 的证据不能用于 B。
5. 有依赖的条件先完成再推进后续动作；涉及同一订单、商品或共享权益的操作记录共同业务对象。09 提交写操作时继续按业务约束保护，不能只靠事项编号区分冲突。
6. 用 Outbox 恢复尚未开始的工作；已开始的工作检查工具记录后恢复安全的只读步骤。未知业务写入始终进入核实分支。

## 验收

- 两个独立查询确实同时开始，快事项完成不等待慢事项。
- 两台 Worker 或两个 session 同时推进同一事项，只有有效执行可以提交状态。
- 过期 Worker 迟到返回、重复投递、Redis 重启后，结果不重复且不覆盖新版本。
- “有货就换，否则退”和“改地址后补发”的后续步骤不会提前执行。用隔离 PostgreSQL、Redis 和进程测试验证竞争。

## 本次交付边界

交付按事项调度与恢复能力，仍以受控只读执行验收。回复发布交给 08，业务写入交给 09。

## 已实现接口与处理步骤

实现集中在 `app/tasks/scheduling.py`，复用 06 的 `TaskExecutor`、`runtime_jobs` 和 Case 证据，不增加 Agent 或流程引擎。

1. 归属确认后的调用方使用 `TaskSchedule(store, authenticated_user_id, scope=...).enqueue(request)` 排队。`request` 沿用 06 的事项、版本、原话来源和预算。身份与业务范围由服务端传入，来源必须已经关联到该事项。数据库先保存请求，随后可用 `TaskQueue.notify(job_id)` 提醒 Worker；提醒不携带业务参数，也不授予执行资格。
2. 同一事项、同一版本的重复唤醒复用待执行、执行中或已完成的记录，跨 session 也一样；相同编号携带不同请求会被拒绝。新版本替代尚未执行的旧版本，正在执行的查询则按下述证据规则收尾。失败恢复使用新的确定编号，保留原执行的中断记录。
3. `TaskWorker.tick()` 先处理过期记录，再领取能够执行的事项。领取时在数据库短事务中核对事项版本、来源、相关会话控制、前置条件和并发额度；模型与工具都在事务外运行。Worker 内使用有上限的线程池，多个进程共用数据库的额度检查与同事项唯一约束。
4. 全局、用户和租户分别受 `TASK_GLOBAL_CONCURRENCY`、`TASK_USER_CONCURRENCY`、`API_TENANT_AGENT_CONCURRENCY` 限制，默认分别为 8、2、4。额度不足时保留待执行记录，让其他符合条件的事项继续。所有实例必须使用一致配置。直接调用 06 的受控入口也要经过数据库额度检查。
5. 等待用户、等待外部结果、暂停或结束的事项不启动模型，不占执行槽位。当前执行保存等待进度后释放槽位；后续消息或外部结果应先更新事项，再按新版本唤醒。尚未开始的工作有排队期限，总积压使用现有 `API_CHAT_QUEUE_MAX_DEPTH` 限制。
6. 查询返回和进度提交时再次检查资格。只补充原因等普通信息、且订单、明细、物流单号、目标和有效来源都没有改变时，已经发出的订单或物流查询可以保存原版本证据，供新执行在 60 秒内按相同参数复用；旧 Agent 本次执行仍中断，不生成针对新消息的答复。对象改变、取消、来源被纠正、查询过期或人工接管时不保存迟到结果。
7. 每次执行还保存相关 session 的控制版本。另一会话转人工后即使立即恢复机器人，旧执行也不会恢复资格，旧查询缓存和前置条件证据同样失效。执行结果带 `controls` 和原有 `provenance`，08 发布前须同时核实这些凭据。

## 条件与共同业务对象

调用方可以通过 `enqueue(..., dependencies=[...])` 指定最多 8 个前置条件。它是服务端构造的结构化契约，不开放给模型执行任意表达式，也不会仅凭一句自然语言就推断条件已经满足。

- 查询条件记录前置执行的 `job_id`、只读工具名、结果字段、比较方式 `eq` / `gt` 和预期值，可以指定具体证据编号。例如库存大于 0 才进入换货分支，库存等于 0 才进入退款分支。前置执行必须已有可核实结果，证据须成功、来源有效、未超过 60 秒，并且所属事项和会话控制没有改变。未知库存不等于没货。
- 操作条件记录前置执行与 `operation_id`。必须能找到归属于当前用户及前置事项的成功业务回执；模型声称改好了地址、查询成功或“已受理”都不够。09 接入真实写入后再写入事项与操作的关联。在此之前，“改地址后补发”会停在核实条件，不模拟改地址或补发。
- 前置条件在领取、调用和保存阶段重复检查。前置事项随后变化，后续执行立即失去提交资格。条件不满足的记录保持等待，超过排队期限结束；不默认选择另一业务动作。
- 只允许引用已存在的执行记录，不能引用未来执行、自己或其他用户的执行，从而避免前置关系成环。条件一旦入队不原地修改；需求改变后先更新事项，建立新版本的请求。
- 入队时记录租户、平台、店铺，以及订单、明细、商品和共享权益等共同对象。只读查询允许并行；这些记录交给 09 用于检查同一业务对象上的写入冲突，不把两个不同的事项编号当作两份独立订单。

## 退出与恢复

数据库是队列、占位和执行结果的依据。Redis 只保存有上限的唤醒提醒；提醒重复、丢失或 Redis 重启后，Worker 仍能扫描 Outbox 找到工作，执行额度也不会因此清空。模型调用继续使用原有模型资源限制。

- 尚未开始的请求在排队期限内可以重新领取，不依赖某一台 Worker 的内存。
- 已开始但超过执行期限的请求先记为中断，旧 Worker 无法继续提交。事项版本、会话控制仍相同且没有未知业务操作时，最多建立两次新的只读恢复请求。
- 恢复重新进入同一 Agent 入口，读取已保存的成功工具证据；对象、参数、来源、会话控制与时效都满足时才复用，否则重新查询。不会盲目重放旧模型调用过程、待答问题或业务动作。
- 发现执行中或结果未知的业务操作时，停止自动恢复，保留原操作状态并创建人工核实工单。明确提交成功前，不把它说成业务已完成。

受控 Worker 入口为 `python -m scripts.task_worker`。`TASK_WORKER_ENABLED` 默认关闭；启动前需要显式启用并配置隔离的数据库。已有真实流量和旧 Worker 不消费这类事项请求；本部分没有新增公开业务写入或回复发布接口。

验收入口为 `tests/test_task_scheduling.py`，与 `tests/test_task_execution.py` 联合运行。测试使用可控模型和工具返回，实际连接隔离 PostgreSQL、启动不同进程，并重启专用测试 Redis；不调用真实订单写入接口，不把这些结果记为生产模型准确率。
