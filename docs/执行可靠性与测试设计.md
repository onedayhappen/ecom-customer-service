# 执行可靠性与测试设计

## 三层保护

可靠性控制分为事项执行资格、单轮工具循环和调用资源边界。事项版本、租约与来源决定“还能否处理”；失败状态机决定“本轮是否重试或停止”；调用时限及容量决定“最多消耗多少资源”。这些机制不会修改订单规则或替用户确认。

| 模块                               | 保护对象                         | 状态生命周期                 |
| ---------------------------------- | -------------------------------- | ---------------------------- |
| `TaskRuns` / `execution_updates`   | 事项版本、控制权、来源及执行预算 | 数据库持久化，恢复继承       |
| `ReActPolicy`                      | 失败分类、有限重试与重复调用     | 当前 ReAct 循环内            |
| `ConvergenceDetector`              | 模型轮数与连续相同工具调用       | 当前执行器实例内             |
| `BoundedCalls`                     | 阻塞调用时间与线程容量           | 进程内共享容量；调用结束释放 |
| `model_budget` / `agent_partition` | 模型、用户、租户与全局额度       | 根据配置协调共享额度         |

## 工具失败状态机

[FailureClassifier](../app/reliability/failure_policy.py) 优先读取 `error_code`；旧结果才使用有限的错误文本识别。失败类别是执行信号，不能直接当作订单、支付或售后的业务状态。

| 类别                   | 当前行为                                                     |
| ---------------------- | ------------------------------------------------------------ |
| `success`              | 继续，并清零连续失败数                                       |
| `validation_error`     | 返回校验问题，允许模型改参；达到连续失败阈值时停止并请求补充 |
| `business_rejection`   | 不透明重试；阈值触发时依据已有证据收尾                       |
| `transient_failure`    | 非写工具每工具每轮最多透明重试一次；仍失败计入连续失败       |
| `evidence_unavailable` | 记录无依据，不能凭模型常识补事实；达到阈值时停止             |
| `evidence_conflict`    | 立即停止自动执行，提示人工核实                               |
| `confirmation_invalid` | 立即进入重新确认出口                                         |

默认连续失败阈值是 3。相同工具和参数的重复调用复用当前循环结果，并计入无进展控制；`read_task_context` 等可变化的进度读取有专门例外。这不是可跨事项复用的业务缓存。

非只读工具遇到瞬时失败时，策略返回 `CHECK_IDEMPOTENCY`，当前 ReAct 实现停止并提示核实，不在该分支自动查询或重放业务操作。真正的操作回执查询、未知结果恢复由 [TaskOperations](../app/tasks/operations.py) 和业务服务处理。

`needs_human` 标记或降级文字不等于已经建工单。真实交接必须经过 `handoff_to_human` 或事项结束处理中的工单事务，以实际 `ticket_id` 为准。

## 收敛与证据检查

[ConvergenceDetector](../app/harness/convergence.py) 检查轮数和连续相同工具参数，当前事项执行器将连续重复阈值设为 3，并结合执行预算限制模型步数。触发后停止继续查询，保留已取得的结果。

[reliability/evidence.py](../app/reliability/evidence.py) 对 ReAct 草稿中的部分实体和金额做证据核对，可移除没有支持的句子。它是有限的文本检查，不能证明整个回答语义正确；正式回复仍经过允许结论投影、对象校验与发布指纹检查，见 [回复组织与通知设计](回复组织与通知设计.md)。

## 阻塞调用与迟到结果

[BoundedCalls](../app/harness/bounded_call.py) 在有容量上限的后台线程运行只读或模型调用，等待超过时限时返回超时。Python 线程不能被强行杀死，因此超时调用继续占用槽位，直到函数真正结束，避免积累无限后台工作。

该包装不能用于脱离事务保护的业务写入。事项专用的准备、流程变更和提交路径不按普通读取挂到超时线程后直接放任执行。迟到读取结果可以记录为审计证据，但不能越过版本或来源屏障发布。

## 测试层次与环境隔离

| 层次             | 验证内容                                     | 入口                                                            |
| ---------------- | -------------------------------------------- | --------------------------------------------------------------- |
| 纯策略与契约测试 | 失败分类、去重、收敛、参数和实体证据         | `test_failure_policy.py`、`test_harness.py`、`test_evidence.py` |
| 服务与持久化回归 | 消息、事项、纠错、确认、接管、图片和恢复事务 | `tests/test_task_*.py` 等模块测试                               |
| 独立基础设施集成 | 跨进程领取、真实 PostgreSQL/Redis 等行为     | `--integration` 与隔离 Compose                                  |
| 前端测试         | 消息合并、时间格式、连续输入、卡片和权限交互 | `frontend/tests`                                                |
| 模型质量评测     | 实际轨迹的任务、上下文、答复与检索质量       | Agent / RAG 评测模块                                            |

[run_platform_checks.py](../scripts/run_platform_checks.py) 在导入应用前覆盖业务连接、模型凭证、图片路径与数据库配置，使用临时 SupportStore 和独立产物目录；`--integration` 标记启用专用基础设施测试。普通回归通过不能替代真实数据库并发或真实模型效果验证。部分核心业务测试还需要独立 MySQL 测试权限，具体条件由测试 fixture 检查。

[FaultInjector](../app/harness/faults.py) 可向工具和客户端注入超时、空结果、冲突等故障；[ForkRunner](../app/harness/fork_runner.py) 使用隔离子进程执行测试入口，超时终止子进程并采集资源。这两者是测试辅助能力，不是线上每次请求都会经过的进程调度器。

完整命令见 [项目 README](../README.md)。质量评测方法分别见 [Agent评测设计](Agent评测设计.md) 和 [RAG评测说明](RAG评测说明.md)。
