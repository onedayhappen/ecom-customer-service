# 业务工具设计

## 工具契约与职责

工具把模型请求转换为受约束的业务查询、资格判断或操作准备。目录中的每个工具定义名称、说明、Pydantic 参数模型、业务分组与副作用类型。模型决定需要查询什么，业务代码核验身份、金额、库存、规则和事务条件。

`contracts.py` 使用严格参数契约，拒绝额外字段与不合法的组合。用户、租户、平台权限和确认凭证来自服务端上下文，不接受模型自报身份。对象引用帮助定位资源，但不是授权凭证。

## 调用链

```mermaid
flowchart LR
    Model[模型工具请求] --> Registry[目录与参数校验]
    Registry --> Dispatch[上下文与对象校验]
    Dispatch --> Service[业务服务]
    Service --> Result[事实、来源、限制与分页游标]
```

工具发现与权限检查分开。`selection.for_task` 返回「全局白名单 ∩（任务类型工具组 ∪ 通用流程工具）」。只有筛选结果中的工具描述和参数会发送给模型，ReAct 与事项执行器同时检查调用名称。调用时仍检查当前事项、允许对象、控制版本和副作用边界。

### 全局白名单与任务筛选

`TOOL_ALLOWLIST` 配置在 API、Worker 与独立 MCP 进程中保持一致，修改后重启相关进程：

- `*`（默认）：全局允许全部注册工具，再按任务筛选。
- 逗号分隔工具名：只启用指定工具，例如 `find_orders,get_order,get_logistics,read_task_context,ask_user,handoff_to_human`。
- 空值：不向模型提供任何工具；通用工具也不会绕过全局限制。
- 未知工具名：配置校验失败，防止拼写错误静默放开能力。

任务工具组在 `app/tools/selection.py` 的 `TASK_TOOLS` 中维护，覆盖商品、库存、价格、配送、优惠券、下单、订单、物流、改址、取消、催单、售后、换货、维修、价保、发票和账号。每组包括所需的对象查询工具；通用集合是上下文查询、澄清、转人工与政策检索。

当前持久事项只有自然语言 `goal`，Worker 通常使用 `others` 标签。因此优先按当前完整目标的规则匹配工具组，复合目标取多个组的并集；没有命中时使用明确的 Intent 标签，再兜底到有限的只读发现工具与澄清。不会退回全量工具。短回答沿用事项目标；执行中接收到已提交的目标更新后重新筛选，并丢弃旧模型计划。选中工具和工具组写入 `execution.tools_selected` 追踪事件。

规则匹配不是语义分类器，未覆盖的表达可能需要澄清；可扩充 `GOAL_RULES` 或 `INTENT_PROFILES`。目标中出现否定或咨询用语也可能使相关工具可见，可见性不代表办理授权，实际操作仍需用户确认和后端校验。全局限制同时用于本地注册表、ToolManager 和独立 MCP 的模型工具入口；已创建业务操作的确认、回执核实等业务接口继续使用原有控制流程。

业务结果包含数据、来源、限制和分页信息。缺少事实、规则或外部能力时返回明确失败，不用虚构数据补齐。工具不把模型解释写成查询结果，也不替用户选择优惠券、商品或售后数量。

优惠券工具组同时包含订单发现和明细查询，支持核验“某张券为什么不能用于这笔订单”。复合目标命中会员等专用工具组后，仍保留目标中明确提及的订单／商品查询能力。参数校验失败会在 `error.validation_errors` 中返回最多 20 条字段路径和错误类型，不回传输入值、异常上下文或可能包含敏感值的错误原文。

## 副作用分类

| 分类                 | 语义                                       |
| -------------------- | ------------------------------------------ |
| `read`               | 查询、资格判断、试算或读取上下文           |
| `quote`              | 保存有期限的报价快照，不预占库存和优惠券   |
| `prepare`            | 保存待确认业务内容，不立即办理             |
| `claim` / `dispatch` | 准备领券或催单确认；实际变更仍经过确认入口 |
| `question`           | 保存待答问题并结束本轮执行                 |
| `handoff`            | 创建或复用真实人工工单                     |

“只读”描述业务副作用，不代表可无条件公开。用户私有订单、支付与持券每次都检查归属。独立 MCP 仅暴露目录中 `task_only=false` 的工具；报价、操作准备和事项流程要求可信的事项执行上下文。

## 参数与分页

- `order_ref` 绑定平台和订单号，不能假定订单号跨平台唯一。
- 商品、SKU、订单行、售后和物流引用分别校验，不能混用对象层级。
- 金额使用精确十进制；订单、商品数量与售后数量按各工具模型校验。
- 签名游标绑定用户、查询和范围。商品或轨迹的键集分页不承诺跨请求不可变快照，数据变化时可能需要重新读取。
- 返回完整数量、截断标记和继续查询引用，模型不能把当前一页当作全部记录。

### 订单、配送与购买

订单、包裹和售后摘要中的 `items_query` 是可执行的完整明细入口。原始/换货/退货包裹统一用 `get_shipment_items`；售后申请的商品行用 `get_after_sale_items`。商品明细游标与物流轨迹、售后过程事件游标分别绑定，不能互相替代。

| `find_orders`                  | `FindOrders`    | `read`     | 按文本、下单时间和状态筛选本人订单。候选包含平台、日期、商品／规格摘要、金额、状态及引用；不选择目标订单，也不将唯一命中视为办理授权。                                                                   |
| `get_order`                    | `Order`         | `read`     | 读取订单状态、金额组成、收货摘要、前 5 个购买行及支付／包裹／售后／发票的数量、记录状态与引用。返回完整计数与截断标记，不生成订单诊断或处理建议。                                                        |

| `prepare_order_update`         | `UpdateOrder`   | `prepare`  | 修改订单信息：待付款允许收货人联系方式、发票信息、备注；已支付待发货仅允许电话、备注。已发货不能修改；不修改商品、数量，不开具发票。确认后保存。                                                         |

### 事项流程

`recall_user_memory` 用于用户问历史喜好或个性化选购确需旧偏好时，由模型主动调用。只接收查询文字，身份取当前事项；返回本人 v3 记录的来源、时间、范围和不确定性，不能用于查订单状态或恢复旧授权。关闭记忆、未迁移的旧存储或读取故障返回暂不可用，正常空结果不代表从未说过。更正、遗忘与来源失效在执行、确认和回复前重查；后续新执行不自动复用记忆工具回执。

| 工具                 | 参数模型       | 副作用     | 职责                                                                                                                                                               |
| -------------------- | -------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `inspect_image`      | `InspectImage` | `read`     | 按附件 ID、具体问题和 brief/full 细节级别回看当前事项图片，返回已持久化观察及不确定性；需要可信事项上下文，图片内容不构成业务授权。                                |
| `recall_user_memory` | `RecallMemory` | `read`     | 按具体问题查询当前用户长期偏好。返回范围、来源、时间及当前/历史标识，参与执行和发布有效性校验；不是业务事实或授权。                                                |
| `read_task_context`  | `Empty`        | `read`     | 读取当前授权事项中的原话、已绑定对象、已明确选择、待补字段和历史回执／交接记录，保留来源与时间。通常首轮由执行器注入；工具不生成处理计划，历史回执不充当当前状态。 |
| `ask_user`           | `Question`     | `question` | 保存 LLM 已拟定的澄清问题和候选，更新事项为待答并结束本轮。工具不自行决定问什么；用户回答不等于业务确认。                                                          |
| `handoff_to_human`   | `Handoff`      | `handoff`  | 创建或复用当前事项的真实人工交接并返回工单编号／状态，服务端附带已有事实和原话。转交决定由明确用户请求或既定升级规则支持；不能自动承诺处理结果。                   |

换货与维修咨询分别使用 `assess_exchange`、`assess_repair`，与准备申请、确认提交共用 `RuleService.service_assessment` 的校验。查询返回 `eligible/ineligible/unknown`、规则编号／版本、原因与缺项；库存记录缺失返回未知，不能当作缺货。资格符合只说明当前记录满足申请规则，不保证处理渠道可用、库存持续可用、审核通过或免费维修。只读查询不要求渠道配置，也不调用供应商；实际准备及提交仍检查渠道并复核业务状态。

验证入口：[test_service_assessments.py](../tests/test_service_assessments.py)，覆盖无写入／无确认卡片／无渠道调用、身份范围、规则和库存变化、咨询与准备结果一致性，以及 MCP 发现和调用。

## 规模与办理边界

当前统一目录有 56 个工具，其中 `inspect_image` 与 `recall_user_memory` 属于需要事项上下文的读取流程；独立 MCP 在全局白名单允许时最多暴露 36 个非事项专用读取工具。实际可见数量还受当前配置和事项目标筛选影响。

摘要中的商品明细通过以下入口继续读取；入口的 `arguments` 从第一页开始，不复用父查询的轨迹或过程事件游标：

| 摘要                                              | 完整读取入口                                                          | 参数与分页                                                                                 |
| ------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `find_orders.purchase_summary`、`get_order.items` | `items_query` → `get_order_items`                                     | `order_ref` + `cursor`                                                                     |
| `get_logistics` 及售后返回的包裹 `items`          | `items_query` → `get_shipment_items`（新增，`Target`，只读）          | 原始、换货或退货包裹的 `target_ref` + `cursor`                                             |
| `find_after_sales.items`                          | `items_query` → `get_after_sale_items`（新增，`AfterSalePage`，只读） | `after_sale_id` + `cursor`                                                                 |
| `get_after_sale_status.purchase_items`            | `purchase_items_query` → `get_after_sale_items`                       | `after_sale_id` + `cursor`                                                                 |
| `get_my_account.contacts`、平台账号摘要           | `contacts_query`／`platform_accounts.items_query` → `get_my_account`  | `collection=contacts`／`platform_accounts` + `cursor`                                      |
| `get_invoices.issued_invoices`                    | `issued_invoices_query` → `get_invoices`                              | 开票申请 `target_ref` + `view=issued` + `cursor`；每条记录再通过 `document_query` 读取文件 |

完整读取每页最多 20 条，统一返回 `data.total`、`data.has_more` 和顶层 `next_cursor`，末页游标为空。补货计划保留按更新时间倒序、计划编号正序；商品明细按订单行编号正序。每页重验本人、平台／店铺范围和商品行归属；游标绑定用户、工具、范围和查询参数，有效期 15 分钟。实时数据发生变化时应从第一页重新查询，不承诺跨页快照。包裹记录数量不等于已发出或签收，售后申请金额不等于已退款。

商品搜索已使用商品规格存在性聚合和 SQL 分页，在同一 SKU 上核验预算与全部已知规格，避免把不同 SKU 条件拼成一个命中。优惠券工具组包含订单发现与明细依赖；未知售后状态保留未知范围，不当作已关闭或影响其他不相关商品。事务异常清理保留原始数据库错误。

集合分页与完整明细读取已落实，不再作为待开发能力。当前仍需补齐的业务设计如下，代码证据和验收条件集中在 [待改进](待改进.md)：

| 编号   | 保留的扩展设计                             | 当前边界                                                           |
| ------ | ------------------------------------------ | ------------------------------------------------------------------ |
| BIZ-06 | 真实供应商接入、原渠道退款与正式票据联调   | 仅退款、退货退款及首次开票已有本地模拟闭环，真实渠道仍需配置和验收 |
| BIZ-05 | 无已有地址的用户可通过受控地址维护完成购买 | 当前只查地址簿，订单改址不新增地址簿记录                           |

业务办理继续沿用准备、用户确认、事务重验、渠道回执；不增加绕过确认的直接退款、直接支付或自由赔偿入口。外部供应商未配置时明确不可用，协议和测试替身不证明真实渠道已经联调。

测试入口包括 [test_tool_workflows.py](../tests/test_tool_workflows.py)、[test_tool_selection.py](../tests/test_tool_selection.py)、[test_core_tools.py](../tests/test_core_tools.py) 和 [test_extended_tools.py](../tests/test_extended_tools.py)。离线便携 SQL 测试验证读取行为，MySQL 专用测试验证事务与数据库语义；不在设计文档中固化某次运行的通过数量。
