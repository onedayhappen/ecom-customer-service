# 开源评测数据集

## 选型范围

本项目的 Agent 端到端评测覆盖任务完成、对象与上下文一致性、最终回复准确性，RAG 评测另包含答案忠实度。公开数据可以提供咨询、动作和知识标注；本项目特有的事项编号、版本、来源失效和发布状态仍需补充场景。以下基于 2026-10-28 查看的一手仓库、数据卡与样例，适配判断针对本项目接口。

当前已有 [三个 Agent rubric 格式示例](../app/evaluation/agent/agent_demo.json)，用于既有静态驱动回归。新的 [Agent 评测方案](Agent评测设计.md)采用 LLM 模拟用户生成交互，公开数据主要作为用户目标、可知信息和业务情境的素材，不要求导入固定的完整对话。动态驱动、记忆对照和正式场景库待实现；下列外部数据尚未形成正式评测题集，也没有计入本项目评测结果。

## 可用来源

| 数据集 | 已有内容 | 本项目用途与适配要求 |
| --- | --- | --- |
| [τ-bench / tau2-bench](https://github.com/sierra-research/tau2-bench) | 客服任务、业务库、工具、政策及预期结果；当前 2.0 提供包含中文在内的六种语言，覆盖零售等领域 | 提取零售多目标咨询和业务状态证据，用于对象归属与回复核验；需要映射工具回执及订单状态 |
| [ABCD](https://github.com/asappresearch/abcd) | 一万多段英文人工客服对话、55 类意图、流程规范、动作及参数标注 | 补充多轮信息收集和状态表达场景；需要将原始对话、动作与槽位映射为事项和工具回执 |
| [CrossWOZ](https://github.com/thu-coai/CrossWOZ) | 约六千段中文多领域对话，包含子目标、对话行为、用户状态和系统状态 | 补充多目标切换、指代和条件更新；旅游生活服务领域需改编为电商场景，并重新审核标注 |
| [FaithDial](https://huggingface.co/datasets/McGill-NLP/FaithDial) | 英文对话历史、知识证据、原始与修正回答，以及相关标注 | 用于校准证据一致性裁判、构造有支持与无支持回答对；不是业务办理数据，也不能直接变成政策召回率标注 |

## 零售场景：τ-bench

零售政策明确要求先核实身份，只处理同一用户的事务，并在修改数据库前列明内容、获得确认。任务文件提供用户情境和 `evaluation_criteria`，适合提取订单查询、取消、修改、退换货等情境。[零售政策](https://github.com/sierra-research/tau2-bench/blob/main/data/tau2/domains/retail/policy.md)、[任务文件](https://github.com/sierra-research/tau2-bench/blob/main/data/tau2/domains/retail/tasks.json)。

其参考动作序列主要用于推导目标数据库状态，不能直接要求被测 Agent 逐调用复制该顺序。迁移时应标注最终状态、必要前置条件和禁止副作用，并允许合理的查询路径差异。[领域与评分说明](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/domains/README.md)。

当前评测可从这些任务中抽取多目标需求、订单对象和回执状态，形成归属与回复场景；实际业务提交过程不在当前 Agent 评测范围内。原库中的订单状态、商品标识和退换货规则需要显式映射，不能直接替换当前业务政策。

仓库当前版本与旧 τ²、τ³ 版本在任务和评分上已有变化。选择题集时固定 release、语言、任务划分和数据版本；改编后的结果标为项目派生题集成绩，不与原排行榜分数混用。[版本与多语言说明](https://github.com/sierra-research/tau2-bench#readme)。

## 多轮客服与中文归属

ABCD 的 `scenario` 保存客户、订单及流程信息，`original` 保存原始轮次，`delexed` 保存动作和参数等标签；仓库同时提供 `guidelines.json`、`kb.json` 和 `ontology.json`。它适合补充业务过程中的信息收集与约束场景。[数据结构说明](https://github.com/asappresearch/abcd#data)。

CrossWOZ 的子目标编号、逐轮 `user_state`、`dialog_act` 和系统查询状态可辅助构造中文归属题。其 `sys_state_init` 与最终 `sys_state` 含义不同，不能不加区分地作为用户真实约束；需要依据原话和用户状态复核。[标注说明](https://github.com/thu-coai/CrossWOZ#data)。

两者的对话和状态标签都不直接证明本项目的字段回滚、跨会话来源迁移或旧确认失效。此类问题需在移植后的消息基础上加入错误关联、后续正确修改及并发输入，再标注实际应保留和失效的内容。

## 回复证据一致性与 RAG 答案忠实度

FaithDial 可按 `history`、`knowledge`、`response`、`original_response` 组织校准样本，检查裁判是否能区分有证据支持与无支持的回答。不能假定所有原始回答都错误，应结合原数据标注；它也没有本项目的订单回执、确认状态和发布版本。[数据卡与样例](https://huggingface.co/datasets/McGill-NLP/FaithDial)。

适合先单独评估忠实度裁判，再将经过人工复核的错误模式移植到退款、物流和售后回执。不能把普通知识段落包装成已执行的业务回执，也不能用参考回答充当实际工具结果。

改编材料集中保留必要的来源与许可说明，不要求在项目中保存原始数据集或原始样本编号。正式场景使用项目自己的标识、版本和派生组，区分原始内容与新增设定；相近改编场景保持在同一数据划分，避免同时用于调试和测试。

可用 CrossWOZ 提供中文指代与目标切换情境，用零售任务与 ABCD 提供用户目标、业务对象和补问条件，用 FaithDial 校准语义判断。原始数据均不能直接作为当前 CLI 输入；用于动态用户模拟时，应整理为 [Agent 评测设计](Agent评测设计.md)中的用户已知信息、披露规则、会话计划和独立评分预期，不能把标准答案或评分要求交给模拟用户。
