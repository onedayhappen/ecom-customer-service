# 工具职责与 ReAct 调用链评审

日期：2026-10-23。配套接口见 [工具设计](TOOL_DESIGN.md)。目标为 **33 个基础工具 + 15 个扩展工具，共 48 个**；本轮调整设计文档，当前 38 个核心工具的代码尚未按新契约改造。

## 1. 全面调整的依据

`compare_products` 暴露的问题是把模型本来就能完成的分析包装成业务工具。相同问题也出现在自动选券、订单诊断、失败原因解释和下一步建议中。这次按照每个工具实际读取什么、计算什么、改变什么重新划分职责，工具数量由这些边界决定。

| 工作 | 负责方 | 可检查的边界 |
| --- | --- | --- |
| 理解用户表达、结合上下文确定查询目标、拟定澄清问题 | LLM | 多个对象是否仍有歧义取决于对话；工具返回候选事实和引用 |
| 商品比较、推荐理由、政策解释、证据归纳、选择下一步查询 | LLM | 结论引用已查事实；未知属性、未覆盖商品和推测分别说明 |
| 读取账号、商品、订单、券、物流、售后等数据 | 查询工具 | 返回来源、时间、覆盖范围、结构化事实和后续引用 |
| 检索排序、分页、关联查询、计数、分币种汇总、最新事件投影 | 查询工具内部的数据处理 | 算法和字段固定；检索相关性不能冒充商品适用性或推荐结论 |
| 优惠门槛、互斥规则、金额分摊、售后余量、状态约束 | 确定性业务服务，通过工具调用 | 输入明确，规则可追溯；缺规则返回未知；LLM 不自行核定金额或资格 |
| 保存待确认操作、领取、催单、建立交接 | 操作工具 | 对象和请求明确，有真实持久化结果与幂等回执 |
| 用户身份、权限、工具可见性、确认、最终提交、并发控制 | 服务端执行器及业务服务 | 不接受模型伪造的身份或确认；提交前重新校验 |

工具可见性按权限、真实数据能力和可信事项上下文决定。模型根据描述和观察选择工具，不增加用户意图分类器，也不以关键词固定调用路线。

### 1.1 对原设计的系统性纠正

| 设计问题 | 本次调整 |
| --- | --- |
| 为“比较商品”设置专用分析工具 | 删除 compare_products；读取各商品详情后由 LLM 选择比较维度并解释 |
| 为减少步骤，将选券和最优组合搜索隐藏在价格试算里 | estimate_purchase 只计算显式商品与券组合；默认不用券；组合选择与最终消费选择保持可见 |
| 将活动和领券模板混成一个大入口 | 分开 list_promotions 与 list_claimable_coupons，两者查询对象、资格和后续动作不同 |
| 查询摘要混入诊断、原因猜测、推荐处理方式 | 统一为事实、来源、统计及缺项；原因只返回真实记录，推理留给 LLM |
| 用一份售后概览替代所有资金查询 | get_after_sale_status 保留有界资金摘要；get_refunds 独立支持订单与售后范围的详细退款流水 |
| 唯一命中或当前上下文被当作办理授权 | 定位、用户请求和提交确认分别记录；唯一结果只说明定位情况 |
| 把 assess → prepare 当成每次办理的固定步骤 | 只读咨询调用 assess；明确办理可直接 prepare，内部执行同样的校验 |
| 将最少参数、最少调用次数当成首要目标 | 保留有用途的日期、状态、数量和分页参数；允许独立读取并行，复用仍有效的结果 |
| 每张表对应一个工具，或每个问法对应一个工具 | 按稳定业务资源与操作划分；允许固定关联摘要，保留独立明细入口 |

### 2.1 查询聚合的取舍

固定关联摘要有助于模型判断下一步，且必须有大小上限。get_order 返回前 5 个购买行、完整行数及关联引用；get_logistics 返回每页最多 5 个包裹及每包最近 3 条轨迹。需要更长历史时分页或下钻。

get_after_sale_status 返回申请与资金摘要，get_refunds 返回详细资金流水。两者共享同一事实来源，但各自满足不同的数据读取范围。工具输出不出现模型生成的“故障诊断”“最佳方案”或“下一步行动计划”。

多个商品详情可以分别读取或由执行器并行调用。以后若存在明确的吞吐瓶颈，可增加有界批量读取能力；批量读取仍返回逐对象事实，不恢复商品比较工具。

## 3. ReAct 调用推演

以下是设计验证示例，不是运行时分类标签或固定流程。每一步都取决于实际观察；已知且仍有效的信息直接复用。

| 用户表达 | 数据读取／操作 | LLM 根据观察决定什么 |
| --- | --- | --- |
| “这两个通勤用哪个好？” | 分别 get_product_details(A)、get_product_details(B)；对象不明确则先 search_products | 按用户在意的重量、续航、降噪等已有属性对比；缺失实测数据就说明，必要时澄清预算与偏好 |
| “推荐两百以内的黑色耳机。” | search_products(query=耳机, max_price=200 CNY, specs=[颜色=黑色])；候选摘要不够时查详情 | 基于候选的可验证属性给出建议；说明预算筛选为标价，不能据此声称含运费到手价不超预算 |
| “两副耳机用什么券便宜？” | 明确 SKU 与数量 → find_my_coupons 限定范围 → 必要时 get_coupon → 对少量有依据的候选组合分别 estimate_purchase | 选择需要核验的组合，比较已成功试算的金额并说明覆盖；不让用户先提供内部券编号，也不宣称全局最低 |
| “这款有活动或可以领的券吗？” | 按问题读取 list_promotions、list_claimable_coupons，可独立并行 | 解释活动与可领券的区别；用户明确领取后才 claim_coupon，获得实例后才能作为持券参与试算 |
| “我不要用券。” | estimate_purchase(items, coupon_refs=[])；省略券也具有同样含义 | 按无券试算回复；已配置的自动活动减免单列，不混称为用了券 |
| “我那张满减券怎么用不了？” | find_my_coupons 定位 → check_coupon(coupon_ref, target={items: ...})；已有未支付订单则传 target={order_ref: ...} | 根据具体失败规则解释；多张同名券或商品数量不清时补问；规则未知时不能编造原因 |
| “上个月买的耳机到哪了？” | find_orders(query=耳机, created_range=上月区间) → get_logistics(order_ref) | 根据日期、平台和商品确定是否仍需选择；用实际轨迹回答，不默认取最新一笔 |
| “一单买三件，怎么只到一件？” | get_order、get_logistics；明细截断时 get_order_items | 对照包裹和购买行解释已记录的拆包情况；缺少履约记录时不能推断丢失或责任 |
| “付款了为什么还显示没付？” | get_payments(order_ref) | 区分订单状态与渠道记录；说明有来源的错误码或状态差异，无法解释时提出核实路径 |
| “上周申请的退款怎么没到账？” | find_after_sales(created_range=上周申请区间) → get_after_sale_status；需要交易明细时 get_refunds | 区分审核、退款提交、渠道成功和银行入账；缺银行证明时说明能核实到哪一步 |
| “这单到底退了几笔钱？” | 已定位订单后直接 get_refunds(target_ref=order_ref) | 按服务端全量统计回答，并按需查看明细；不把当前页金额相加当作订单总退款 |
| “这单只退一件能退多少？先别申请。” | get_order 获取购买行，必要时补问 → assess_after_sale(kind, items=[购买行×1]) | 解释可申请金额与规则条件，保持只读；金额由服务端算出 |
| “就退这一件，买错了。” | 明确购买行、方式与数量后 prepare_after_sale(kind, items, reason=买错了) | 展示准备结果与确认卡片；不为形式先调用 assess，不声称资金已经退回 |
| “退款不用办了。” | 注入上下文不足时 read_task_context；已有申请必要时查状态 | 区分停止当前未提交事项和撤回实际申请；后者才调用 prepare_after_sale_cancel，不确定时先澄清 |
| “这单改寄公司。” | list_addresses(query=公司) → 明确地址后 prepare_order_address_change | 判断候选是否唯一且符合用户原话；完整地址由用户在确认界面核对 |
| “帮我取消这单。” | 订单已明确时 prepare_order_cancel(order_ref) | 根据准备结果解释限制或展示确认；无需为可选原因补问 |
| “发票开好了吗？” | get_invoices(order_ref)；用户要求下载且存在正式票时 get_invoice_document | 分清开票申请与正式发票，按真实文件状态回答 |
| “拆封了还能退吗？” | search_policies(query=拆封退货规则, subject_ref=商品或订单)；具体数量／方式已知且需要判断资格时 assess_after_sale | 结合条款适用范围和已查事实解释；条款原文不能直接充当审核通过 |
| “退货寄哪里？已经寄回了怎么登记？” | get_return_instructions → 用户提供真实承运商和运单后 prepare_return_shipment | 根据授权返回的地址和承运商选项引导填写；后续用 get_after_sale_status 区分物流、验货和退款 |
| “就买这款两件，寄家里，用刚才那张券。” | 规格／地址／券已明确后 quote_checkout → 有效报价后 prepare_purchase | 价格或权益变化时解释并重新取报价，按新内容确认；未接通下单能力时不能假装下单 |

“最少参数”应理解为不要求模型填入可由服务器取得的身份、当前时间、金额和规则，不要求填写无业务用途的字段。日期范围、商品数量、显式状态、分页等对正确定位必要的参数应保留。

## 4. 价格、优惠和选择的边界

### 4.1 精确计算属于工具

estimate_purchase 的输入是确定的商品、数量以及一组明确指定的本人持券。省略 coupon_refs 和传空数组都表示不用券；非法组合返回原因，不能自动替换。活动按配置好的固定优先级及互斥规则执行，规则冲突或未配置时明确返回未知。

金额计算、门槛校验、逐行分摊与后续退款应使用一致的确定性服务和规则版本。LLM 可以比较已经算好的金额，但不能自行套公式替代业务系统核定可支付金额。运费未知时只给商品部分试算；quote_checkout 接通后才生成含全部费用的可提交报价。

### 4.2 选择和推荐保持可见

LLM 根据用户偏好与券规则选择少量需要核验的方案，调用试算后解释差异。未验证的券组合不能说成可用；只检查了部分候选时，应说“已核验方案中更便宜”，不能保证最低价。某组规则未知时也不能默认其价格更高而忽略。

“最低现金支出”“优先用即将到期的券”“保留大额券给下次购买”是不同目标，应根据用户表达确定。当前目录不提供全局最优组合搜索。若以后确有大量组合的确定性优化需求，需单独约定优化目标、候选范围、搜索上限和最优性保证，再设计对应工具，不能将优化偷偷加入普通试算。

可领券模板只支持说明规则和潜在条件；只有明确领券并成功取得本人券实例后，才能将它用于正式持券试算。领取、下单与金额咨询的授权分别处理。

## 5. 返回结果与调用闭环

每个查询结果应提供：

- 对象类型、可展示标签、稳定引用及已验证的访问范围。
- 实际筛选条件、未应用条件、候选数或总数未知标记、是否截断及下一页游标。
- 结构化事实和业务来源时间；查询时间与业务更新时间分开。
- 缺字段、未接通能力及规则缺项；空记录和接口不可用分开。
- 下游工具需要的合法引用与编号，避免让模型从名称或自由文本拼接主键。

读取状态采用 ok / no_match / unavailable；规则核验另给 eligible / ineligible / unknown，并包含实际值和规则来源。一次查询没有结果不能扩大成“用户不存在任何记录”；指定范围内未匹配必须回显范围。

工具传回的数据不携带能覆盖权限或执行器行为的指令。LLM 决定是否需要继续查询、澄清或回答；系统强制执行身份、对象归属、额度和确认约束。调用超出额度时保留已经核实的事实并说明未完成范围，不能编造完整结论。

| 会员、积分 | 等级权益规则、积分台账和一致的余额计算 |
| 结算、购买 | 完整价格服务、报价快照、订单创建、库存与券占用、超时释放及独立支付流程 |

这些条件未满足时，工具应不暴露或明确返回未接通。不得以创建本地记录代替外部业务已经完成。

## 7. 落地验收要求

1. 所有工具都能说明读取的数据、执行的确定性规则或产生的系统操作；没有只包装 LLM 总结／推荐的工具。
2. 搜索候选、完整详情和后续动作之间的引用连通，模型不需要虚构内部编号；多候选不默认选第一条。
3. 商品比较仅基于查到的属性，缺失属性不补造；排序相关性不冒充推荐质量。
4. 优惠省略与空数组都不用券；明确组合失败不替换，不自动领取；金额由统一服务计算。
5. 申请、支付、退款、物流和发票状态各自可追溯，查询摘要与详细流水口径一致。
6. 翻页、搜索不完整、来源过期和规则未知均明确展示；有限搜索不声称全局最优。
7. 明确办理可直接 prepare，咨询保持只读；准备、用户确认和实际提交有独立状态及幂等控制。
8. 扩展工具只有在所需数据和处理流程接通后才进入可用目录。
9. 用第 3 节对话验证模型能按观察决定下一步；不将示例固化成分类器或脚本调用链。

本轮仅完成设计复核与文档调整。以上验收要求需在后续代码改造时执行，不能视为现有系统已经通过。
