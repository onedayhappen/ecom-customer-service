# 模型调用与提示词设计

## 模块职责

模型负责理解原话、提出事项归属、选择工具和选择答复结论。身份、状态变更、业务授权及最终发布由程序校验。主链路是一个 Agent 的多个调用阶段，不是多个 Agent 互相派单。

阅读入口是 [AgentEngine](../app/agents/engine.py)。它提供 `rewrite`、`associate`、`execute_task`、`compose_reply`，实际执行顺序由 [ConversationWorker](../app/tasks/conversation_worker.py) 和数据库中的待处理状态决定。

## 各阶段的输入与输出

| 阶段         | 模型看到什么                                         | 模型产生什么               | 程序如何使用                               |
| ------------ | ---------------------------------------------------- | -------------------------- | ------------------------------------------ |
| 查询改写     | 本批原话、必要公开对话与图片观察                     | 自然语言查询               | 仅辅助召回，失败回退原话                   |
| 事项关联     | 原始消息、候选事项、有效问题、合法订单线索           | `AssociationProposal`      | 验证逐字来源、版本与范围后提交             |
| 事项执行     | 单个事项目标、关联原话、有效历史、工具证据与图片观察 | 工具调用或执行草稿         | 逐调用校验并保存证据，不直接发布草稿       |
| 回复组织     | 最新问题、事项与允许结论摘要                         | `{"claim_ids":["…"]}`      | 按编号渲染固定正文及限制，再核验发布资格   |
| 短期摘要     | 待压缩的公开原话及已有引用                           | 带序号和逐字引用的摘要项目 | 校验原文、角色与范围后更新快照             |
| 长期记忆提取 | 当前用户公开原话及已有记忆快照                       | 分组增删改与遗忘计划       | v3 证据校验、用户版本锁与事务提交          |
| 图片识别     | 独立视觉端点接收衍生图与具体问题                     | 结构化 `Observation`       | 保存为图片观察，不升级为用户授权或业务事实 |

提示词集中在 [app/prompts](../app/prompts)，图片观察提示词位于 [vision.py](../app/media/vision.py)。修改提示词时同时查看其输出解析器；要求模型输出 JSON 不等于已经通过数据校验。

`recall_user_memory` 是事项执行中的按需读取工具，不是新增一个独立记忆 Agent；`get_shipment_items/get_after_sale_items` 是摘要之后的完整明细查询。它们与普通工具一样进入筛选、调用预算和结果校验，召回快照另绑定到后续步骤的有效性依赖。

## 客户端与请求边界

`scripts/task_worker.py` 创建 OpenAI 兼容 SDK 客户端，关闭 SDK 自动重试，外包 [LlmClient](../app/observability/llm_client.py) 后交给 Agent。`bind_scene` 为改写、关联、执行和回复标记场景，共享底层客户端但不共享各阶段的消息列表。

`LlmClient` 在实际请求前补齐提供商参数、输出上限和完整请求预算，再取得模型并发、频率及 Token 额度。处于事项执行范围时，每次实际提供商调用还消耗该执行的模型预算。追踪记录实际请求、响应、用量、耗时与异常；同步/异步适配避免重复采集或提前释放在途资源。

[runtime/model_client.py](../app/runtime/model_client.py) 提供线程安全、按需创建的进程内客户端，供记忆、摘要等路径使用。事项 Worker 则显式创建并关闭自己的客户端，不能把两者理解成所有进程共用同一个连接。

图片使用独立的 `VISION_*` 配置。视觉适配器不复用会记录完整文本请求的追踪补丁，避免 Base64 图像进入文本日志。评测角色也各自构造上下文，不能把裁判预期交给客服或模拟用户。

## 工具与提示词的关系

[selection.py](../app/tools/selection.py) 根据当前事项目标和全局白名单筛选工具；[DataPlan](../app/data_plan/builder.py) 固定本次允许的工具名，ReAct 同时用它生成 schema 和检查实际调用。`Intent` 是描述性标签，不会单独授予权限，也没有一个必经的独立意图分类模型。

用户新补充导致事项更新时，执行器重新组装上下文、重选工具并放弃未执行的旧计划。历史模型响应不能跨越新的事项范围继续执行。

## 配置与失败处理

配置由 [Settings](../app/config/settings.py) 从环境及 `.env` 读取。文本模型 API key、服务地址和通用模型名支持 `DEEPSEEK_*` 优先于部分旧字段的别名；Worker 显式使用 `deepseek_model_name`，因此仅设置旧 `MODEL_NAME` 并不能保证所有角色同步更换模型。

提供商地址匹配 DeepSeek 时，代码附加关闭思考模式的参数，以适配没有持久化 `reasoning_content` 的工具循环。其他兼容端点不自动获得该参数。

超时、无效 JSON、输出未完整结束及越权工具调用各有确定失败出口。改写可回退原话；回复选择可回退程序渲染；关联不能靠自由文本绕过来源校验；执行受总时限、调用次数及控制版本约束。详见 [执行可靠性与测试设计](执行可靠性与测试设计.md)。

## 按需记忆读取

长期记忆通过事项专用的 `recall_user_memory(query)` 按需接入。执行器复用 `TaskMemory.recall`，将实际读取的版本与来源绑定到执行、工具证据、确认和回复；模型需要时主动查询，没有每轮自动预注入。新执行不自动复用上次记忆及依赖该记忆的工具结果。评测记录真实调用，不额外注入偏好。
