# 人工接管设计

## 交接对象与控制范围

人工接管建立真实工单，同时记录被接管的事项。会话级控制与事项级约束共同生效：某事项在会话 A 被接管后，会话 B 的机器人也不能绕过该约束办理。

用户主动转人工或执行器调用 `handoff_to_human` 后，经 SupportStore 事务保存工单、控制版本、事项关联与停止自动执行。模型仅输出“已转人工”不构成交接。

`task_handoffs` 以工单与事项共同去重，保存用户、交接版本、快照、接管和释放时间。

## 交接内容

| 内容           | 来源与用途                           |
| -------------- | ------------------------------------ |
| 目标和待答问题 | 最新事项，说明用户仍需解决什么       |
| 原始消息       | 会话、序号、时间与原文，保留更正关系 |
| 已核实事实     | 有效查询与来源                       |
| 业务操作       | 原操作编号、状态和真实回执           |
| 公开人工沟通   | 保留说话人与来源，区分承诺和业务结果 |

内部备注和私有核实记录只供授权客服读取，不进入客户会话或模型上下文。客服承诺不是自动获得的赔付、改价或权益授权。

当前交接从新版回执 `data` 按字段白名单生成有界的 `observed_evidence.facts`，保留多订单候选、金额与币种、包裹商品行、售后及退款汇总的嵌套范围。每条查询附带参数范围、来源事件、事项版本、读取时间、同步时间和查询限制；迟到或依据已失效的回执不进入事实摘要。旧订单和物流回执仍可作为历史查询读取。

候选记录、历史业务查询、准备操作和真实业务操作回执分别标识，提交申请不等于退款到账、履约或开票完成。图片通过当前有效的附件与观察关系单独展示摘要、时间和不确定性，不构成业务事实或授权。分页、截断、缺项和未支持的摘要明确提示，不能将缺字段解释为没有真实业务记录。适配与回归入口见 [待改进](待改进.md) 的 `RUN-03`。

## 接管与在途操作

接管使未开始执行、未使用确认和未发布旧回复失去资格。已经发出的业务操作保留记录并查询实际结果，不能因为工单创建就宣称操作已撤销。

接管和操作开始登记在统一控制规则下竞争：控制先改变则阻止开始，业务已取得提交资格则保留真实结果并交人工核实。

## 工单权限与更新

客服角色由数据库中的 `support_staff` 授权，不能由注册参数、前端或模型指定。队列领取、转派、停用和管理员核实各有权限检查。

负责客服或管理员通过 `POST /api/v1/support/tickets/{ticket_id}/tasks/{task_id}` 更新允许字段。请求包含唯一编号和事项版本，相同请求重试返回原结果，版本竞争只有符合当前版本的一次修改成功。

更新事件记录操作者、角色、字段变化和来源。不能写入权限结论或任意赔偿金额；已有执行中、未知或成功业务操作时不能把事项改绑到另一订单。

## 恢复机器人

标记工单解决与恢复机器人是两个动作。恢复需要明确事件，并检查：

1. 原事项是否还有其他有效工单接管。
2. 是否存在执行中或结果未知的业务操作。
3. 人工最新更新、公开对话与实际回执是否可读取。
4. 需要继续处理的原消息是否仍保留。

最后一个接管释放后增加事项版本，清除旧追问并重新安排执行。外部申请编号与已提交结果继续保留，旧确认不恢复，已成功操作不重放。

活动工单可以读取最新交接；释放后历史快照固定，旧客服不能通过历史工单查看后来新增的信息。
