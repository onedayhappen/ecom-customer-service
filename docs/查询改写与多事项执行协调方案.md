# 查询改写与多事项执行协调方案

更新日期：2026-10-26。

本文总结查询改写、事项关联、运行中补充消息及执行协调的设计方案。第 9 节记录本次实现及其边界；流程正确性仍需结合测试和实际运行验证。

## 1. 目标与处理单位

用户可以连续发送消息，每条消息都可能包含多个事项。系统需要持续理解这些消息，把变化送到正确事项，并避免按照旧需求执行操作或发布回复。

区分三个层次：

| 层次 | 职责 |
| --- | --- |
| 消息与批次 | 保存原话，确定一次改写和关联处理哪些输入 |
| 事项 | 管理目标、条件、版本、执行状态及业务证据 |
| 回复与交互 | 向用户说明一个或多个事项的结果、进度或待补信息 |

一条消息可以影响多个事项，一个事项可以由多条消息共同补充。批次不等于事项，也不等于一次完整交互。执行器属于事项，而不是属于消息 A 或消息 B。

## 2. 总体流程

```text
原始消息逐条入库
    ↓
领取待处理消息，固定批次范围
    ↓
查询改写：保留全部诉求、对象、条件和关系
    ↓
事项关联：产生一个或多个关联决定
    ↓
更新事项集合，并向对应事项记录更新
    ↓
各事项分别执行，在步骤边界读取新变化
    ↓
检查结果是否仍有效，协调正式回复
```

消息理解与事项执行可以并发。某个事项等待模型或工具返回时，后台仍能理解用户追加的消息。

## 3. 消息批次、查询改写与事项关联

### 3.1 消息批次

- 每条原始消息保留消息编号、内容和时间，不被改写结果覆盖。
- 领取时，将已经到达的待处理消息按顺序组成有大小上限的批次；领取后到达的消息进入下一批。
- 同一批的改写和关联使用相同的来源消息范围。记录改写使用的历史范围，避免把后到消息悄悄混入本批。
- 限制同一会话的在途批次数量；合并尚未领取的消息，不为每条追加消息无限创建模型请求。

### 3.2 查询改写

输入为本批用户原话，以及必要的近期用户原话和客服实际回复，尤其是提问及选项。之前的改写结果不作为主要历史依据。

只输出自然语言，不输出 JSON，不选择事项，不执行操作：

- 修正明确错别字，补全有依据的指代和省略。
- 保留所有诉求及其对应对象，不能强行合成一个目标。
- 保留否定、疑问、条件和前后修正；不能把“能不能退款”变成“立即退款”。
- 无法确定的内容保持不确定，不猜测订单号等身份信息。
- “换不了再退”是条件关系，不能变成同时执行换货和退货。

原话已经清楚时可以原样保留。改写超时、报错或输出为空时，记录失败并使用原话继续关联。

### 3.3 事项关联

用原话和改写辅助检索候选事项，再结合历史及最新事项状态，形成结构化关联决定。原话始终是事实依据，改写不能独立提供操作授权。

每个决定需要关联来源消息和原文依据，表达新增、补充、修改、停止、澄清或无实质变化等语义；具体映射到现有输出契约，不在本文另定义一套字段。

同一批可以产生多个决定，也可以用多条消息共同更新一个事项。不能机械地按句号拆分事项。

缺订单号等办理信息不一定意味着事项归属不清，可以先建立事项再补问。只有某个诉求存在歧义时，优先澄清这一部分，其他明确且独立的事项仍可推进。

## 4. 流水线并发与顺序

```text
批次 A：改写 A → 关联 A → 更新若干事项 → 各事项执行
批次 B：          改写 B → 关联 B → 更新若干事项
```

- 同一批必须先改写再关联。
- 可以让“关联 A”与“改写 B”重叠。B 改写只解释原始对话，不依赖 A 尚未提交的事项结果。
- 同一会话的事项关联按批次顺序处理；关联 B 时读取 A 提交后的最新事项状态。仅对提交结果排序而让模型都读取旧状态，不足以保证正确。
- 事项执行可以与消息理解并发。不同事项能否并发，还要检查业务对象冲突和前置依赖。
- 如果同一事项可以跨会话出现，还需通过事项版本及提交校验协调跨会话更新，不能只靠会话内顺序。

批次之间的改写重叠由 `QUERY_REWRITE_PREFETCH` 控制，默认开启。关闭时仍保留改写和关联，只取消提前改写；消息理解与事项执行仍可并发。

## 5. 执行中接收新消息

### 5.1 新消息尚未关联

新消息可能影响当前会话中的多个事项，不能提前认定它只是新增诉求或只修改一个事项。

第一版采用保守且简单的边界：允许已发出的模型或工具调用返回，保存实际结果；相关执行暂缓启动下一步，正式回复暂缓发布。消息改写和关联继续推进，不等待所有在途调用结束才开始理解。

消息持续追加时，优先合并待处理输入并控制在途工作，避免不断重新执行。不能用“等够几秒”作为忽略未处理取消消息、直接提交业务操作的依据。

### 5.2 关联后，按事项处理更新

为各事项记录可追踪的更新，执行器在模型调用前、每次工具调用前、结果保存后及正式回复发布前检查。

| 事项变化 | 处理方式 |
| --- | --- |
| 无实质变化 | 继续执行 |
| 补充信息或增加条件 | 更新上下文，重新判断下一步，必要时重新预检 |
| 修改目标 | 作废未执行的旧计划，保留有效结果，按新目标规划 |
| 修改订单等处理对象 | 重新确定范围，旧对象证据不能直接用于新对象，必要时重建执行 |
| 要求停止 | 停止后续操作，核实并记录已发出的操作结果 |
| 新增独立事项 | 新事项进入调度，不让原执行器顺带办理 |

模型请求发出后不能中途插入新消息。它返回时若事项已变化，应先处理变化，不能直接执行旧响应中的剩余工具计划。一次模型响应包含多个工具调用时，每个调用前都要检查。

不要求每次更新都从头执行，也不追求必须保住同一个协程或循环。能否安全复用事实、是否需要重新规划，比保留执行现场更重要。

### 5.3 防止旧执行与重复操作

- 同一事项同时只有一个有效执行者，通过执行归属、租约和版本检查保证。
- 不同事项对同一订单的冲突操作需要协调，不能仅凭事项 ID 不同就同时执行。
- 在发起业务操作和发布回复前，将新消息检查、版本检查与操作准入协调起来，避免检查后又按旧状态提交。
- 已发出的业务操作可能无法撤回；保存其实际结果，但不能让旧结果覆盖新事项状态。
- 对结果未知的操作先核实，不能直接重试。已成功的操作不能因重新规划而再次提交。
- 单批多事项的关联提交需具备事务一致性和幂等性，重试不能重复创建事项或追加同一更新。

## 6. 状态存储与恢复

复用已有工具证据，不另建一套独立维护的工具结果存储。

| 位置 | 职责 |
| --- | --- |
| 数据库 | 原始消息、批次及关联结果、事项与版本、执行记录、工具证据和业务操作结果 |
| 进程内存 | 正在执行的消息上下文、局部循环状态，供正常运行时继续使用 |
| Redis | 沿用唤醒通知、额度协调和缓存；确有需要再保存临时检查点，不作为唯一业务事实来源 |

需要补充的执行信息包括：事项 ID、执行 ID、采用的事项版本、已消费更新的位置、已完成及在途调用、已消耗的调用和重试预算。

第一版不要求任意位置精确恢复。进程重启后，从最新事项和有效证据重新组织下一次模型请求；不能只恢复内存对话而遗漏已发生的业务操作，也不能把预算全部清零。

若后续引入 Redis 检查点，优先引用已有证据 ID，保证引用有效期。检查点丢失时回到数据库重建执行。模型上下文摘要不能代替完整的操作记录。

## 7. 回复、日志与示例

回复可以汇总多个事项当前已取得的结果，不必等待全部事项结束。明确说明每个事项的结果、等待状态或待补信息，不重复发布已经回答过的结果。

日志保持每个会话一个文件，每行对应一次以正式客服回复为边界的交互。一个交互可以包含多条用户消息、多个处理批次和多个事项。处理中尚未回复的交互保留处理中或失败状态；进度提示不作为正式回复边界。

日志记录改写、关联、工具调用、更新消费、重新规划、异常回退及最终回复，通过消息编号、事项 ID、执行 ID 串联。不把一次模型调用或一个批次误当成一次完整交互。

示例：

> A：耳机我要退货，另外查一下键盘物流。
>
> B：耳机改成换货，键盘不用查了，另外鼠标能开发票吗？

| 事项 | A 关联后 | B 关联后的处理 |
| --- | --- | --- |
| 耳机售后 | 处理退货诉求 | 更新为换货，检查已发生的操作，作废未执行的退货计划 |
| 键盘物流 | 查询物流 | 停止后续查询，保留已返回结果 |
| 鼠标开票咨询 | 尚未出现 | 创建或关联咨询事项，查询能否开票，不直接提交开票申请 |

## 8. 主要后端技术

优先沿用现有技术栈，实现阶段调度和状态协调，不为此引入新的大型任务框架。

| 技术或机制 | 模块用途 | 实施选择 |
| --- | --- | --- |
| Python / FastAPI | 接收消息、查询状态、推送回复 | 沿用现有接口层 |
| 后台 Worker / `ThreadPoolExecutor` | 并发处理模型和工具的网络等待 | 沿用现有有界线程池，增加阶段调度；并发不要求全部改成协程 |
| PostgreSQL / 事务 / 条件更新 | 批次顺序、事项更新、执行记录与幂等提交 | 作为可靠状态来源，扩展现有任务和事项机制 |
| Redis 通知与限流 | 唤醒 Worker，协调调用额度与必要缓存 | 通知是处理提示，实际领取和执行权由数据库确认 |
| 执行状态机 | 区分待执行、运行中、等待更新、失效、完成等语义 | 与现有状态契约对齐，不混淆技术等待与用户要求暂停 |
| 版本、执行租约、幂等标识 | 拒绝旧结果，防重复领取和重复操作 | 复用并补齐现有机制，租约过期后旧执行仍需被版本或归属检查拦截 |
| ReAct 步骤检查点 | 消费事项更新、保存结果、重新规划 | 本次主要新增能力，检查点不等于另一套完整工具日志 |
| 统一模型调用额度管理 | 改写、关联、ReAct 共享容量控制 | 同时控制并发、频率及 Token 预算，超额排队，不无限重试 |

`asyncio` 是后续可选的执行方式。若迁移，需要异步客户端或同步调用适配，不能只给阻塞函数加 `async`。跨 Worker 的协调不能依赖单进程的 `Event` 或内存锁。等待模型和工具时不长期占用数据库事务或行锁。

## 9. 本次实现与运行边界

本次复用既有数据库表及线程池架构，没有新增数据库迁移或任务框架。主要代码分工：

- `app/tasks/intake.py`：消息接收和批次领取。
- `app/agents/query_rewrite.py`、`app/prompts/query_rewrite.py`：自然语言改写及输出检查。
- `app/tasks/candidates.py`：先固定原始对话范围，再使用原话和改写检索候选。
- `app/tasks/association.py`：改写保存、失败回退，以及多事项关联、校验和原子提交。
- `app/tasks/rewrite_ahead.py`：有界提前改写，只缓存输入快照与结果，不拥有消息处理权。
- `app/tasks/conversation_worker.py`、`app/tasks/scheduling.py`：Worker、线程池和执行调度。
- `app/execution/react.py`、`app/tasks/execution.py`：步骤检查、等待关联、更新上下文和重新规划。
- `app/tasks/execution_updates.py`：消费已提交的关联更新、推进执行版本、保存调用预算。
- `app/tasks/execution_store.py`：工具证据及执行记录，已有结果优先复用。
- `app/tasks/replies.py`：回复协调与有效性检查。
- `app/runtime/task_queue.py`、`app/runtime/budgets.py`：Redis 唤醒通知及额度控制。
- `app/observability/interactions.py`：沿用交互日志，记录改写、提前改写、等待输入、版本更新和重新规划。

实现细节与边界：

1. 改写结果及原始历史快照保存在关联任务的 `runtime_jobs.payload.query_rewrite` 中；重试复用结果，租约恢复保持原批次范围。错误、超时、空输出或结构化输出回退到原话。
2. 每个 Worker 最多使用两个提前改写线程，每个会话只保留一个待消费的提前改写批次。只有原话、历史和范围均一致时才复用结果；不一致时走正常改写。跨 Worker 不依赖该缓存，可能重复进行只读改写，但不会重复提交事项。
3. `association_decisions` 及其事件作为事项更新记录；运行任务的 `provenance.tasks` 作为已消费版本。不新增另一套事项更新表。
4. 同一执行中的重新规划保留调用次数、循环限制和总截止时间。`runtime_jobs.payload.usage` 保存模型、工具和进度调用计数；Worker 恢复继承计数，沿用最多两次恢复及每次执行时限。
5. 新消息未关联时，沿用现有用户范围的输入屏障，可能同时暂缓该用户其他机器人会话中的执行和正式回复；不影响其他用户。等待发生在线程中，不持有数据库事务，并受执行截止时间约束，超时进入现有中断/失败处理。
6. 只有可核对到已提交关联决定的版本变化，才能由原执行消费并重新规划。人工接管、来源失效、手工纠错和无法解释的版本变化走原有中断路径。
7. 新需求使旧提问或外部等待失效时，清除旧等待并重新评估。没有字段或目标变化的普通补充可保持版本；明确重申字段仍保留新的来源证据，供后续纠错使用。
8. 迟到工具结果仍保存到 `task_tool_result`，标记 `late=true`，不直接进入当前证据或回复。原执行仍有效时保存的结果继续按对象、时效和来源有效性检查复用。
9. 订单等身份字段的切换继续受原有关联校验限制：不能通过普通更新悄悄换单，应澄清、纠错或建立独立事项；不会为了运行中引导绕过已有业务确认和操作锁。

测试入口：

```powershell
.\.venv\Scripts\python.exe scripts/run_platform_checks.py tests/test_query_rewrite_updates.py
```

## 10. 验收重点

- 一条或多条消息同时更新多个事项，信息不会串到其他事项。
- 补充信息、修改目标、修改对象、条件依赖和停止要求均按原意处理。
- 新消息在模型等待、工具等待、多个工具之间及回复发布前到达，旧计划不会绕过检查。
- 独立事项可继续推进，冲突操作和依赖事项不会错误并发。
- 关联重试、Worker 重启、租约过期及 Redis 通知丢失，不造成重复创建或重复业务操作。
- 工具成功、失败、结果未知及迟到返回均有可追踪记录。
- 持续追加消息和模型限流时工作量有上限，预算不会因重新规划不断重置。
- 日志能从一次正式交互追溯到每条原话、各个事项更新和实际执行结果。
