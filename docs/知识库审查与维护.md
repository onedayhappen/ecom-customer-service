# 知识库审查与维护

## 模块职责

知识正文位于 `app/rag/knowledge`，描述本项目服务流程、工具行为与适用条件。本文解释正文如何与代码关联、审核记录如何校验，以及内容变更怎样进入索引；运行时检索与发布命令见 [政策检索设计](政策检索设计.md)。

业务资格、金额和资源占用由可执行规则判断，见 [业务规则与权益计算设计](业务规则与权益计算设计.md)。知识正文用于解释，不直接授予办理权限。

## 正文、侧文件与审核记录

| 文件 | 用途 | 校验入口 |
| --- | --- | --- |
| `app/rag/knowledge/<名称>.md` | 按完整二级章节组织的知识正文 | `policy_chunks` |
| 同名 `<名称>.policy.json` | 来源、版本、访问范围、适用时点及审核状态 | `PolicyMetadata` |
| [knowledge_review.json](knowledge_review.json) | 正文及元数据摘要、逐篇源码依据、审核范围 | `verify_review` |

自编正文使用受限 `repo:app/rag/knowledge/<名称>.md` 来源，切分时核验来源文件名与实际正文相符。标识不用于任意文件读取或网络请求。通用服务说明按咨询时点选取；历史订单资格另查其可执行规则，不能直接继承正文中的一般描述。

审核记录的顶层包含 `version`、`reviewed_by`、`review_scope`、`scope_basis`、`documents` 和 `digest_format`。`documents` 按正文文件名索引，各项保存 `source_id/version`、正文与侧文件摘要，以及 `review_basis` 中源码路径到摘要的映射。记录核对的是项目实现一致性。

`scripts.verify_policy_knowledge.verify_review` 依次检查：

1. `digest_format` 必须为 `utf8-lf-sha256`。
2. `documents` 与知识目录中的 Markdown 文件集合一致。
3. 每篇正文和侧文件摘要匹配，来源编号及版本一致。
4. 每项源码依据仍存在且摘要匹配。

摘要通过 UTF-8 文本读取后计算 SHA-256，Windows/Linux 换行归一化；纯换行变化不导致内容过期。正文、范围或代码变化则要求重新核对含义并更新审核记录。

## 内容变更流程

1. 沿映射定位工具契约、任务筛选、服务实现、数据表与前端入口，确认用户实际可用的流程。
2. 编写适用对象、前置条件、查询或办理步骤、确认要求及结果含义。动态价格、库存、会员额度、活动时间和配送报价由工具取得，正文解释其含义与计算依据。
3. 检查二级章节完整性。正式切分会将文首限定语附到各章节，章节超长时先编辑拆分，保持条件与例外相连。
4. 核对同名侧文件的来源、版本、范围和时间依据，再更新审核记录。涉及可执行资格时，同时检查业务规则的 RAG 来源与版本关联。
5. 运行审核摘要校验、知识切分预检与相应工具测试；在部署环境发布并验证正式索引。

## 索引与验证职责

普通索引由 `update_index` 同步内容哈希清单；正式 `PolicyIndex` 使用版本化发布、活动指针与来源撤回记录。普通索引同步成功不等于正式政策工具已切换。

删除正文后，普通索引需要同步；正式索引需要发布新版本，并按来源有效性决定是否撤回旧版本。历史订单规则仍按自己的适用时点核验，不能只删除磁盘文件改变历史解释。

`python -m scripts.verify_policy_knowledge` 先校验审核记录，再检查已发布索引与正文一致，并逐条执行脚本 `QUERIES` 中的主题检索、目标命中和证据重验，同时验证无关问题被拒绝。它使用配置的真实 Embedding 与索引，运行前需完成对应环境的发布。
