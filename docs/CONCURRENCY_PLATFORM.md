# 并发平台改造与验收

分支：`codex/concurrency-platform`。基线：`35f5232`。范围保持为可靠入队 Outbox、故障恢复、队列监控、真实多实例测试、事件通知与推送、分级限流与资源隔离、数据库查询与锁优化、模型与检索服务扩展。

## 设计

1. PostgreSQL 是会话、任务执行记录和投递意图的事实来源。用户消息、任务路由与待投递 Job 在同一事务提交，202 表示已持久化受理。Redis 只承担有界调度和通知，不作为唯一结果存储。
2. 独立 dispatcher 使用有期限的领取和 `SKIP LOCKED` 分批投递，不在数据库事务内等待 Redis。Redis 提交成功、DB 确认前崩溃时可重复投递。执行占位与控制版本拒绝重复或过期执行。
3. 独立恢复循环处理未投递、已投递未开始、运行超时与结果落库。未开始任务可重新投递；已经开始的任务绝不盲目重跑。未知写入进入人工核实，取消和人工接管优先于旧执行。
4. 事件同事务写入通知 Outbox，按会话合并唤醒，Pub/Sub 仅通知“有更新”。API 实例共享订阅器，连接使用有界唤醒信号；数据库游标补拉修复通知丢失。定时兜底、撤权检查、连接额度、重连抖动和慢客户端边界均需验证。
5. 区分入站速率、Agent 并发、模型并发/RPM/Token 预算与检索资源。控制操作和人工消息不等待 Agent 执行额度。用户/租户身份来自服务端，限流失败可解释且不会产生半提交任务。
6. 只读事务使用一致快照，不获取会话排他锁；状态更新保留行锁。任务查询仅载入未完成记录和有界历史；历史工单使用持久化快照。池预算、归档与维护任务独立于消息热路径。
7. 模型支持独立 OpenAI 兼容服务部署及共享调用预算；检索提供受保护的独立 HTTP 服务与远程客户端，保留本地开发模式。部署、健康检查、资源额度和故障测试必须覆盖跨进程路径。

## 验证约束

真实集成使用专用数据目录、端口、数据库名和 Redis namespace，不读取或修改现有业务数据库。不对共享 Redis 使用 FLUSHDB。模型/订单故障注入使用明确标记的替身服务；其结果只能证明协议和资源控制，不能声称真实模型质量或硬件容量。

负载报告必须区分测试硬件、连接数、到达速率、执行耗时、P95/P99、错误率和业务不变量。不以 SQLite 测试替代 PostgreSQL 行锁/多进程验证，也不以单次绿色测试替代故障恢复证据。
