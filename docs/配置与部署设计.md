# 配置与部署设计

## 配置加载与装配

[Settings](../app/config/settings.py) 通过 Pydantic Settings 加载环境变量与 `.env`。配置对象在模块导入时创建，修改环境后通常需要重启相关进程。数据库放量状态独立于进程配置，不能仅修改 `.env` 就替代跨实例控制。

| 配置组       | 关键项                                                                                                                              | 使用边界                                                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 身份与浏览器 | `API_JWT_SECRET`、`API_AUTH_BACKEND`、`AUTH_COOKIE_*`、`CORS_ORIGINS`                                                               | API 验签、登录会话与浏览器凭证                                    |
| 支持库       | `SUPPORT_DATABASE_URL`、`API_SESSION_POSTGRES_DSN`                                                                                  | 前者非空时优先；保存会话、事项及 v3 记忆                          |
| 业务库       | `ORDER_DB_DSN`、`BUSINESS_DATA_KEYS`、`BUSINESS_DATA_KEY_VERSION`                                                                   | MySQL 事实、事务、地址与私密参数加密                              |
| 模型         | `DEEPSEEK_API_KEY/BASE_URL/MODEL_NAME`                                                                                              | Worker、摘要与记忆等文本调用；旧别名限制见模型文档                |
| 图片         | `VISION_*`、`MEDIA_*`                                                                                                               | 独立视觉端点、私有目录、容量和识别任务边界                        |
| 政策检索     | `EMBEDDING_*`、`LOCAL_EMBEDDING_MODEL_PATH`、`CHROMA_*`、`RETRIEVAL_*`                                                              | 模型与发布索引必须匹配，本地或远程检索                            |
| 并发与通知   | `API_CONCURRENCY_REDIS_URL`、`TASK_*CONCURRENCY`、`MODEL_*`                                                                         | 共享额度、执行容量、队列与通知                                    |
| 记忆与摘要   | `MEMORY_ENGINE`、`MEMORY_ENABLED`、`SHORT_TERM_*`、`CONTEXT_*`                                                                      | v3/兼容引擎、派生上下文和完整请求预算                             |
| 处理方与观测 | `COMMERCE_PROVIDER_MODE`、`COMMERCE_PROVIDER_CONFIG`、`COMMERCE_SIMULATOR_*`、`COMMERCE_INVOICE_ROOT`、`OBSERVABILITY_*`、`AUDIT_*` | 外部办理、票据文件、追踪与审计                                    |
| MCP 读取     | `MCP_ENABLED`、`MCP_SERVER_URL`、`MCP_SERVICE_TOKEN`、`MCP_CONTEXT_JWT_SECRET`、`MCP_CONTEXT_TOKEN_TTL_SECONDS`                     | 默认事项 Worker 的远程业务读取，签名绑定身份/范围；事项流程仍本地 |

`MEMORY_STORAGE_BACKEND`、`MEMORY_POSTGRES_DSN` 等保留兼容存储配置；v3 的实际权威存储是 SupportStore，不能仅改旧记忆路径就迁移 v3 数据。旧订单缓存和连接池配置也不控制所有新业务工具，见 [业务数据访问设计](业务数据访问设计.md)。

## 启动与迁移

1. MySQL 版本迁移建立账号、商品及业务结构；数据导入脚本另外执行。
2. `SupportStore.initialize` 初始化支持库及模块 schema，数据库放量状态决定哪些用户自动处理。
3. API 启动校验身份密钥、占位配置及启用 MCP 时的服务密钥，再装配支持库、连接池、观测和路由。
4. 事项、通知、记忆、交易和维护进程分别启动；API 健康不等于后台工作已推进。
5. 政策检索需要已审核元数据及已发布索引；图片识别需要单独配置视觉端点。

API 的运行配置检查允许未配置文本模型 key 的只读/人工场景，但事项 Worker 的模型调用仍需要有效模型服务。各进程没有一个统一的“所有依赖都已可用”探针。

事项 Worker 启动同样调用配置校验。MCP 默认关闭，开启后需启动可达的 MCP 服务并在两端配置一致的服务和用户签名密钥；不能把镜像内 `localhost:9123` 当作另一个容器的服务地址。首次发现失败可使用本地同名实现，但已发送的远程调用不因重连失败而改为本地重放。

## 本地与容器部署

[docker-compose.yml](../docker-compose.yml) 装配 PostgreSQL、Redis、MySQL、API、Nginx 和各后台进程；可选服务按 profile 启动。容器通过服务名互访，宿主机 DSN 使用映射端口，不能混用 `localhost` 与容器服务地址。

持久目录主要有 `.docker-data/app`、`.docker-data/logs` 及各数据库目录；本地模型挂载为只读。API 和事项 Worker 必须访问同一图片目录，保留 `/app/data` 下的 RAG 发布清单、向量索引和私有附件。数据库备份本身不包含原图、票据文件、模型或密钥。

[Dockerfile](../Dockerfile) 将 `migrations/mysql` 复制到镜像的 `/app/migrations/mysql`，与迁移脚本读取路径一致。Compose 在 MySQL 健康后启动 `order-init`，执行业务数据库迁移；迁移成功后启动后端，失败则阻止依赖服务继续启动。迁移脚本按 `schema_migrations` 中的版本记录跳过已执行步骤。新增迁移需要新增 SQL、登记脚本版本并重新构建部署镜像；修改数据库中的业务数据无需重建镜像。空库迁移与启动验收见下文。

前端由 Vite 单独运行或构建为静态产物；当前后端镜像不会自动打包前端。Nginx 负责 API 转发，并对 SSE 关闭缓冲。

2026-10-30 已在 Docker Desktop Linux 容器中完成完整前后端镜像构建与隔离部署验收：依赖一致性、全新 MySQL 的 12 个迁移、重复迁移及业务哨兵数据保留、迁移失败阻止后端启动、API 健康与就绪、前端和网关访问、各 Worker 启动、共享票据目录与加密密钥，以及服务重启恢复。验收入口为 [check_container_deployment.py](../scripts/check_container_deployment.py)，使用真实 Compose 服务定义、独立数据卷和离线模型配置，结束后清理本次容器与数据卷；这项验收不包含真实模型效果和供应商联调。

MySQL 健康检查通过 TCP 使用应用账号执行目标数据库查询，避免初始化临时服务或认证失败被 `mysqladmin ping` 误判为可用；PostgreSQL 也通过 TCP 检查，避免初始化临时 Unix socket 被提前判定就绪。迁移 `--check` 缺少版本时返回退出码 1，全部已应用时返回 0。

运行 `python scripts/check_container_deployment.py` 可复验。Docker Hub 镜像代理不可用时加 `--public-mirror`，通过 Dockerfile 基础镜像参数使用 Docker 官方镜像的公共 ECR 分发地址；基础镜像参数不改变安装的完整项目依赖。部署到其他主机时仍需核对该环境的配置、卷权限和密钥，不能沿用测试临时密钥。

`COMMERCE_PROVIDER_MODE` 已支持 `disabled`、`simulator` 和 `http`。留空时兼容旧配置：存在非空 `COMMERCE_PROVIDER_CONFIG` 选择 HTTP，否则禁用。模拟器只处理演示订单的仅退款、退货退款和首次开票；真实渠道失败不会自动切换到模拟模式，已登记任务的渠道模式也不能随配置切换。

`COMMERCE_SIMULATOR_SCENARIO` 支持 `success`、`reject`、`delay`、`lost_response`；`COMMERCE_SIMULATOR_STEP_SECONDS` 控制推进间隔，场景和间隔在模拟处理方首次受理时保存。`COMMERCE_INVOICE_ROOT` 为私有票据根目录，API 与交易 Worker 必须挂载同一持久目录。迁移版本 `012_local_provider` 建立模拟状态和演示来源字段，不会自动为历史申请补建渠道任务。演示数据初始化、启动命令与失败恢复见 [售后与开票本地演示闭环方案](售后与开票本地演示闭环方案.md)。

## 扩容与恢复

各副本共享支持库、业务库和协调 Redis；连接池是进程内资源，副本数量会扩大总连接数。共享锁与版本检查保护提交，进程内线程池不提供跨实例唯一性。

嵌入式 Chroma 和当前本地图片目录不自带跨主机同步。多机图片/索引分发的设计目标与实现边界见 [待改进](待改进.md)；不能把复制应用进程当作已经完成存储扩容。

`/health`、`/ready`、进程心跳和积压指标分别检查存活、支持库放量版本及后台状态。放量暂停仍允许历史和人工服务；恢复前核实未知业务操作，不重放写入。运行命令统一见 [项目 README](../README.md)，控制与观测见 [运行与可观测性设计](运行与可观测性设计.md)。
