# 电商客服 Agent 重构实施方案

本文件规定完整链路和共用约束。代码实现按 [分步实施入口](refactoring/README.md) 中的 14 份小方案逐次推进，每次只实现一部分。

## 一 目标与核心规则

采用单 Agent 架构，复用同一套模型、提示词和工具执行逻辑。独立事项可以并行执行，不引入多 Agent 分工、互相评审或长期运行的事项流程。

1. 消息持续接收并逐条保存，不依赖判断用户是否已经说完。
2. 结合最近对话、待答问题、历史事项和必要的订单查询，判断消息属于哪件事。
3. 每个事项只维护一份当前记录，保存目标、已知信息、待解决问题和状态，支持跨 session 继续。
4. 允许暂时无法确定归属；不明确时查询或澄清，不强行选择最近的事项。
5. 独立事项并行推进，相关信息按顺序更新；回复综合已收到的信息，不与消息条数绑定。
6. 关联判断可纠正，业务提交必须经过对象核验、具体确认和防重复执行检查。
7. Agent harness 负责上下文、权限、调用预算、失败处理、进度保存和结果核验。模型提出判断，程序控制保存、执行和发布。

技术基础沿用 FastAPI、PostgreSQL、Redis、MySQL、Chroma 和 React。PostgreSQL 保存消息、事项与执行记录；Redis 用于调度和缓存；订单与业务操作以业务系统为准。

## 二 数据与保存方式

### 事项记录

改造现有事项表，每个事项保存一份当前记录：

| 字段 | 内容 |
| --- | --- |
| `task_id` | 事项的独立编号，由服务端生成 |
| `user_id` | 所属用户，取自认证身份 |
| `goal` | 用户要完成的具体目标 |
| `details` | 已知信息，包括按需明确的店铺、订单、商品、数量、包裹、售后申请和处理条件 |
| `waiting_for` | 尚缺的信息、待答问题或正在等待的外部结果 |
| `status` | 处理中、等待用户、等待外部结果、暂停、结束、取消 |

程序另存版本、创建与更新时间，以及信息对应的原始消息或工具结果引用。用户陈述与工具核实结果分别标注来源。稳定查询字段使用数据库普通列，不同业务的内容使用 JSONB。

例如，用户要求退 A 单中的一件耳机，可以保存：

```json
{
  "task_id": "T001",
  "user_id": "U001",
  "goal": "申请耳机退货",
  "details": {
    "order_id": "A",
    "item_id": "ITEM-1",
    "quantity": 1,
    "reason": "左耳没声音"
  },
  "waiting_for": "核实商品与退货资格",
  "status": "处理中"
}
```

事项属于用户，不绑定唯一 session。会话和消息通过关联记录连接事项；一条消息可以关联多个事项。订单号与意图只用于找候选，不作为唯一键。相同订单的开票与退货分别保存，相同订单上的新故障也可以成为新事项。

原始消息、工具结果、确认凭证、操作回执和人工工单复用现有存储。事项是对话进度的唯一写入位置，旧订单草稿退出重复写入；Case 中的业务证据和审计保留。

### 更新要求

- 原话先持久化，再返回已接收；重试使用稳定请求编号，相同编号携带不同内容时拒绝。
- 事项变更与对应变更记录在同一数据库事务保存。变更记录复用事件机制，保留来源、修改前后值和版本，供纠错使用。
- 更新时检查事项版本；冲突后读取最新记录再判断，不覆盖另一执行已保存的信息。
- 事项变化和工具结果及时保存，不等 session 结束或后台摘要生成。
- 创建待执行工作时使用现有 Outbox，将需要投递的记录与状态更新一起提交。模型和外部工具调用在数据库事务之外进行。

## 三 消息处理链路

```text
持续接收并保存消息
        ↓
读取尚未理解的消息与相关上下文
        ↓
判断归属和作用：新建、补充、改口、暂停、取消、续接或澄清
        ↓
程序校验并保存关联与事项变更
        ↓
独立事项并行查询或准备操作
        ↓
检查新消息、事项版本、业务资格与确认
        ↓
保存结果，协调发布回复
```

### 接收与关联调度

同一会话按服务端接收顺序分配消息序号。记录哪些消息尚未理解、哪些已确定关联、哪些仍待澄清；完成关联不等于已经执行或回复。

开始判断时读取当前已收到、尚未理解的消息，保留每条边界。执行期间的新消息继续保存并触发后续判断。可选短暂等待只能用于减少重复追问，正确性不能依赖固定等待窗口。

同一会话的关联判断按顺序协调，保存时检查读取的消息范围与事项版本。通过消息与关联决定的唯一标识防止重复创建事项。跨会话明确关联到已有事项时，读取并更新同一记录。

明确取消和转人工优先处理；自然语言目标不明确时先澄清。未理解的消息保留在原记录中，不能因为已经读取就丢弃。

### 事项执行与并行

同一事项同时只允许一个有效执行推进，独立事项在并发额度内同时运行。新消息补充原因时，仍适用的订单查询可以继续；对象从 A 改为 B 时，A 的结果不能用于 B 的操作。

结果保存和使用前检查事项版本。版本变化后按对象、参数和查询时间判断是否仍可复用，不全量丢弃有效结果，也不让旧结果覆盖新要求。

存在条件或共同业务资源时协调执行：“有货就换，否则退款”先查库存；“改地址后补发”先确定地址；涉及同一订单或共享优惠的冲突写操作按业务约束执行。条件存入事项记录，不引入独立流程引擎。

等待用户或外部结果时保存进度并释放 Worker 和模型额度。用户补充或业务更新到达后，再触发一次短暂执行。

## 四 归属判断与错误兜底

### 准备候选与输出决定

按以下范围准备信息：当前消息、最近原话、客服刚问的问题及所属事项、当前未完成事项。存在历史指代或候选不足时，再查询该用户其他 session 的事项、相关原话和订单。

检索先限制用户和业务访问范围，再按订单、商品、时间与状态找候选。长期偏好不用于推断具体订单。摘要帮助定位线索，歧义或纠错时回查原话。上下文过长时移除无关历史，保留当前请求、对象、否定和条件。

模型对一条或多条消息输出一个或多个关联决定，包含：来源消息、目标事项或新建请求、消息作用、拟修改的信息，以及是否需要澄清。模型输出不直接提交数据库，由 Pydantic 校验结构，再执行服务端校验。

消息作用至少覆盖新建、补充、修改目标、暂停、恢复、取消和仅咨询。简单问候或插问不必创建事项。问题从故障排查转为换货时，可以更新原事项目标；已执行的申请和回执不能被改写或删除。

### 第一层 不确定时暂缓关联

存在多个合理候选、回答无法对应具体问题、对象不明或当前信息冲突时，保存待澄清记录和来源原话，不修改候选事项的业务字段、不启动相关写操作。

优先通过已有资料和只读查询缩小范围；仍不唯一时，询问能够区分对象的一个问题。明确唯一的续接不额外确认。不得仅依据模型自报置信度放行。

### 第二层 程序检查明显冲突

保存关联前检查：

1. 用户、事项、订单和商品是否在当前访问范围内。
2. 消息中明确的订单号、结构化商品选择是否与目标一致。
3. 所回答的问题是否属于该事项，且尚未失效；“是的”“第二个”等回答没有唯一对应问题时不得直接关联。
4. 事项版本是否与本次读取一致，是否已被修改、取消或人工接管。
5. 是否已有正在执行、已成功或结果未知的相关业务操作。

格式错误、越权和过期版本不落库。可恢复的冲突先重新读取，再做有限次数判断；仍无法确定就澄清或交人工。程序校验只能发现可检查的冲突，不能保证所有语义关联正确。

### 第三层 按影响限制操作

| 下一步 | 执行条件 |
| --- | --- |
| 查询信息 | 先验证访问权限；对象有歧义时查询候选，不默认选定后办理 |
| 保存用户补充 | 保存原话来源与变更前值，允许纠正；不得标成业务系统已核实 |
| 回复结果 | 明确商品或订单，对照该对象的证据，便于发现关联错误 |
| 提交退款、改地址等 | 展示具体对象、动作、参数和金额影响，校验确认凭证与最新业务状态 |

确认不能只有一句“确定吗”。参数或对象变化后，相关确认失效；不相关事项的新消息不撤销有效确认。用户点击确认不替代权限、资格和参数校验。

### 第四层 发现关联错误后修正

用户纠正、工具结果冲突或程序检查发现错误时：

1. 停止受影响事项尚未执行的动作，作废对应待确认操作和未发布的过时回复。
2. 依据来源消息和变更记录，只撤回或修正错误关联造成的字段更新。检查当前版本；存在后续修改时重新合并，不能直接恢复整个旧快照。
3. 重新确定正确事项，将原消息和补充关联过去，保留其他正确进度。无明确对象时继续澄清。
4. 使受污染的摘要、缓存和派生记忆失效或重新生成，避免旧错误被再次召回。事项草稿不直接作为长期记忆来源。
5. 简短告知已更正；已发生的错误回复保留历史并补发纠正说明。
6. 若业务已开始或已成功，保留回执并核实实际结果。按业务规则处理撤销或补救；不能靠修改事项记录宣称业务已撤回。

复用事件与审计记录追踪修正原因。一个事项反复关联失败，或写入结果无法确认时，停止自动办理并交人工。

## 五 记忆与 RAG

### 记忆分工

| 信息 | 使用规则 |
| --- | --- |
| 最近原话与待答问题 | 解释“左耳”“第二个”“是的”等补充；记录问题对应的事项 |
| 事项记录 | 立即保存当前进度，支持跨 session 恢复 |
| 历史摘要与原话 | 摘要带来源，必要时回查；当前明确更正优先于过去的陈述 |
| 长期偏好 | 只保存可追溯、跨会话适用的信息；不保存临时订单状态或交易授权 |
| 业务证据 | 保存查询时间与对象；状态变化快的信息在执行前重新查询 |

短期上下文和完整模型请求预算复用 `app/session`。预算包含提示词、工具说明、工具结果和历史；必要内容超限时返回明确错误或请用户缩小范围，不能静默截掉对象、条件和否定。

长期记忆复用 `app/memory` 的候选提取、来源校验、版本更新和检索。后台摘要失败不影响事项恢复。密码、令牌和“以后不用确认”等内容不得变成记忆中的执行权限；删除或纠错后同步处理相关索引与缓存。

跨 session 续接先读取原事项和操作记录，再刷新业务状态。已提交则查询原申请，结果未知则先核实，不重放旧操作。明确唯一的对象直接恢复沟通；新的业务提交重新展示具体参数并取得有效确认。

### 知识检索

RAG 用于政策、配送说明、发票规则和常见问题；订单、金额及申请状态通过业务工具查询。

1. 按事项组织检索条件，保留商品、渠道、时间和用户限制，不补造未知事实。
2. 文档按完整条款或小节切分，保存来源、店铺、品类、版本、生效范围和访问权限。
3. 按适用范围过滤，再结合关键词和向量相似度检索；去重后返回少量片段。额外排序模型按评测结果决定是否引入。
4. 历史订单选择其适用规则，不一律使用最新版本。没有可靠依据、存在冲突或适用条件不明时追问或转人工。
5. 回答保留资料来源。知识片段、附件和工具文本均作为资料，不能修改系统规则、权限和确认要求。

复用 Chroma 和现有索引更新能力。更换向量模型时配套重建索引；发布前验证检索效果并保留可回退版本。

## 六 工具执行与安全控制

### Agent harness

所有模型和工具调用经过统一执行入口，实施工具白名单、参数检查、用户归属检查、调用次数和时长限制、重复调用检测、资源配额及停止检查。

临时查询失败允许有限重试；参数缺失就追问；业务拒绝不反复尝试；写操作超时先查操作状态，不自动重提。没有可核实证据时不能由模型补造结果。已取得业务结果但语言生成失败时使用确定性模板回复。

复用 `app/execution`、`app/reliability`、`app/runtime` 和现有循环检测。业务技能按需加载，只提供办理指引，不扩大工具权限。工具使用受限接口和受控参数，不能执行模型任意生成的 SQL、命令或外部地址。

### 写操作

1. 查询对象归属和业务状态，进行操作预检与确定性计算。
2. 展示订单、商品、数量、动作、原因、金额及相关权益影响。
3. 由服务端签发绑定操作参数和有效版本的确认凭证。
4. 提交前处理此前已收到但尚未理解、可能影响本操作的消息；检查事项版本、人工接管和取消状态。
5. 校验确认并用固定参数执行，业务工具再次验证资格。先建立操作记录，执行后保存真实回执；重复投递返回已有结果。

提交前记录已处理到的消息位置。尚未判断归属的新消息先完成判断，明确无关后不阻塞本次操作。检查消息位置、事项与接管版本，以及登记“操作已开始”，必须在同一短事务内完成；检查后又收到的消息按后续变更处理，不能承诺撤回已开始的请求。

操作记录使用服务端生成的稳定操作编号，绑定用户、对象、动作及固定参数；同一次操作的确认、重试和回执复用该编号。业务系统支持幂等时传递同一编号，不支持时查询实际结果或交人工核实，不能仅靠 Redis 锁保证不重复退款。

转人工或明确取消先被接受、且操作尚未开始时阻止执行；已发往业务系统的请求通过业务查询核实。结果未知时暂停相关写入并交人工，不宣称成功或撤回。

退款、优惠、赠品和运费金额由业务系统及确定性计算提供，统一使用整数分等金额单位。估算与正式预检区分；提交金额或参数改变后重新确认。

### 工具能力边界

按工具实际能力开放办理。部分商品退货必须支持商品行和数量参数；多包裹查询必须返回包裹明细。现有仅接收订单号与原因的 `apply_refund` 不能代替部分退款接口。未实现的换货、补发、赔付等操作转人工；演示发票不能声称正式开票。

## 七 回复与人工接管

事项执行返回结构化结果或待答问题，由会话层协调发布。能够一起回答就合并，耗时事项稍后补充，不等待所有事项完成，也不按每条消息分别回复。

发布前检查新增消息与事项版本，调整受影响内容。限制追加理解次数和时间，持续输入时先回复已核实且不受影响的部分，不无限重跑。已经发送后的新消息正常续接。

按事项、订单、商品和来源核对金额与状态，不能将不同订单的证据拼成同一个结论。高风险字段优先由结构化结果生成。记录哪些问题与结果已发布，通过稳定事件编号避免重连重复展示。

优先问一个能推进主要诉求的明确问题，说明对象。用户已提供、系统能查到或待澄清记录已有的信息不重复询问。“怎么还没好”查询已有事项进度，不重复提交申请。

前端允许持续输入，区分已接收与处理中，复用 SSE 事件流补拉进展。确认卡片按具体操作展示，失效后禁用；不要求用户管理复杂待办面板。

人工接管创建真实工单，交接目标、原话、已核实信息、待答问题、承诺及操作回执。首版沿用会话级接管；同一事项在其他 session 中也不得被机器人自动提交。人工返回后读取最新记录再恢复。未经授权不得承诺赔付、改价或例外权益。

## 八 业务场景规则

| 场景 | 必须执行的规则 |
| --- | --- |
| 一单多件、多个包裹 | 明确商品、数量和运单，不能把一件或一个包裹的结果推广到整单 |
| 方案从故障排查改为换货或退款 | 保留原问题上下文；已提交的申请先核实能否变更，不直接覆盖 |
| “有货就换，否则退”或“改地址后补发” | 先满足条件再提交，有依赖的操作不独立并行 |
| “不退了”“取消刚才那个” | 区分取消待办、取消订单与撤销售后；撤销业务必须有回执 |
| 用户说谢谢或长期不回复 | 不自动等同于事项解决；未完成信息保留，必要时暂停 |
| 退货已寄回、退款已受理 | 记录实际阶段，不宣称仓库已收货或资金已到账 |
| 用券、满减、赠品与组合支付 | 核实实付和适用规则，展示部分退款对金额和权益的影响 |
| 显示签收但用户说没收到 | 同时保留系统状态与用户陈述，进入调查或转人工 |
| 其他客服承诺补偿 | 查询原话、工单和授权，不能把陈述当作已批准操作 |
| 用户在其他渠道申请或修改 | 提交前查询已有申请，避免重复办理 |
| 用户只发图片、语音或链接 | 识别后核实对象；附件无权改变工具权限，识别失败提供文字或人工路径 |
| 加急、指定快递、改规格、额外优惠 | 区分记录需求、申请协调和实际执行，无能力不承诺已安排 |

若目标是提交申请，成功回执可结束提交工作；若目标是解决退货退款，受理后保持等待外部结果，按实际进度继续。

业务回调验证来源并按申请号或运单更新事项；无回调时复用维护进程进行有间隔、有上限的查询。重复和晚到事件不覆盖较新结果，无法判断时重新查询业务系统。

材料或寄回期限记录来源并展示。提醒需要实际调度和通知能力，遵守用户偏好；首版先更新站内记录，离线推送后续接入，不承诺不存在的提醒。

附件后续通过受控上传保存，OCR、视觉模型或语音识别结果与原消息关联；访问范围和保留期限受控。识别出的订单号和金额必须核验，不作为独立授权。

## 九 工程实现与恢复

| 模块 | 改造职责 |
| --- | --- |
| `app/api`、`app/support/store.py` | 持续接收、消息顺序、处理位置、会话关联及发布协调 |
| `app/tasks` | 用户范围事项记录、候选检索、关联校验、版本更新和纠错 |
| `app/agents`、`app/prompts` | 单 Agent 的关联判断、澄清与执行提示词，不引入多 Agent |
| `app/session`、`app/memory` | 上下文预算、历史回查、跨会话检索、来源及派生记忆修正 |
| `app/execution`、`app/reliability` | 并行执行入口、停止检查、确认、幂等、失败及证据核验 |
| `app/tools`、`app/data`、`app/rag` | 业务对象与参数能力、真实数据、确定性计算、适用知识检索 |
| `app/runtime`、`scripts` | 可靠投递、事项执行占位、并发配额、恢复与外部状态维护 |
| `frontend` | 连续发送、事件恢复、协调回复和有效确认卡片 |
| `app/harness`、`app/evaluation`、`tests` | 按消息时间线验证关联、执行、纠错和故障恢复 |

会话级控制只负责转人工、重置等全局操作；普通消息不再无差别使其他事项作废。事项版本控制进度更新，消息序号记录处理位置；同一事项的执行占位跨 session 生效。数据库锁仅覆盖短事务。

未开始的作业可重新投递；已开始的作业先检查工具与业务操作记录再恢复。未知写入不重跑。过期 Worker 不得覆盖新状态、重复写入或发布过时回复。

日志关联消息、事项、执行和操作编号，记录资料来源、结构化决定、变更与纠错、工具结果及发布内容。日志脱敏，不保存隐藏推理。私有人工备注不进入用户可见历史或未经授权的模型上下文。

监控遗漏诉求、误关联、错误恢复、重复追问、事项完成、证据支持、模型成本、排队和查询耗时。权限、确认和归属检查不可在服务降级时跳过；生产数据源故障不能用演示数据冒充结果。

## 十 实施顺序

实施顺序、每次改动范围及完成条件统一维护在 [分步实施入口](refactoring/README.md)。先完成 01 至 05 的保存、接收、候选、归属与纠错，再完成 06 至 09 的执行、并行、回复与业务提交，随后接入 10 至 13 的记忆、RAG、人工接管及外部进度，最后通过 14 迁移上线并退役旧链路。

每次只实现当前小方案，并完成其测试；需要后续接入的接口分别验证契约和最终集成。新链路在分步开发期间默认关闭，生产切换前必须满足下方验收标准，不把局部演示视为整个项目重构完成。

数据结构使用版本化迁移，取消旧任务表中会话内只能一个活跃事项的限制。能明确映射的旧草稿转成事项；无法确定的保留为历史参考，不能自动生成待执行业务操作。

同一用户相关会话使用一致的新旧规则。API、Worker 与前端配套升级；处理在途作业后切换。回退保留业务操作记录，不通过旧队列重新执行历史申请。

首版必须覆盖所有已开放工具的上述保护；尚无业务接口的场景明确转人工。附件识别、额外排序模型和离线通知按需要后续增加。

## 十一 验收标准

| 场景 | 断言 |
| --- | --- |
| 连续消息在执行前、执行中和回复后到达 | 信息不丢失，不重复询问已提供内容；不要求始终只回复一次 |
| 一条消息涉及两个事项 | 各部分关联正确，新诉求不遗漏 |
| 两笔相似订单或两个待答问题 | 不明确就澄清，不凭偏好或最近出现顺序强行绑定 |
| 错关联后用户纠正 | 只修正相关字段，旧确认失效，其他正确进度保留 |
| 错关联后已有后续修改 | 不用旧快照覆盖新信息，冲突可解释并可恢复 |
| 错误已进入摘要或缓存 | 纠错后不再召回错误结论，原话和审计保留 |
| 错误操作已经开始或成功 | 查询真实状态，执行必要补救或转人工，不虚报撤回 |
| 跨 session 续接与同时修改 | 找回同一记录，版本冲突不覆盖，不重放旧授权 |
| 两个独立事项一快一慢 | 并行推进，快结果先发布，慢结果后续补充且不重复 |
| 条件请求与同订单冲突操作 | 先核实条件，冲突操作不同时提交 |
| 部分退款、多包裹与优惠分摊 | 商品、数量、运单与金额正确，工具能力不足时不扩大范围 |
| 确认前收到修正或取消 | 先处理影响，旧参数不能提交 |
| 受理成功但未完成业务 | 状态与回复准确，不因道谢或生成回复成功而关闭 |
| 外部更新重复、乱序或来自其他渠道 | 不倒退状态，不重复申请，必要时重新查询 |
| 人工接管后另一 session 继续询问 | 遵守接管范围，交接进度完整，不争抢提交 |
| 无知识依据、历史规则或签收争议 | 使用适用来源，不编造、不把用户陈述与系统事实混淆 |
| 越权、恶意资料与附件识别错误 | 不泄露数据，不扩大权限，不绕过确认 |
| 重启、重复投递、超时和持续输入 | 不丢消息、不无限执行、不重复写入、不发布过时结果 |

分层验证：固定模型与工具返回值检查程序规则；真实模型配受控工具验证理解与关联质量；隔离的 PostgreSQL、Redis 和业务环境验证多实例并发及恢复。真实模型评测使用脱敏、多事项、跨会话和纠错场景，按会话隔离数据。

权限、确认、幂等和对象隔离由代码断言验收，不依赖模型打分。记录关联准确率、澄清是否必要、纠错成功率、错误业务操作、耗时和成本。每次修改提示词、模型、工具或检索配置后运行对应回归；记录实际结果，不以模拟测试代替真实模型与集成验收。
