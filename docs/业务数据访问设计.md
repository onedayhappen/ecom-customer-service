# 业务数据访问设计

## 查询与存储的分工

当前事项先经 `execute_task_tool` 按配置选择本地执行或 MCP 业务读取；本地和远端复用 `registry → dispatch → CommerceService → BusinessStore → MySQL`。事项流程、报价和准备确认保持本地。模型传入结构化查询和对象引用，程序负责所属用户、平台、商家、规则与分页范围。订单状态和金额不从模型、记忆或政策文本推断。

| 文件                                                                                              | 职责                                                                                   |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| [catalog.py / contracts.py](../app/tools/catalog.py)                                              | 名称、说明、副作用及严格参数契约；参数实现见 [contracts.py](../app/tools/contracts.py) |
| [dispatch.py](../app/tools/dispatch.py)                                                           | 注入身份，区分读取、报价、准备操作及事项流程                                           |
| [service.py](../app/services/commerce/service.py)                                                 | 组装业务服务、统一查询回执，提供请求范围内的测试工厂替换                               |
| [base.py](../app/services/commerce/base.py)                                                       | 对象解码、订单归属、可信业务范围与快照                                                 |
| [reads.py](../app/services/commerce/reads.py) / [queries.py](../app/services/commerce/queries.py) | 领域读取与面向工具的事实视图                                                           |
| [collection_queries.py](../app/services/commerce/collection_queries.py)                           | 订单、售后、持券、发票等集合的 SQL 筛选、键集分页、批量关联与完整聚合                  |
| [rules.py](../app/services/commerce/rules.py)                                                     | 确定性资格、费用及政策适用规则                                                         |
| [pagination.py](../app/services/commerce/pagination.py)                                           | 签名游标、稳定排序与 SQL 分页                                                          |
| [business_store.py](../app/data/business_store.py)                                                | MySQL 连接、事务及有界结果读取                                                         |

`CommerceService` 用显式继承组合查询、扩展写入、订单变更和履约服务。判断某个工具的最终实现时，应沿类继承查找实际覆写方法，不能只读同名基础方法。

当前查询层的继承关系是 `QueryService(ItemQueryService, CollectionQueryService, ReadService, RuleService)`。集合筛选、统计和批量关联主要读 [collection_queries.py](../app/services/commerce/collection_queries.py)，包裹/售后完整商品行读 [item_queries.py](../app/services/commerce/item_queries.py)，账号视图和业务工具覆写读 [queries.py](../app/services/commerce/queries.py)。

## 一次读取如何完成

以查询订单为例：

1. 工具参数模型解析 `order_ref`，拒绝额外字段；身份由请求级上下文取得。
2. `owned_order` 按平台、订单号和当前用户查询，并检查服务端业务范围。
3. 同一读取事务汇总订单、购买行及关联记录，超过内嵌数量的部分提供继续查询引用。
4. `CommerceService.read` 添加来源表、观察时间、同步时间缺项与完整性信息。
5. 事项执行器保存工具事件；回复投影只使用与当前事项匹配且仍有效的回执。

商品搜索支持商品、商家关键词及显式预算、规格过滤。存在不认识的属性或没有记录的库存时返回缺项，不能把未应用条件当作已满足。匹配、排序和分页用于发现对象，不直接给出“最适合”或办理授权。

## 统一结果契约

成功回执包含 `ok`、`success`、`data`、`observed_at`、`data_as_of`、`sources`、`completeness`、`limitations` 和 `next_cursor`。普通业务读取还添加 `status` 与 `missing_fields`。

当前业务库没有统一上游同步水位，`CommerceService.read` 设置 `data_as_of=None`，并明确读取时刻不等于同步时刻。成功查询仍可能是 `partial`；`status=no_match` 只表示本次没有匹配记录，不能推断现实中未发货、未退款或不存在业务。

失败回执把业务错误保留在 `error.code/message`，同时映射为执行器使用的 `error_code`。例如暂不可用映射为瞬时失败、状态改变映射为确认失效。参数错误只返回有限字段路径和类型，不泄露输入值、数据库异常或连接信息。

演示订单、售后、退款和票据读取保留 `is_demo`／来源标识，回复事实与人工交接继续区分演示和真实业务。模拟渠道并非业务库缺失时的自动替身，仅作用于明确初始化的演示订单；读取完成状态不能将模拟退款解释为真实到账。

## 事务与分页

`BusinessStore` 为每次事务建立 MySQL 连接，设置 UTC 与 `REPEATABLE READ`。读取使用只读事务，结束回滚；写入成功提交，异常回滚后关闭连接。它目前不复用旧订单 DAO 的连接池，不能将 `ORDER_DB_POOL_*` 描述为当前全部工具的连接池控制。

`Transaction.all` 使用流式字典游标，最多探测 10001 行；超过 10000 行明确要求缩小范围。常规列表在 SQL 层分页，游标绑定身份、工具、参数和范围。跨请求分页不是不可变快照，前后业务变更可能需要重新查询。

订单、售后和发票列表按创建时间降序、唯一标识升序翻页；持券按到期时间与持券标识升序翻页。键集游标记录排序方向与末行键，不以整个集合的状态摘要或偏移量定位，因此页内记录状态改变不会导致下一页失效或因偏移移动而漏行。筛选总数按每次读取重新统计。

这些列表的关联摘要通过窗口函数批量读取，订单行的物流、售后状态和数量在 SQL 中聚合。金额、占用、配送数量等汇总不受摘要或当页范围影响。订单物流的 `quantities` 仅为最多 20 行的摘要，`quantities_total`／`quantities_truncated` 标明范围，`quantity_totals` 是完整订单数量汇总，`quantities_query` 可继续分页查询订单行。大集合回归见 [test_collection_queries.py](../tests/test_collection_queries.py)。

资格与金额计算见 [业务规则与权益计算设计](业务规则与权益计算设计.md)。写入还需要操作确认、资源占用和数据库锁，见 [业务操作与交易设计](业务操作与交易设计.md)。

## 兼容代码与当前主链路

`app/data/order_service.py`、`product_service.py`、`logistics_service.py`、`dto.py` 和 Redis 缓存适配保留旧读取接口或测试用途。旧适配的“未配置 DSN 时显式使用 mock”和缓存行为，不能推广为新工具链的默认行为：当前 `BusinessStore` 缺少 DSN 直接返回业务不可用，不静默回退演示数据。

`commerce_dao.py` 仍保留历史实现，但 `ensure_schema` 已明确拒绝建立退役的 `commerce_*` 表。初始化应使用版本迁移，不调用旧 DAO 重建结构。

MySQL 迁移先建立账号、订单和商品基础表，再按 `VERSIONS` 执行 SQL 与结构调整，用 `schema_migrations` 记录版本。`--check` 只检查登记版本；seed 脚本用于明确的数据导入，与迁移、用户注册和外部平台同步分别处理。结构与业务关系见 [数据库表设计](数据库表设计.md)。

## 从摘要读取完整集合

内嵌摘要只用于定位对象，完整读取入口直接返回 `tool` 和 `arguments`。不要从显示文字拼参数，也不要把父查询的下一页游标交给另一个明细工具。

例如，先 `get_logistics(target_ref=订单引用)` 找到具体包裹，再使用该包裹的 `items_query` 调用 `get_shipment_items`；需要更多商品行时把同一工具返回的 `next_cursor` 带入后续请求。售后过程事件和售后商品行同样分别翻页。

| 读取对象                   | 完整入口                                        | 不可混用的分页范围                              |
| -------------------------- | ----------------------------------------------- | ----------------------------------------------- |
| 订单购买行 | `get_order_items(order_ref, cursor)` | 订单商品行与订单列表 |
| 原始/换货/退货包裹商品行   | `get_shipment_items(target_ref, cursor)`        | 包裹商品行与 `get_logistics` 的轨迹             |
| 售后申请商品行             | `get_after_sale_items(after_sale_id, cursor)`   | 申请商品行与 `get_after_sale_status` 的过程事件 |
| SKU 补货计划               | `get_restock_plan(sku_id, cursor)`              | SKU、更新时间排序与计划编号                     |
| 脱敏联系方式或平台账号     | `get_my_account(collection, cursor)`            | `contacts` 与 `platform_accounts` 两个集合      |
| 某开票申请下的全部正式发票 | `get_invoices(target_ref, view=issued, cursor)` | 正式发票集合与默认申请列表                      |

以上完整集合默认每页最多 20 条，回执使用 `data.total/has_more` 和顶层 `next_cursor`；末页游标为空。签名绑定当前用户、工具、查询参数、渠道范围和排序键，有效期 15 分钟。每一页重新核验归属，错误订单行或售后关系不能靠分页隐藏；明细中的申请金额、包裹数量仍不代表退款成功或实际签收。

补货计划按更新时间倒序、计划编号正序读取，商品明细按订单行编号正序读取。发票列表的 `document_query` 指向单份文件读取，不属于正式发票列表的下一页。

当前同时保留两种分页实现：`sql_page` 按排序键实时读取，支持混合升降序；`page` 用于仍在内存处理的有界集合，游标还绑定完整集合摘要，集合变更会明确要求重查。不能把“SQL 列表已迁移为键集分页”理解为项目中所有集合都没有快照校验。

## 扩展一个业务能力

新增读取时依次补参数模型、工具目录、服务方法、分发入口和 `selection.py` 的相关工具组，再检查对象归属、分页、缺项及证据渲染。新增可办理能力还需预检、固定确认、幂等回执和结果核实，不能仅增加一个直接写库的模型工具。
